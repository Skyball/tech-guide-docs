评估为什么重要

No metrics, no improvement. — 没有度量，就没有改进。Agent 的输出质量本质上是主观的：同一个回答，不同用户可能给出截然相反的评价。评估体系是将「感觉不错」转化为「可量化、可复现、可对比」的唯一路径。

评估金字塔

🏭 生产监控 — 实时质量追踪、异常告警、用户反馈闭环
🔬 在线 A/B 测试 — 真实流量下的效果对比
📊 离线评估 — Golden Dataset + 自动化指标

从底层到顶层：成本递增，但离真实用户越近。三层缺一不可。

✅ 正确做法

  • 建立 Golden Dataset，每次改 Prompt 都跑回归
  • 离线指标 + 在线 A/B 双重验证
  • 生产环境持续监控幻觉率、拒答率
  • 将评估纳入 CI/CD 流水线

❌ 常见反模式

  • 只用 Demo 验证 — 3 个例子跑通就上线
  • 靠感觉调 Prompt — 「我觉得这次回答更好」
  • 只看离线指标 — 忽略用户真实满意度
  • 评估一次就忘 — 没有持续监控和迭代
💡
Agent 工程师的核心能力：不是写出最炫的 Prompt，而是建立「改 → 测 → 比 → 上线」的闭环。评估体系是这个闭环的基础设施。

RAGAS 框架

RAGAS（Retrieval Augmented Generation Assessment）是目前最流行的 RAG 评估框架，提供上述所有指标的自动化计算，支持 LLM-as-Judge 模式。

faithfulness
生成内容是否被 context 支持
answer_relevancy
回答与问题的相关程度
context_recall
ground truth 是否被检索覆盖

LLM-as-Judge

用大模型（如 GPT-4o）评估小模型的输出。成本低、可扩展，但需注意：

  • Judge 模型应强于被评估模型
  • 使用结构化 Rubric（评分标准），避免开放式「好不好」
  • 定期与人工评估校准（Human Alignment）
  • 注意 Position Bias — 交换 A/B 顺序再评一次

人工评估协议

维度1 分3 分5 分
准确性明显错误/幻觉基本正确，有小瑕疵完全准确
完整性遗漏关键信息覆盖主要要点全面详尽
可读性混乱难懂结构清晰简洁专业
安全性包含有害内容无有害但边界模糊完全安全合规
Scoring Rubric 设计原则：每个分数档位有具体示例，标注员培训后先跑 20 条校准，Cohen's Kappa ≥ 0.6 才正式标注。

代码示例：RAGAS 评估流水线

from datasets import Dataset
from ragas import evaluate
from ragas.metrics import (
    faithfulness,
    answer_relevancy,
    context_precision,
    context_recall,
)

# Golden Dataset 格式
eval_data = {
    "question": ["告警 CPU 使用率超过 90% 怎么处理？"],
    "answer": ["建议先检查 top 进程，确认是否为正常流量峰值..."],
    "contexts": [["CPU 告警 SOP: 1. 查看 top 进程 2. 检查流量..."]],
    "ground_truth": ["查看 top 进程，检查是否为正常流量，必要时扩容"],
}

dataset = Dataset.from_dict(eval_data)

# 运行评估（使用 GPT-4o 作为 Judge）
result = evaluate(
    dataset,
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
    llm="gpt-4o",
)

print(result)
# {'faithfulness': 0.92, 'answer_relevancy': 0.88, ...}

# 设置阈值，低于阈值则 CI 失败
THRESHOLDS = {"faithfulness": 0.85, "answer_relevancy": 0.80}
for metric, threshold in THRESHOLDS.items():
    score = result[metric]
    assert score >= threshold, f"{metric}={score} < {threshold}"

在线评估：A/B 测试

离线指标高 ≠ 用户满意。离线评估无法捕捉：延迟感知、交互体验、长尾 query、用户意图多样性。A/B 测试是在真实流量中验证改动的金标准。

A/B 测试设计要素

流量分割

  • 按 user_id 哈希分桶（保证同一用户始终在同一组）
  • 典型比例：90/10 或 95/5（新方案占小流量）
  • 避免按 session 分桶（同一用户可能跨组）

核心指标选择

  • Primary 任务完成率、用户满意度（👍/👎）
  • Secondary 平均对话轮数、拒答率
  • Guardrail 延迟 P99、单次成本、错误率

统计显著性与实验时长

# 样本量估算（简化公式）
# n = 16 * σ² / δ²
# σ = 指标标准差, δ = 期望检测的最小差异 (MDE)

import math

def sample_size(baseline_rate, mde, alpha=0.05, power=0.8):
    """二项分布指标（如任务完成率）的样本量估算"""
    p = baseline_rate
    delta = mde
    z_alpha = 1.96   # α=0.05 双侧
    z_beta = 0.84    # power=0.80
    n = ((z_alpha + z_beta) ** 2 * p * (1 - p)) / (delta ** 2)
    return math.ceil(n)

# 例：基线完成率 70%，想检测 3% 的提升
n = sample_size(baseline_rate=0.70, mde=0.03)
print(f"每组需要 {n} 个样本")  # ≈ 1818

# 实验时长 = 样本量 / 日活用户数
# 若日活 5000，每组需 1818 → 约 1 天（但建议至少 7-14 天）

常见陷阱

⚠️ Novelty Effect

用户对新 UI/新回答风格的新鲜感导致短期指标虚高。对策：实验至少跑 2 周，观察指标是否收敛。

⚠️ Carryover Effect

用户在不同版本间切换导致行为污染。对策：按 user_id 固定分桶，实验期间禁止切换。

Feature Flag 管理 Prompt 版本

# prompts/registry.yaml
# versions:
#   alert_analysis_v3:
#     weight: 90
#     prompt_file: prompts/alert_v3.txt
#   alert_analysis_v4:
#     weight: 10
#     prompt_file: prompts/alert_v4.txt

import hashlib

def get_prompt_version(user_id: str, versions: dict) -> str:
    bucket = int(hashlib.md5(user_id.encode()).hexdigest(), 16) % 100
    cumulative = 0
    for name, cfg in versions.items():
        cumulative += cfg["weight"]
        if bucket < cumulative:
            return name, cfg["prompt_file"]
    return list(versions.items())[-1]

def estimate_agent_cost(llm_calls: list[dict], pricing: dict) -> float:
    """估算 Agent 会话总成本"""
    total = 0.0
    for call in llm_calls:
        model = call["model"]
        p = pricing[model]
        total += (call["input_tokens"] / 1e6) * p["input"]
        total += (call["output_tokens"] / 1e6) * p["output"]
    return total

]

成本优化策略

目标不是用最便宜的模型，而是在保证质量的前提下将成本降低 50%+。以下策略按 ROI 排序。

策略 1：Model Routing（模型路由）

简单问题用小模型，复杂问题用大模型。典型架构：Haiku/GPT-4o-mini 做分类路由 → Sonnet/GPT-4o 做复杂推理。

async def routed_completion(query: str) -> str:
    complexity = await classify_query(query, model="gpt-4o-mini")  # ~$0.0001

    if complexity == "simple":
        return await llm_complete(query, model="gpt-4o-mini")   # ~$0.001
    elif complexity == "medium":
        return await llm_complete(query, model="gpt-4o")        # ~$0.01
    else:
        return await agent_loop(query, model="gpt-4o")           # ~$0.10
# 若 70% query 是 simple → 平均成本降低 60%+

策略 3：Semantic Caching（语义缓存）

import numpy as np
from functools import lru_cache

class SemanticCache:
    def __init__(self, threshold=0.92):
        self.entries = []  # [(embedding, query, response)]
        self.threshold = threshold

    async def get_or_compute(self, query: str, compute_fn) -> str:
        emb = await embed(query)
        for cached_emb, cached_q, cached_resp in self.entries:
            sim = np.dot(emb, cached_emb) / (np.linalg.norm(emb) * np.linalg.norm(cached_emb))
            if sim >= self.threshold:
                return cached_resp  # 缓存命中，成本 = $0
        response = await compute_fn(query)
        self.entries.append((emb, query, response))
        return response
# FAQ 类场景缓存命中率 30-50% → 等效成本降低 30-50%

策略 4：Context Window 优化

# 对话历史压缩：保留最近 N 轮 + 早期摘要
async def compress_history(messages: list, max_tokens=4000) -> list:
    if count_tokens(messages) <= max_tokens:
        return messages

    recent = messages[-6:]  # 保留最近 3 轮
    older = messages[:-6]
    summary = await llm_summarize(older, model="gpt-4o-mini")
    return [{"role": "system", "content": f"历史摘要: {summary}"}] + recent

策略 5-7：Batch / Fine-tuning / 其他

Batch Processing

非实时任务用 Batch API（OpenAI Batch 半价）。适合：离线评估、数据标注、报告生成。

Fine-tuning

高频固定格式任务（如告警分类）微调小模型，推理成本降 90%，延迟降 80%。

Output Token 控制

设 max_tokens、要求简洁输出格式（JSON vs 散文），Output 单价是 Input 的 3-5 倍。

🎯
优化优先级：Semantic Cache（零成本命中）→ Model Routing（60% 降本）→ Context 压缩（Agent 场景关键）→ Prompt 精简 → Fine-tuning（长期 ROI）。先度量，再优化，每次只改一个变量。

面试题 + 实战练习

常见面试题

Q1：如何评估 RAG 系统的质量？

参考答案：

分三层评估：

  1. 检索层：Context Precision（检索结果有多准）、Context Recall（该检索的是否都检索到）。用 RAGAS 或 BEIR benchmark。
  2. 生成层：Faithfulness（是否幻觉）、Answer Relevancy（是否答非所问）。LLM-as-Judge + 人工抽检。
  3. 端到端：Answer Correctness（与 ground truth 对比）。Golden Dataset 回归测试。

关键：建立 Golden Dataset（200+ 条），每次改检索策略或 Prompt 都跑全量回归。设置 faithfulness ≥ 0.85 为 CI 门禁。

Q2：如何设计 Prompt 的 A/B 测试？

参考答案：

  1. 假设：明确「改 X → 预期 Y 指标提升 Z%」
  2. 分桶：按 user_id 哈希，90/10 分流，Feature Flag 控制 Prompt 版本
  3. 指标：Primary = 任务完成率；Guardrail = P99 延迟、单次成本、faithfulness
  4. 样本量：用 MDE 公式计算，通常每组 1000-2000 样本
  5. 时长：至少 7-14 天，避免 Novelty Effect
  6. 决策：Primary 指标显著提升 + Guardrail 无退化 → 全量发布
Q3：如何将 Agent 的 Token 成本降低 50%？

参考答案：

Agent 成本大头是 Input Token（每次 Tool Call 重传上下文）。组合拳：

  1. Model Routing：70% 简单 query 走 mini 模型（成本降 90%）
  2. Context 压缩：Tool Result 只保留摘要，历史对话滚动摘要（Input 减 50%）
  3. Semantic Cache：FAQ 类 30% 命中率（等效降 30%）
  4. 减少 Tool Call 次数：合并工具、预检索（5 次 → 3 次 = 降 40%）
  5. Prompt 精简：System Prompt 从 2000 → 200 tokens

综合效果：0.6 × 0.5 × 0.7 × 0.6 ≈ 12.6% 原始成本，即降约 87%。实际保守估计 50-60% 降本可达。

实战练习

练习 1：设计告警分析 Agent 的评估方案

你的团队刚上线一个告警分析 Agent（输入告警 JSON → 输出处置建议）。请设计完整的评估方案，包括：离线指标选择、Golden Dataset 构建计划、A/B 测试设计、成本监控。

参考答案

离线指标：

  • Faithfulness ≥ 0.90（处置建议必须基于 Runbook，不能幻觉）
  • Answer Relevancy ≥ 0.85（建议与告警类型相关）
  • 自定义：步骤完整性（是否包含「确认 → 止损 → 根因 → 修复」四步）

Golden Dataset：

  • 从生产日志采样 300 条真实告警
  • 人工编写 50 条 edge case（OOM、网络分区、级联故障）
  • SRE 团队双人标注 ground truth 处置方案
  • Cohen's Kappa ≥ 0.7 后定版为 eval-v1.0

A/B 测试：

  • Primary：SRE 采纳率（👍 反馈 / 总分析数）
  • Guardrail：P99 延迟 < 30s，faithfulness 不下降
  • 95/5 分流，跑 14 天，日活 ~200 告警 → 每组 ~1400 样本

成本监控：

  • 每次分析记录 input/output tokens，Dashboard 展示日均成本
  • 告警 > $0.15/次 时触发 Review（正常应 ~$0.08-0.12）

练习 2：成本优化方案设计

当前 Agent 每次分析平均消耗 35K input tokens + 2.5K output tokens（GPT-4o），日处理 800 次，月成本约 $2,600。请设计优化方案将月成本降至 $1,300 以下，且 faithfulness 不低于 0.85。

参考答案

现状分析：

  • 单次成本 ≈ $0.108，Input 占 92%
  • 35K input 中：System Prompt ~2K，Runbook 全文 ~15K，Tool Results ~12K，历史 ~6K

优化方案：

措施Input 节省质量影响
Runbook 改 RAG 检索 top-3 片段（15K→3K）-12K无（更精准）
Tool Result 摘要压缩（12K→4K）-8K轻微，监控 faithfulness
简单告警路由到 GPT-4o-mini（40% 流量）成本 -85% for 40%仅简单告警，复杂仍用 4o
Semantic Cache（15% 命中率）-15% 总请求无（完全相同 query）

预期效果：

  • 优化后 Input：35K → ~12K（-66%）
  • 40% 流量走 mini：等效再降 30%
  • Cache 15%：等效再降 15%
  • 综合：$2,600 × 0.34 × 0.70 × 0.85 ≈ $530/月（远低于 $1,300 目标）
  • faithfulness：RAG 检索更精准，预期 ≥ 0.88
🎯
学习路径建议：先在自己的 Agent 项目上建立 Golden Dataset（20 条即可起步）→ 接入 RAGAS 跑通离线评估 → 加 CI 回归门禁 → 再考虑 A/B 测试和成本优化。评估和成本是一体两面：没有评估的优化是盲目的，没有成本意识的评估是不可持续的。
