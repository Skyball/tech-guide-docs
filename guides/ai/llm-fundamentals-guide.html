Transformer 架构全貌

2017 年 Google 论文 "Attention is All You Need" 提出 Transformer，彻底改变了 NLP 领域。它抛弃了 RNN/LSTM 的序列递归结构，完全依赖 Self-Attention 机制，成为 GPT、BERT、T5 等所有现代 LLM 的基石。

为什么 Transformer 取代了 RNN/LSTM？

RNN / LSTM 旧范式

  • 按时间步 串行 处理，无法并行训练
  • 长距离依赖通过隐状态传递，容易 梯度消失
  • 序列越长，信息衰减越严重
→

Transformer 新范式

  • 所有 token 位置 并行 计算 Attention
  • 任意两个位置直接交互，路径长度 O(1)
  • GPU 友好，训练效率大幅提升

Encoder-Decoder 整体结构

# Transformer 架构（简化示意）
# 原始论文用于机器翻译：Encoder 理解源语言，Decoder 生成目标语言

输入序列 → [Embedding + Positional Encoding]
                ↓
         ┌─── Encoder ×N ───┐
         │  Multi-Head Attn  │
         │  Add & Norm       │
         │  Feed Forward     │
         │  Add & Norm       │
         └───────────────────┘
                ↓ (Cross-Attention)
         ┌─── Decoder ×N ───┐
         │  Masked Self-Attn │
         │  Cross-Attention  │  ← 关注 Encoder 输出
         │  Feed Forward     │
         └───────────────────┘
                ↓
         Linear → Softmax → 输出概率

Self-Attention 逐步拆解

  1. 输入：每个 token 被映射为 Query(Q)、Key(K)、Value(V) 三个向量
  2. 计算相关性：Q 与所有 K 做点积，得到 attention score
  3. 归一化：除以 √dk 后做 Softmax，得到权重分布
  4. 加权求和：用权重对 V 加权，得到该位置的输出表示

直觉类比：每个 token 在问「我应该关注句子中的哪些其他 token？」——Attention 权重就是答案。

Multi-Head Attention（多头注意力）

单头 Attention 只能捕捉一种关系模式。Multi-Head 将 Q/K/V 拆成 h 个头，各自独立计算 Attention，最后拼接：

# 不同 head 可能学到不同模式：
Head 1: 语法依存关系（主语 → 谓语）
Head 2: 指代消解（"它" → "服务器"）
Head 3: 位置邻近关系
Head 4: 语义相似性

MultiHead(Q,K,V) = Concat(head₁, ..., headₕ) · WO

典型配置：GPT-3 使用 96 个 head，每个 head 维度 128。

Positional Encoding（位置编码）

Attention 本身不包含位置信息——"猫追狗"和"狗追猫"在纯 Attention 下等价。因此必须注入位置信息：

# 原始 Transformer：正弦/余弦位置编码
PE(pos, 2i)   = sin(pos / 100002i/d)
PE(pos, 2i+1) = cos(pos / 100002i/d)

# 最终输入 = Token Embedding + Positional Encoding
input = Embedding(token) + PE(position)

现代模型（GPT、LLaMA）多用 RoPE 或 ALiBi，详见「上下文窗口」章节。

Layer Normalization + 残差连接

残差连接 (Residual)

output = LayerNorm(x + Sublayer(x))

让梯度可以直接流过，解决深层网络训练困难的问题。Transformer 通常 12~96 层。

Layer Norm

对每个 token 的向量做归一化（而非 Batch Norm），稳定训练。Post-Norm（原始）vs Pre-Norm（现代 LLM 更常用）。

🤖 Agent 开发提示：理解 Transformer 结构有助于调试 Agent 行为——上下文过长时 Attention 分散、Layer 越深抽象程度越高。选模型时关注层数、head 数、hidden size 这些架构参数。

Attention 机制详解

Attention 是 Transformer 的核心。理解 Q/K/V 三要素，就理解了 LLM 如何「阅读」和「关联」文本中的信息。

Q/K/V 直觉类比：图书馆检索

概念图书馆类比数学含义
Query (Q)你的问题："关于分布式系统的书在哪？"当前 token 想要查询什么信息
Key (K)每本书的标题/索引标签每个 token 提供的「可被匹配」的特征
Value (V)书的实际内容每个 token 携带的实际语义信息

检索过程：用 Q 与所有 K 计算相似度 → 得到权重 → 按权重从 V 中「借阅」信息。

Attention Score 计算公式

Attention(Q, K, V) = softmax( QKT / √dk ) · V

# 逐步拆解：
scores = Q @ K.T          # 点积，shape: (seq_len, seq_len)
scores = scores / √d_k    # 缩放，防止点积值过大
weights = softmax(scores) # 归一化为概率分布，每行和为 1
output = weights @ V      # 加权求和 Value

为什么要除以 √dk？

当维度 dk 较大时，Q·K 点积的方差约为 dk，数值会很大。Softmax 在大数值下梯度趋近于 0（梯度消失），训练不稳定。

除以 √dk 将方差归一化到 1，使 Softmax 输入保持在合理范围。这是工程细节，但面试常考。

Masked Attention（因果掩码）

在 Decoder（GPT 类模型） 生成时，每个 token 只能看到它之前的 token，不能「偷看未来」：

# Causal Mask：上三角矩阵设为 -∞
# 位置 3 只能 attend 到位置 0,1,2

     t₀   t₁   t₂   t₃
t₀ [  ✓    ✗    ✗    ✗  ]
t₁ [  ✓    ✓    ✗    ✗  ]
t₂ [  ✓    ✓    ✓    ✗  ]
t₃ [  ✓    ✓    ✓    ✓  ]

# 实现：scores[i,j] = -inf if j > i

这保证了 自回归生成 的正确性——模型在预测第 n 个 token 时，不会利用第 n+1 个及之后的信息。

Self-Attention vs Cross-Attention

Self-Attention 自注意力

Q、K、V 都来自同一个序列。每个 token 关注同一序列中的其他 token。

用途：GPT 理解上下文；BERT 双向编码。

Cross-Attention 交叉注意力

Q 来自 Decoder，K/V 来自 Encoder 输出（不同序列）。

用途：T5 翻译时 Decoder 关注源语言；多模态模型中文本关注图像特征。

💡
Agent 场景：RAG 检索到的文档片段，在 Cross-Attention 架构（如 T5）中会作为 Encoder 输入；在纯 Decoder 模型（GPT）中则直接拼接到 Prompt 里，通过 Self-Attention 关联。

Tokenization 分词

LLM 不直接处理文字，而是处理 Token——整数 ID 序列。分词方式直接影响成本、上下文利用率和多语言支持能力。

核心认知：Token ≠ Word

你好世界["你", "好", "世界"] 或 ["你好", "世界"]取决于训练语料

BPE 算法逐步演示

Byte Pair Encoding：从字符级开始，迭代合并最高频的相邻字符对。

# 初始词汇表（字符级）
语料: "low lower newest widest"
词汇: {l, o, w, e, r, n, s, t, i, d}

# 迭代 1：最高频对 "e"+"s" → "es" (3次)
词汇: {..., es}

# 迭代 2：最高频对 "es"+"t" → "est" (3次)
词汇: {..., est}

# 迭代 3：最高频对 "l"+"o" → "lo" (2次)
词汇: {..., lo}

# ...重复直到词汇表达到目标大小（如 50K）

# 最终编码 "lowest" → ["lo", "west"] 或 ["low", "est"]

SentencePieceT5, LLaMA-2, Gemini语言无关，直接处理 Unicode；无需预分词空格

生成过程：解码策略

LLM 生成文本的本质是逐 token 预测——每次输出一个 token 的概率分布，采样一个 token 追加到序列，再预测下一个。解码策略决定了「如何从分布中选 token」。

自回归生成循环

# 伪代码：自回归生成
prompt_tokens = tokenize("分析以下告警：CPU 使用率 95%")
generated = prompt_tokens.copy()

while not is_stop(generated):
    logits = model(generated)           # 模型输出每个 token 的原始分数
    probs = apply_decoding(logits)      # 应用 temperature / top_p 等
    next_token = sample(probs)          # 从分布中采样
    generated.append(next_token)

response = detokenize(generated[len(prompt_tokens):])

Temperature（温度）

控制概率分布的「尖锐程度」。原始 logits 为 z，温度为 T：

pi = exp(zi / T) / Σ exp(zj / T)

T → 0   : 分布极尖，几乎总是选最高概率 token（确定性）
T = 1   : 原始分布，不做修改
T → ∞   : 分布趋于均匀，输出随机
T = 0：贪婪解码，适合代码生成、数据提取、结构化输出
T = 0.7~1.0：适度随机，适合对话、创意写作

Top-K 与 Top-P（Nucleus）采样

Top-K

只保留概率最高的 K 个 token，其余置零后重新归一化。

# K=50：只从 top 50 候选中选
# 问题：分布平坦时 K=50 仍太宽；尖锐时 K=50 可能多余

Top-P (Nucleus)

按概率从高到低累加，取累积概率 ≥ P 的最小 token 集合。

# P=0.9：保留覆盖 90% 概率质量的 token
# 自适应：尖锐分布 → 少 token；平坦 → 多 token

Beam Search

维护 B 条最优候选路径，每步扩展所有候选，保留总分最高的 B 条。适合翻译、摘要等需要全局最优的任务，但：

  • 输出多样性低，容易重复
  • 计算成本是贪婪解码的 B 倍
  • 现代 Chat 模型很少使用，Top-P 更常用

Temperature + Top-P 如何协同

# 典型处理顺序：
logits → ÷ temperature → softmax → top_p 截断 → 采样

# 低 temperature 使分布尖锐 → top_p 截断后候选更少 → 更确定
# 高 temperature 使分布平坦 → top_p 保留更多候选 → 更随机

不同任务的参数推荐

任务类型TemperatureTop-P说明
代码生成0 ~ 0.2—确定性优先，语法必须正确
告警分析 / QA0 ~ 0.30.9事实准确，少量措辞变化可接受
Agent 工具调用0—JSON/函数参数必须精确
创意写作0.8 ~ 1.20.95多样性优先
头脑风暴1.0 ~ 1.50.95高随机性，探索更多可能
🎯
Agent 最佳实践：工具调用、结构化输出用 temperature=0 + JSON mode；用户对话用 temperature=0.7；后台批处理分析用 temperature=0.2, top_p=0.9。永远不要用高 temperature 做需要精确格式的输出。

上下文窗口与位置编码

上下文窗口（Context Window）决定了模型一次能「看到」多少 token。这是 Agent 系统设计中最重要的约束之一。

常见上下文窗口大小

模型上下文窗口约等于
GPT-3.54K / 16K~3K / ~12K 英文词
GPT-4o128K~96K 英文词 / ~200 页文档
Claude 3.5200K~150K 英文词
Gemini 1.5 Pro1M ~ 2M~750K 英文词 / 整本书
LLaMA 3 8B8K (原生) / 128K (扩展)取决于 RoPE 扩展

超出上下文会发生什么？

  • 硬截断：API 直接拒绝或截掉超出部分（最常见）
  • 静默截断：截掉开头或结尾，模型不知道丢失了信息 → 回答质量骤降
  • Lost in the Middle：即使没截断，模型对上下文中间部分的召回率显著低于首尾

为什么更长上下文 = 更高成本？

# Self-Attention 计算复杂度
Time:  O(n² · d)    # n = 序列长度, d = 隐藏维度
Space: O(n²)         # Attention 矩阵存储

# 上下文从 4K → 128K（32倍）
# 计算量增长 32² = 1024 倍！

# 这就是为什么长上下文 API 按 token 定价且价格更高

RoPE（Rotary Position Embedding）基础

现代 LLM（LLaMA、GPT-NeoX、Qwen）普遍使用 RoPE 替代原始正弦位置编码：

  • 通过旋转矩阵将位置信息编码到 Q/K 中
  • Attention score 自然包含相对位置信息
  • 支持外推：训练 4K 的模型可通过插值扩展到 32K/128K
  • 长距离衰减：距离越远，Attention 权重自然降低
# RoPE 直觉：把 Q/K 向量在复平面上旋转 θ·position 角度
# 两个位置的相对角度 = 相对距离的函数
# → Attention(Q_m, K_n) 只依赖 (m - n)，即相对位置

上下文压缩策略

检索增强 (RAG)

不塞全部文档，只检索相关片段注入 Prompt。Agent 开发最常用方案。

摘要压缩

用 LLM 对历史对话/长文档做摘要，保留关键信息。适合多轮对话 Agent。

滑动窗口

只保留最近 N 轮对话，丢弃更早历史。简单但可能丢失重要上下文。

结构化提取

从长文本中提取结构化字段（JSON），只传必要字段给模型。

🤖 Agent 开发提示：设计 Agent 时永远假设上下文有限。把 System Prompt + Tool Schema + 历史对话 + RAG 检索结果的总 token 数控制在窗口的 70% 以内，留余量给模型输出。

模型架构对比

不同架构适合不同任务。理解 GPT vs BERT vs T5 的设计差异，帮助你选择合适的模型和微调策略。

三大架构范式

架构结构Attention代表模型擅长
GPT Decoder-only仅 DecoderCausal (单向)GPT-4, LLaMA, Claude文本生成、对话、代码
BERT Encoder-only仅 Encoder双向BERT, RoBERTa分类、NER、语义匹配
T5 Encoder-DecoderEncoder + Decoder双向 + CausalT5, BART, FLAN-T5翻译、摘要、QA

为什么 Decoder-only 在生成任务中胜出？

  1. 统一框架：预训练（next token prediction）和下游任务（生成）形式一致，无需 task-specific head
  2. Scaling Law：纯 Decoder 架构在大规模数据+参数下展现更强的涌现能力
  3. In-Context Learning：Decoder-only 天然支持 few-shot prompting，无需微调
  4. 工程简单：推理只需维护 KV Cache，一条生成路径

Mixture of Experts (MoE)

MoE 不增加推理计算量的情况下扩大模型容量：每层有 N 个「专家」FFN，但每个 token 只激活 Top-K 个。

# MoE 层工作流程
input → Router(gate) → 选择 Top-2 专家
                     → Expert_3(input) × w₃
                     → Expert_7(input) × w₇
                     → 加权合并 → output

# 示例：Mixtral 8×7B
# 总参数 47B，但每个 token 只激活 2 个专家 ≈ 13B 计算量
# → 大模型容量 + 小模型推理速度
模型总参数激活参数专家数
Mixtral 8×7B47B~13B8, Top-2
DeepSeek-V2236B~21B160+, Top-6
Switch Transformer1.6T~390B2048, Top-1
💡
Agent 选型建议：简单路由/分类用 7B；工具调用 Agent 至少 13B；复杂多步推理用 70B 或 GPT-4 级 API。MoE 模型（Mixtral）是性价比之选——47B 容量但 13B 推理成本。

训练流程概览

现代 LLM 的训练是一个三阶段流水线。作为 Agent 工程师，你几乎从不需要从头训练，但需要理解每个阶段做了什么，以便做出正确的技术选型。

三阶段训练流水线

# Stage 1: Pre-training（预训练）
# 数据：互联网文本（TB 级）
# 目标：Next Token Prediction
# 产出：Base Model（会续写，但不会对话）
        ↓
# Stage 2: SFT（Supervised Fine-Tuning，监督微调）
# 数据：人工标注的 instruction-response 对
# 目标：学会遵循指令、对话格式
# 产出：Chat Model（能对话，但可能不安全/不准确）
        ↓
# Stage 3: RLHF / DPO（对齐）
# 数据：人类偏好排序 / 正例-负例对
# 目标：输出更有帮助、更安全、更诚实
# 产出：Aligned Model（ChatGPT、Claude 就是这个）

每个阶段教会模型什么？

Pre-training

  • 语言规律、世界知识
  • 代码语法、数学模式
  • 推理链的基础能力

SFT

  • 理解用户意图
  • 遵循指令格式
  • 生成结构化输出

RLHF / DPO

  • 拒绝有害请求
  • 承认不确定性
  • 偏好简洁/详细的平衡

RLHF vs DPO

方法流程优缺点
RLHF训练 Reward Model → 用 PPO 强化学习优化效果好但复杂：需 Reward Model、PPO 不稳定、训练成本高
DPO直接用偏好对 (chosen, rejected) 优化策略简单稳定：无需 Reward Model，效果接近 RLHF

技术选型决策树

你的需求是什么？
│
├─ 通用问答 / 对话 → Prompting（零成本，最常用）
│   └─ 需要最新/私有知识 → + RAG
│
├─ 特定领域术语/风格 → Fine-tuning（SFT/LoRA）
│   └─ 例：医疗术语、公司代码风格、特定 JSON 格式
│
├─ 需要实时外部数据 → RAG（检索 + Prompt）
│   └─ 例：告警分析查日志、客服查知识库
│
└─ 需要特定行为模式 → Fine-tuning + RLHF/DPO
    └─ 例：严格遵循 SOP、特定输出格式

为什么通常不需要从头训练？

  • Pre-training 需要 $1M~$100M 算力成本（GPT-4 级别）
  • 需要 TB 级高质量清洗数据
  • 需要大规模 GPU 集群和分布式训练工程能力
  • 开源 Base Model（LLaMA、Qwen）+ LoRA 微调即可满足 95% 的 Agent 需求
🤖 Agent 开发提示：90% 的 Agent 场景用 Prompting + RAG 就够了。只有当你需要模型稳定输出特定格式（如告警分析 SOP）、或使用大量领域术语时，才考虑 LoRA 微调。永远优先考虑 Prompt 工程。

Embedding 与向量空间

Embedding 是 LLM 世界中的「通用语言」——将文本映射到高维向量空间，使语义相似的文本距离相近。RAG、语义搜索、聚类都依赖 Embedding。

什么是 Embedding？

Embedding 是一个稠密浮点向量，编码了文本的语义信息：

# 文本 → 向量
"Redis 连接超时"  → [0.12, -0.34, 0.56, ..., 0.08]  # 1536 维
"Redis connection timeout" → [0.11, -0.33, 0.55, ..., 0.09]  # 非常接近！
"今天天气真好"    → [-0.45, 0.78, -0.12, ..., 0.33]  # 距离很远

Word2Vec 直觉

Embedding 概念的鼻祖。核心思想：上下文相似的词，向量应该相近。

# 经典例子：向量运算
vec("King") - vec("Man") + vec("Woman") ≈ vec("Queen")

# 训练方式：
# CBOW: 用上下文预测中心词
# Skip-gram: 用中心词预测上下文

Word2Vec 是词级别 embedding。现代 LLM 使用上下文相关的 embedding——同一个词在不同句子中向量不同（因为 Self-Attention）。

Sentence Embedding

将整个句子/段落映射为一个固定长度向量，用于语义搜索和 RAG 检索：

from openai import OpenAI

client = OpenAI()
response = client.embeddings.create(
    model="text-embedding-3-small",
    input="Redis 连接池耗尽导致服务不可用"
)
vector = response.data[0].embedding  # 1536 维浮点列表
print(f"维度: {len(vector)}")

为什么 Cosine Similarity 有效？

cosine_sim(A, B) = (A · B) / (||A|| × ||B||)

# 值域 [-1, 1]：
# 1.0  = 完全相同方向（语义相同）
# 0.0  = 正交（无关）
# -1.0 = 完全相反

# 为什么不用欧氏距离？
# Embedding 向量的绝对长度不携带语义信息
# Cosine 只关注方向（语义），忽略长度（文本长短）

Token 预算控制策略

输入端控制

  • 精简 System Prompt，去掉冗余示例
  • RAG 检索 top_k 从 10 降到 3~5
  • 对话历史只保留最近 N 轮
  • 长文档预摘要再注入

输出端控制

  • 设置 max_tokens 上限
  • Prompt 中要求「简洁回答」
  • 结构化输出比自由文本更短
  • 流式输出 + 早停检测

Model Routing（模型路由）

不是所有请求都需要最强模型。用小模型做路由/简单任务，大模型做复杂推理：

# 路由策略示例
def route_request(query: str) -> str:
    complexity = classifier.predict(query)  # 用小模型/规则分类
    if complexity == "simple":
        return call_llm("gpt-4o-mini", query)   # $0.001/次
    elif complexity == "medium":
        return call_llm("gpt-4o", query)       # $0.02/次
    else:
        return call_llm("gpt-4o", query, think=True)  # 复杂推理

# 典型路由：
# FAQ/分类/格式化 → mini (80% 流量)
# 分析/推理/代码 → 4o (15% 流量)
# 多步 Agent 编排 → 4o + 多次调用 (5% 流量)
💰
成本优化公式：总成本 = 请求数 × (Input tokens × Input 单价 + Output tokens × Output 单价)。优化优先级：① 减少请求次数（缓存/路由）→ ② 减少 Input tokens（压缩/RAG 精选）→ ③ 减少 Output tokens（max_tokens/结构化）→ ④ 降低模型单价（路由到 mini）。

面试高频题

以下 8 道是 AI Agent 工程师面试中最常被问到的 LLM 基础题。点击展开查看参考答案。

Transformer 为什么比 RNN 好？

三个核心优势：

  1. 并行计算：RNN 必须按时间步串行计算 ht = f(ht-1, xt)，Transformer 所有位置同时计算 Attention，训练速度提升 10~100 倍
  2. 长距离依赖：RNN 中相距 100 步的两个 token 需经过 100 次隐状态传递，梯度消失/信息衰减严重。Transformer 任意两位置直接 Attention，路径长度 O(1)
  3. 可扩展性：Transformer 完美适配 GPU 并行 + Scaling Law，参数从 100M 扩展到 1T+ 仍有效。RNN 在大规模下无明显收益
Attention 的计算复杂度是多少？ 
Time:  O(n² · d)
Space: O(n²)

# n = 序列长度, d = 隐藏维度
# QK^T 矩阵: n × n
# 每个 head 都要算一次
# Multi-Head: O(h · n² · d/h) = O(n² · d)

# 优化方向：
# Flash Attention: O(n²) 时间但 O(n) 显存（分块计算）
# Sparse Attention: O(n·√n) 只算部分位置
# Linear Attention: O(n·d²) 用核函数近似
Temperature=0 和 Temperature=1 的区别？
Temperature行为适用场景
T = 0贪婪解码，永远选概率最高的 token。输出完全确定（相同输入 → 相同输出）代码生成、工具调用、数据提取、需要可复现结果
T = 1使用模型原始概率分布采样，保留模型的「自然」随机性通用对话、问答
T > 1分布更平坦，低概率 token 也有机会被选中，输出更随机/创意创意写作、头脑风暴

公式：pi = exp(zi/T) / Σexp(zj/T)。T 越小，最高 logit 对应的概率越接近 1。

什么是 KV Cache？为什么它能加速推理？

KV Cache 是推理优化技术：在自回归生成中，缓存之前所有 token 的 Key 和 Value 向量，避免重复计算。

# 无 KV Cache：生成第 100 个 token 时，重新计算 1~99 的所有 K/V
# 有 KV Cache：只计算第 100 个 token 的 K/V，与缓存的 1~99 拼接

# 计算量对比（生成 N 个 token）：
# 无 Cache: O(N²) — 每步重新算全部
# 有 Cache: O(N)   — 每步只算 1 个新 token

# 代价：显存占用 O(N · d · layers · 2)
# 长上下文 + 大模型 → KV Cache 可能占数 GB 显存

Agent 开发影响：多轮对话时 KV Cache 可复用 System Prompt 部分（Prompt Caching 的基础）。

现代趋势：Decoder-only（GPT 路线）主导生成任务；Encoder 组件被 Embedding 模型（BGE、GTE）继承用于检索。

什么是 Hallucination？如何缓解？

Hallucination（幻觉）：模型生成看似合理但实际错误的内容——编造事实、引用不存在的论文、虚构数据。

根本原因：LLM 是概率生成模型，训练目标是「生成流畅文本」而非「生成真实文本」。

缓解策略：

  1. RAG：提供真实文档作为 grounding，减少凭空编造
  2. 降低 Temperature：减少随机性，更忠实于输入
  3. Prompt 约束：「仅根据提供的文档回答，不知道就说不知道」
  4. 输出验证：用代码/API 验证模型输出的数据（如 SQL 查询结果）
  5. Self-Consistency：多次生成取一致答案
  6. Citation 要求：要求模型标注信息来源
RAG vs Fine-tuning 如何选择？
维度RAGFine-tuning
知识更新实时（更新文档即可）需重新训练
成本低（Embedding + 检索）中~高（GPU 训练）
可解释性高（可展示检索来源）低（知识在权重里）
适合知识库 QA、文档分析、私有数据特定风格/格式、领域术语、行为模式
局限检索质量决定上限数据量不足时效果差

决策法则：需要最新/私有知识 → RAG；需要特定输出风格/格式 → Fine-tuning；两者可以组合使用（Fine-tune 模型 + RAG 注入知识）。

什么是 MoE？为什么它能降低推理成本？

Mixture of Experts (MoE)：每层包含 N 个独立的 FFN「专家」，Router 为每个 token 选择 Top-K 个专家处理，最终加权合并。

# 传统 Dense 模型：每个 token 激活全部参数
# MoE 模型：每个 token 只激活 K/N 的参数

# Mixtral 8×7B 示例：
# 总参数: 47B（大容量，学更多知识）
# 激活参数: ~13B（小计算量，推理快）
# → 47B 的知识密度 + 13B 的推理速度

降低推理成本的原因：计算量 ∝ 激活参数量（而非总参数量）。MoE 通过稀疏激活，在保持大模型容量的同时，将每次前向传播的计算量控制在较小范围。代价是需要存储全部专家参数（显存需求仍较大）。
