项目概览

Pi Agent（earendil-works/pi）是一个 TypeScript monorepo AI Agent 工具链，MIT 许可，GitHub 61K+ stars。它不是一个「黑盒框架」，而是一组松耦合、可组合的包——你可以只用 pi-ai 做 LLM 抽象，也可以整套跑起交互式编码 Agent CLI。

为什么值得读？

架构清晰

四层分离：AI → Agent → Application → UI。每层职责单一，依赖方向严格向下，pi-ai 零依赖 agent 逻辑。

工程成熟

事件驱动、不可变状态、Provider 抽象、扩展系统——都是生产级 Agent 系统的标配模式，代码量适中、可读性高。

TypeScript 全栈

类型安全贯穿 LLM 消息、工具 Schema、Agent 状态。对熟悉 Node/TS 的开发者友好，也便于对比 Python 生态（LangGraph、AutoGen）。

可扩展

Extensions、Skills、Prompt Templates、Packages、Themes——扩展点设计可直接借鉴到你自己的 Agent 平台。

分层架构解析

Pi 采用四层架构，每层只依赖下层，扩展点明确。理解这层划分，是阅读整个代码库的主线。

四层一览

层级包核心职责扩展点
AI Layerpi-aiProvider 抽象、流式 API、凭证解析、模型注册新增 Provider、自定义 API 实现
Agent Layerpi-agent-coreAgent 循环、工具执行、状态、事件自定义 AgentTool、Hook、消息转换
Application Layerpi-coding-agentCLI、扩展、Skills、会话、内置工具Extension 模块、Skill MD、Prompt Template
UI Layerpi-tui / pi-web-ui终端/Web 渲染、订阅 Agent 事件Theme、自定义组件

为什么分层？

单一职责

pi-ai 只管「怎么调 LLM」，不关心工具或会话树。换模型 Provider 不动 Agent 逻辑。

可测试性

Agent 循环可用 Mock LLM 单测；Provider 可独立测流式解析。层间通过接口契约隔离。

可复用性

第三方可只依赖 pi-agent-core 自建业务 Agent，不必引入整个 CLI。

Bundle 优化

Provider 工厂 + 懒加载 API 实现，按需打包 SDK chunk，避免一把梭 import 所有厂商。

与其他框架对比

Pi Agent

  • 四层包分离，TS 类型优先
  • 事件流 + 不可变 AgentState
  • Steering / Follow-up 消息队列
  • Extension 即 TS 模块 + Hook
vs

LangGraph

  • 图节点 + 边状态机（Python）
  • Checkpoint 与 interrupt 一等公民
  • Tool 绑定在 Node 上
  • 可视化图编排

Pi Agent

  • 线性 Agent Loop + 并行工具
  • Session 树分支（coding-agent）
vs

AutoGen

  • 多 Agent 对话编排
  • 角色分工（Assistant/User/GroupChat）
  • 更偏协作而非单 Agent 工具链
类比 FastAPI：pi-ai ≈ Starlette/HTTP 抽象层；pi-agent-core ≈ 路由 + 依赖注入；pi-coding-agent ≈ 你的业务 App；pi-tui ≈ 前端。分层思路相通。

pi-ai：统一 LLM API 层

@earendil-works/pi-ai 把所有 LLM 厂商藏在统一接口后面。核心概念：Provider（运行时单元）+ Models（Provider 集合）+ Stream（流式事件）。

Provider 模式

// Provider = 模型目录 + 鉴权 + API 实现
import { createModels } from "@earendil-works/pi-ai";
import { anthropicProvider } from "@earendil-works/pi-ai/providers/anthropic";

const models = createModels({
  providers: [anthropicProvider()],
});

// 流式调用——与具体厂商无关
const stream = models.stream({
  model: "claude-sonnet-4-20250514",
  messages: [{ role: "user", content: "Hello" }],
  tools: [...],
});

内部 API 实现共享

API 实现使用的 Provider
anthropic-messagesAnthropic 原生
openai-responsesOpenAI 原生
openai-completionsxAI、Groq、OpenRouter 等兼容端点
Per-model dispatchGitHub Copilot、OpenCode Zen 等混合 API

多个 Provider 可共享同一 wire protocol，减少重复代码；新 Provider 只需实现 catalog + auth + stream 行为。

流式 API 设计

流式返回 AssistantMessageEventStream，事件类型包括：

  • text_delta — 文本增量
  • thinking_delta — 推理块（支持 o1/Claude thinking）
  • tool_call_start / tool_call_delta — 工具调用增量解析
  • message_end — 完整 assistant 消息

上层 Agent 订阅这些事件，无需关心 Anthropic SSE 还是 OpenAI chunk 格式差异。

如何新增 Provider

  1. 在 packages/ai/src/providers/ 新建 Provider 工厂
  2. 定义模型 catalog（id、context window、tool calling 能力）
  3. 实现 auth 解析（API Key / OAuth）
  4. 绑定 API 实现（复用 openai-completions 或写新 adapter）
  5. 注册到 createModels({ providers: [...] })

pi-agent-core：Agent 运行时

@earendil-works/pi-agent-core 在 pi-ai 之上实现有状态的 Agent 执行引擎：Agent 类封装状态与事件，agentLoop 驱动 LLM ↔ 工具循环。

Agent 类与生命周期

import { Agent } from "@earendil-works/pi-agent-core";

const agent = new Agent({
  models,
  tools: [readTool, bashTool],
  systemPrompt: "You are a coding assistant.",
});

agent.on("message_update", (ev) => { /* UI 更新 */ });
await agent.prompt("Fix the bug in auth.ts");

Agent Loop 流程

用户输入 (prompt)
    │
    ▼
┌───────────────────────────────────────┐
│  turn_start                           │
│  convertToLlm() 过滤/转换消息          │
│  LLM stream → message_update 事件      │
│  解析 tool_calls                       │
└───────────────┬───────────────────────┘
                │
        有 tool_calls?
         /        \
       否          是
        │           ▼
        │    tool_execution_start
        │    并行/串行执行 AgentTool
        │    tool_execution_end
        │    追加 toolResult 到 state
        │           │
        └─────┬─────┘
              ▼
         turn_end
              │
    shouldStop / steering / followUp?
              │
              └──► 下一轮 turn 或 agent_end

事件驱动架构

Agent 不直接操作 UI，而是发射事件。订阅者（TUI、Web、日志）各自响应。这是 Observer 模式的典型应用。

事件触发时机
agent_start / agent_end整次请求开始/结束
turn_start / turn_end单轮 LLM+工具周期
message_updateLLM 文本/thinking 增量
tool_execution_start/end工具执行前后

状态管理

AgentState 包含不可变的 messages 数组。每次更新产生新 state 引用（而非原地 mutate），便于：

  • 时间旅行 / Session 分支
  • React 式 UI 重渲染
  • 序列化 Checkpoint

消息队列：Steering 与 Follow-up

Steering（转向）

Agent 在多轮工具执行中途注入新用户消息，改变后续行为。每轮 turn 开始检查 getSteeringMessages hook。

Follow-up（跟进）

当前 agent 运行结束后自动处理的排队消息，适合批量任务链。

AgentTool 接口

interface AgentTool {
  name: string;
  description: string;
  parameters: JSONSchema;       // LLM function calling schema
  execute(args, ctx): Promise<ToolResult>;
  execution?: "parallel" | "sequential";
}

Abort 与错误恢复

  • AbortSignal 贯穿 LLM stream 与工具执行
  • beforeToolCall hook 可阻止工具（返回 terminate: true）
  • agentLoopContinue 支持从失败点重试
  • shouldStopAfterTurn 在 turn_end 后优雅退出，不中断进行中的 stream

工具系统设计

工具是 Agent 与外部世界（文件系统、Shell、搜索）的桥梁。Pi 在 pi-coding-agent 提供内置工具，在 pi-agent-core 定义通用 AgentTool 契约。

内置工具一览

工具功能典型场景
read读取文件内容理解代码上下文
write创建/覆写文件生成新文件
edit精确替换文件片段 surgical 修改
bash执行 Shell 命令测试、构建、git
grep代码搜索定位符号、引用

工具接口设计

// 工具三要素：name + description + parameters schema
{
  name: "read",
  description: "Read file contents from the workspace",
  parameters: {
    type: "object",
    properties: {
      path: { type: "string", description: "Relative file path" },
    },
    required: ["path"],
  },
  async execute({ path }, ctx) {
    const content = await fs.readFile(path, "utf-8");
    return { content: [{ type: "text", text: content }] };
  },
}

Agent 如何选择工具？

  1. 所有工具的 name + description + parameters 序列化进 LLM 的 tools 字段
  2. LLM 在 assistant 消息中返回 tool_calls（含 name + arguments JSON）
  3. Agent Loop 校验参数 → 执行对应 execute → 包装为 toolResult 消息
  4. Tool Result 追加到 state，触发下一轮 LLM 调用

与 OpenAI Function Calling / Anthropic Tool Use 标准对齐，Pi 不做「魔法路由」——完全交给模型决策。

工具结果格式化

ToolResult 支持多模态 content 块（text、image 等）。错误时返回 isError: true，LLM 可据此自我纠正——这是 Agent 鲁棒性的关键。

return {
  content: [{ type: "text", text: "File not found: auth.ts" }],
  isError: true,
};

Hook：beforeToolCall / afterToolCall

  • beforeToolCall：审计、权限检查、参数改写；可 block 并设 terminate: true
  • afterToolCall：结果过滤、日志、敏感信息脱敏

创建自定义工具

const weatherTool: AgentTool = {
  name: "get_weather",
  description: "Get current weather for a city",
  parameters: { type: "object", properties: { city: { type: "string" } }, required: ["city"] },
  async execute({ city }) {
    const data = await fetchWeather(city);
    return { content: [{ type: "text", text: JSON.stringify(data) }] };
  },
};

agent.registerTool(weatherTool);
对比 LangGraph：LangGraph 用 @tool 装饰器 + bind_tools；Pi 用显式 AgentTool 对象 + JSON Schema。Pi 更偏「配置即对象」，LangGraph 更偏 Python 装饰器风格。

pi-coding-agent：编码 Agent CLI

@earendil-works/pi-coding-agent 是 Pi 的旗舰应用：交互式终端编码助手，整合 Agent 运行时、内置工具、扩展系统与会话管理。

Extension 系统

Extension 是 TypeScript 模块，通过 lifecycle hooks 注入行为：

// extension 示例结构
export default {
  name: "my-extension",
  onSessionStart(ctx) { ... },
  onBeforeToolCall(tool, args) { ... },
  onMessageComplete(msg) { ... },
};

类似 VS Code Extension 或 FastAPI 中间件——在固定生命周期点插入逻辑，不改核心代码。

Skills（技能）

Markdown 文件（SKILL.md），描述特定任务的 SOP 与约束——与 Cursor Rules / Claude Skills 同构。

  • Agent 根据任务语义选择相关 Skill 注入 system context
  • 团队可版本化管理排查手册、代码规范
  • 位于 .pi/skills/ 或 Extension 包内

Prompt Templates

可复用提示词模板，支持参数化：

# templates/review.md
Review the following {{language}} code for {{focus}}:
{{code}}

CLI 或 Extension 调用 renderTemplate("review", { language: "TS", focus: "security", code: "..." })

Session 管理

分支 (Branching)

Session 是消息树而非线性列表。可从任意节点 fork 新分支，对比不同修复方案。

Compaction（压缩）

上下文窗口满时，LLM 摘要旧消息，保留关键信息——类似「滚动摘要」策略。

树导航

TUI 支持在 Session 树中前进/后退（undo/redo 语义）。

持久化

JSONL Session Repo 落盘，支持恢复中断会话。

事件系统与流式输出

Pi 的实时 UI 体验建立在细粒度事件流上。从 LLM token 到工具 stdout，每一帧都有对应事件，UI 订阅即可渲染。

完整事件流（单次 Turn）

agent_start
  └── turn_start
        ├── llm_start          （内部：开始 stream）
        ├── message_update     ×N  text_delta / thinking_delta
        ├── llm_end            （assistant 消息完整）
        ├── tool_execution_start   ×M（每个 tool call）
        ├── tool_execution_end     ×M
        └── turn_end
  └── agent_end

事件如何驱动 UI

// pi-tui 简化订阅逻辑
agent.on("message_update", ({ delta }) => {
  chatPane.appendText(delta.text);  // 差分渲染，非全量重绘
});

agent.on("tool_execution_start", ({ toolName, args }) => {
  toolPanel.showRunning(toolName, args);
});

agent.on("tool_execution_end", ({ result }) => {
  toolPanel.showResult(result);
});

Observer 模式实现

Agent 侧（Subject）

Agent 继承 EventEmitter 或内部 dispatch 表。Loop 各阶段 emit(event, payload)，不感知订阅者数量。

UI 侧（Observer）

TUI/Web/Logger 各自 on() 注册。多个 Observer 可并行存在——日志与 UI 同时消费同一事件流。

两层流式：LLM Stream + Agent Events

层级流粒度
pi-aiAssistantMessageEventStreamToken / tool_call_delta
pi-agent-coreAgent eventsTurn / Tool 生命周期

Agent Loop 将 pi-ai 的细粒度 delta 转发 为 message_update，并在此基础上包装 turn/tool 级语义事件。

如何订阅事件

const agent = new Agent({ ... });

// 方式 1：回调
agent.on("turn_end", (ev) => console.log("Turn done", ev));

// 方式 2：AsyncIterator（若支持）
for await (const event of agent.events()) {
  if (event.type === "message_update") { ... }
}
💡
设计启示：永远不要让 UI 轮询 Agent 状态。事件流是 Agent 框架与前端解耦的标准答案——你的告警分析平台 stream server（NDJSON）也是同一思路。

状态管理与会话

Agent 的「记忆」= AgentState + 持久化 Session。Pi 用不可变更新 + 树形 Session 支持复杂对话场景。

AgentState 结构

interface AgentState {
  messages: AgentMessage[];   // 完整对话 transcript
  model: string;
  systemPrompt?: string;
  tools: AgentTool[];
  // 扩展字段通过 declaration merging 追加
}

不可变状态更新

// 每次 append 产生新 state，不 mutate 旧对象
const nextState = {
  ...prevState,
  messages: [...prevState.messages, newMessage],
};
agent.setState(nextState);

好处：Session 分支只需复制 messages 前缀 + 新后缀；React/Immer 友好；调试时可 diff 相邻 state。

Conversation History 管理

  • User / Assistant / ToolResult 三种核心消息类型
  • convertToLlm() 在每次 LLM 调用前过滤内部消息、转换格式
  • 自定义消息类型通过 TypeScript declaration merging 扩展，convert 函数负责映射

Context Window 管理（Compaction）

当 messages 总 token 接近模型上限：

  1. 选取早期消息块
  2. 调用 LLM 生成摘要
  3. 用摘要消息替换原块，释放 token 预算
  4. 保留最近 N 轮完整消息以保证连贯性

Compaction 在 AgentSession 层触发，对 Agent Loop 透明。

Session 分支

Session Tree 示例：

    [root: "Fix auth bug"]
           │
     ┌─────┴─────┐
  [分支 A]    [分支 B]
  "用 JWT"    "用 Session"
     │            │
  [A1 完成]    [B1 进行中]

每个节点存完整 messages 快照。切换分支 = 加载对应 state，无需重跑 LLM。

Checkpoint 序列化

  • JsonlSessionRepo：每行一条 operation record，append-only
  • 支持 crash 后 replay 恢复
  • 可导出/导入 Session 用于调试或分享
对比 LangGraph：LangGraph Checkpoint 是图状态的序列化；Pi Session 是对话树的序列化。Pi 更偏「聊天产品」，LangGraph 更偏「工作流引擎」。

可扩展性设计模式

Pi 的可扩展性不是事后补丁，而是架构一等公民。以下模式可直接迁移到任何 Agent 框架设计。

1. Declaration Merging（声明合并）

通过 TypeScript module augmentation 扩展消息类型，无需改核心类型定义：

// 在 extension 中
declare module "@earendil-works/pi-agent-core" {
  interface AgentMessage {
    customField?: string;
  }
}

类似 FastAPI 的 dependency override——扩展不污染核心包。

2. Plugin / Extension 架构

Extension = 独立 npm 包或本地 TS 模块，声明 hooks：

  • onSessionStart / onSessionEnd
  • onBeforeToolCall / onAfterToolCall
  • onMessageComplete
  • 注册额外 tools、commands、keybindings

3. Hook 系统

Agent 核心在关键路径预留 hook 点，Extension 和内置逻辑使用同一机制——开闭原则的典型实现。

4. Packages 系统

Extension 可发布到 npm（@scope/pi-extension-xxx），用户 pi install @scope/pi-extension-xxx 即可启用。类似 VS Code Marketplace。

5. Theme 系统

pi-tui 支持 Theme 包定义颜色、边框、组件样式。终端 UI 也能品牌化——对内部工具平台有参考价值。

练习 1：Trace 完整请求流

目标：从用户输入 "Read README.md" 到 LLM 返回最终文本，列出关键函数调用链。

参考答案 
1. CLI 入口 packages/coding-agent/src/cli.ts
   └── AgentSession.prompt(userInput)

2. AgentSession packages/coding-agent/src/core/agent-session.ts
   └── agent.prompt() / agentLoop()

3. agentLoop packages/agent/src/agent-loop.ts
   ├── emit("agent_start")
   ├── runLoop():
   │   ├── emit("turn_start")
   │   ├── convertToLlm(state.messages)
   │   ├── models.stream({ messages, tools })
   │   │   └── pi-ai Provider → HTTP SSE
   │   ├── on each delta → emit("message_update")
   │   ├── parse tool_calls from assistant message
   │   ├── for each tool:
   │   │   ├── emit("tool_execution_start")
   │   │   ├── tool.execute(args)
   │   │   └── emit("tool_execution_end")
   │   ├── append toolResults to state
   │   └── emit("turn_end")
   └── emit("agent_end")

4. 若无 tool_calls → turn_end 后直接 agent_end
   若有 tool_calls → 新一轮 turn_start（带着 tool results）

练习 2：实现简单自定义工具

目标：实现 echo 工具，接收 message 参数并原样返回；注册到 Agent 并测试。

参考答案 
import { Agent } from "@earendil-works/pi-agent-core";
import type { AgentTool } from "@earendil-works/pi-agent-core";

const echoTool: AgentTool = {
  name: "echo",
  description: "Echo back the given message unchanged",
  parameters: {
    type: "object",
    properties: {
      message: { type: "string", description: "Text to echo" },
    },
    required: ["message"],
  },
  async execute({ message }) {
    return {
      content: [{ type: "text", text: message }],
    };
  },
};

const agent = new Agent({
  models,
  tools: [echoTool],
});

await agent.prompt("Use the echo tool to repeat: hello pi");
// 期望：LLM 调用 echo({ message: "hello pi" })，返回 tool result

练习 3：对比 Pi 与 LangGraph 的 Tool Calling

目标：列表对比两者在工具定义、绑定、执行、结果回传上的异同。

参考答案
维度Pi AgentLangGraph
工具定义AgentTool 对象 + JSON Schema@tool 装饰器 + Pydantic schema
绑定方式传入 Agent({ tools: [...] })llm.bind_tools(tools) 或 ToolNode
执行触发Agent Loop 解析 assistant tool_callsToolNode 或 prebuilt ToolExecutor
并行执行默认 parallel，可 per-tool 设 sequentialToolNode 可配置 parallel
结果格式ToolResult content blocks + isErrorToolMessage content string
Hook/拦截beforeToolCall / afterToolCallMiddleware / custom ToolNode
状态集成messages 数组 append toolResultGraph state reducer 合并 messages
编排模型线性 loop + steering 队列有向图 + conditional edges

相似点：都依赖 LLM native function calling；都需把 tool result 喂回模型；都支持并行工具。

差异点：Pi 更简单直接（单 loop）；LangGraph 适合复杂分支/多 Agent；Pi 用 TS 显式对象，LangGraph 用 Python 装饰器 + 图 DSL。
