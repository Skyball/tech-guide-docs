Redis 是什么

💡
一句话：Redis 就是一个超快的内存字典——数据放在内存里，读写只需微秒，还能持久化到磁盘。

直觉理解：书桌 vs 书架

想象你在写论文：

  • 书桌（内存 / Redis）：手边常用资料，拿取只需 1 秒，但桌面空间有限
  • 书架（磁盘 / MySQL）：能存海量书籍，找一本可能要走上好几步

Redis 的核心思路：把热点数据放在「书桌」上，需要时再同步到「书架」。99% 的读请求走内存，延迟从毫秒级降到微秒级。

典型使用场景

缓存 最常用

热点数据缓存，减轻 DB 压力。TTL 自动过期，配合 Cache-Aside 模式。

Session 存储

Agent 会话上下文、用户登录态。Hash 结构字段级读写，EXPIRE 滑动续期。

分布式锁

SET NX EX 原子加锁，Lua 脚本安全释放。秒杀、定时任务互斥。

限流计数

INCR + EXPIRE 固定窗口，或 ZSet 滑动窗口。API 网关、Agent 调用频率控制。

排行榜

Sorted Set 天然有序，ZREVRANGE 取 Top N。游戏积分、Agent 耗时排名。

消息队列

List（LPUSH/BRPOP）或 Stream（消费组）。轻量任务队列，详见 消息队列指南。

⚠️ Redis 是内存数据库，不是关系型 DB 替代品。数据量超过内存容量时必须规划淘汰策略或 Cluster 分片。
面试题：Redis 适合做什么，不适合做什么？

适合：热点缓存、Session、计数器、排行榜、分布式锁、轻量消息队列、限流、UV 统计、地理位置（GEO）。

不适合：复杂关系查询（JOIN）、大数据量持久存储（>内存）、强一致事务（无 ACID）、大 value 存储（视频/文件应存 OSS）、精确计数要求零误差（HyperLogLog 有误差）。

数据结构全景

💡
一句话：Redis 不是简单的 KV，而是 8 种专用容器——选对结构，一个命令搞定复杂逻辑。

5 种基础结构

String 最基础

底层：SDS（Simple Dynamic String），O(1) 获取长度，二进制安全，预分配减少 realloc。

常用命令

SET key value [EX seconds] [NX]
GET key
INCR / DECR / INCRBY
MSET k1 v1 k2 v2
SETEX key 3600 value
APPEND key suffix

适用场景

  • 简单 KV 缓存
  • 计数器（INCR 原子递增）
  • 分布式 ID（INCR order:id）
  • 限流（INCR + EXPIRE）
# Python 示例
import redis
r = redis.Redis(host='localhost', port=6379, decode_responses=True)
r.set('user:1001:name', 'Alice', ex=3600)
r.incr('page:views')
print(r.get('user:1001:name'))  # Alice

Hash 字段级

底层：小数据用 listpack（<128 字段且 value <64B），大数据用 hashtable。

HSET user:1001 name Alice age 25
HGET user:1001 name
HMGET user:1001 name age
HGETALL user:1001
HINCRBY user:1001 age 1
HDEL user:1001 age
HLEN user:1001

适用场景

  • 对象缓存（用户信息、商品详情）
  • Session 存储（多字段上下文）
  • 字段级更新，避免整对象序列化

List 双端队列

底层：quicklist（双向链表 + listpack 节点），支持 O(1) 头尾插入。

LPUSH queue task1 task2
RPUSH queue task3
LPOP queue          # task2（后进先出栈）
BRPOP queue 30      # 阻塞消费，超时 30 秒
LLEN queue
LRANGE queue 0 -1   # 查看全部
RPOPLPUSH src dst   # 可靠队列：移到 processing

场景：简单消息队列、最新 N 条记录（LPUSH + LTRIM 0 99）、Timeline 时间线。

Set 无序去重

底层：整数集合 intset 或 hashtable。

SADD tags python redis go
SISMEMBER tags python    # 1
SMEMBERS tags
SINTER set1 set2         # 交集
SUNION set1 set2         # 并集
SDIFF set1 set2          # 差集
SCARD tags               # 集合大小

场景：标签系统、共同好友、已处理 ID 去重、抽奖（SRANDMEMBER）。

Sorted Set (ZSet) 有序 + 去重

底层：listpack + skiplist（跳表，O(log N) 查找），score 相同按 member 字典序。

ZADD leaderboard 9850 "player1" 8720 "player2"
ZREVRANGE leaderboard 0 9 WITHSCORES  # Top 10
ZRANK leaderboard "player1"             # 排名（升序）
ZINCRBY leaderboard 100 "player1"       # 加分
ZRANGEBYSCORE delay:queue 0 1694510400  # 延迟队列取到期任务
ZREMRANGEBYRANK leaderboard 0 -11       # 只保留 Top 10

场景：排行榜、延迟队列、范围查询、权重调度。

3 种扩展结构

Stream 日志流

底层：radix tree + listpack。支持消费组和 ACK，类似轻量 Kafka。

XADD events * user_id 1001 action login
XREAD COUNT 10 STREAMS events 0
XGROUP CREATE events mygroup $ MKSTREAM
XREADGROUP GROUP mygroup c1 COUNT 1 STREAMS events >

Bitmap 位图

底层：String 的 bit 操作。极省内存的用户签到、在线状态。

SETBIT sign:202609 11 1    # 第 11 天签到
GETBIT sign:202609 11      # 1
BITCOUNT sign:202609       # 本月签到天数
BITOP AND dest a b         # 位运算

HyperLogLog 基数统计

底层：稀疏编码，12KB 固定内存估算唯一元素数，误差 ~0.81%。

PFADD uv:20260912 user1 user2 user3
PFCOUNT uv:20260912        # 3（UV 估算）
PFMERGE uv:week uv:day1 uv:day2

Go 数据结构操作示例

package main

import (
    "context"
    "fmt"
    "github.com/redis/go-redis/v9"
)

var ctx = context.Background()

func main() {
    rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})

    // String
    rdb.Set(ctx, "counter", 0, 0)
    rdb.Incr(ctx, "counter")

    // Hash
    rdb.HSet(ctx, "user:1001", "name", "Alice", "age", 25)
    name, _ := rdb.HGet(ctx, "user:1001", "name").Result()

    // List
    rdb.LPush(ctx, "queue", "task1", "task2")
    task, _ := rdb.BRPop(ctx, 0, "queue").Result()

    // Set
    rdb.SAdd(ctx, "tags", "go", "redis")
    isMember, _ := rdb.SIsMember(ctx, "tags", "go").Result()

    // ZSet
    rdb.ZAdd(ctx, "rank", redis.Z{Score: 100, Member: "p1"})
    top, _ := rdb.ZRevRangeWithScores(ctx, "rank", 0, 9).Result()

    // Stream
    rdb.XAdd(ctx, &redis.XAddArgs{
        Stream: "events",
        Values: map[string]interface{"action": "login"},
    })

    fmt.Println(name, task, isMember, top)
}
面试题：Redis 为什么这么快？
  1. 纯内存操作：数据在 RAM，无磁盘 IO 瓶颈（持久化异步）
  2. 单线程模型：无锁竞争、无上下文切换，命令原子执行
  3. IO 多路复用：epoll/kqueue 单线程处理海量连接
  4. 高效数据结构：SDS、跳表、listpack 针对场景优化
  5. 6.0+ 多 IO 线程：网络读写并行，命令执行仍单线程

持久化机制

💡
一句话：持久化就是给「书桌」拍快照或记流水账——断电后还能把数据找回来。

fork + COW 原理图

BGSAVE 触发
    │
    ▼
fork() ──► 子进程（写 RDB）     父进程（继续服务客户端）
    │              │                      │
    │         共享内存页               新写入触发 COW
    │         （只读共享）             复制被修改的页
    │              │                      │
    │         逐页写入 .rdb           内存占用可能翻倍
    │              │
    ▼              ▼
  完成写入      父进程不受影响（微秒级 fork）

⚠️ 大实例（>10GB）fork 可能耗时数百 ms，期间延迟抖动。
   建议：控制 maxmemory、避免 bigkey、升级内核（THP 关闭）。

RDB 快照

原理：fork 子进程，利用 Copy-on-Write（COW）将内存数据写入 .rdb 文件。父进程继续服务，子进程写磁盘。

# redis.conf RDB 配置
save 900 1      # 900 秒内至少 1 次写 → 触发快照
save 300 10     # 300 秒内至少 10 次写
save 60 10000   # 60 秒内至少 10000 次写
dbfilename dump.rdb
rdbcompression yes
stop-writes-on-bgsave-error yes

# 手动触发
BGSAVE          # 后台快照（推荐）
SAVE            # 阻塞快照（生产慎用）

优点

  • 文件紧凑，适合备份和灾难恢复
  • 恢复速度快（直接加载二进制）
  • 对性能影响小（子进程 COW）

缺点

  • 两次快照间数据可能丢失
  • fork 时内存翻倍风险（大实例）
  • 数据变化频繁时 BGSAVE 开销大

AOF 日志

原理：每条写命令追加到 appendonly.aof 文件。重启时重放命令恢复数据。

# redis.conf AOF 配置
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec    # 同步策略
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
aof-use-rdb-preamble yes  # 混合持久化（4.0+）
appendfsync行为数据安全性能
always每条命令 fsync最安全，不丢最慢
everysec每秒 fsync 一次最多丢 1 秒推荐
noOS 决定何时刷盘可能丢较多最快

AOF Rewrite：AOF 文件膨胀时，fork 子进程根据当前内存状态生成最小命令集，替换旧文件。BGREWRITEAOF 手动触发。

混合持久化（Redis 4.0+）

AOF rewrite 时，前半段用 RDB 二进制格式写入（快速加载），后半段追加 rewrite 期间的增量 AOF 命令。兼顾恢复速度和数据完整性。

aof-use-rdb-preamble yes   # 默认开启

# 文件结构示意
# [RDB 格式全量数据] + [增量 AOF 命令]

数据恢复流程

Redis 启动
    │
    ▼
存在 AOF 文件？
    ├── 是 → AOF 文件开头是 RDB 魔数？
    │         ├── 是（混合模式）→ 先加载 RDB 部分 → 再重放 AOF 增量
    │         └── 否（纯 AOF）→ 重放全部 AOF 命令
    └── 否 → 存在 RDB 文件？
              ├── 是 → 加载 RDB 快照
              └── 否 → 空实例启动

选 RDB

  • 纯缓存，可重建
  • 需要快速冷启动
  • 定期备份到 OSS
  • 主从复制全量同步源
vs

选 AOF

  • Session / 队列不可丢
  • everysec 最多丢 1 秒可接受
  • 需要命令级审计
  • 金融级数据（配合 always）
生产推荐：RDB + AOF 混合持久化，everysec 策略。缓存场景可只开 RDB 或关闭持久化（纯内存）。
面试题：RDB 和 AOF 的区别？什么时候用哪个？
维度RDBAOF
原理定时内存快照写命令日志追加
文件大小紧凑较大（rewrite 压缩）
恢复速度快慢（重放命令）
数据丢失可能丢最后一次快照后数据everysec 最多丢 1 秒
性能影响fork 时内存压力always 模式 IO 压力大

选择：可重建的缓存 → RDB 或不开持久化；不可丢数据 → AOF everysec + 混合持久化；两者都开时 AOF 优先加载。

内存管理与淘汰策略

💡
一句话：书桌满了就得扔东西——Redis 用 8 种策略决定扔哪些 key。

Redis 内存组成

used_memory（INFO memory 总占用）
├── 数据内存（key + value + 数据结构开销）
│   ├── 每个 key ~50-100B 元数据（dictEntry、redisObject）
│   └── value 实际存储（SDS、listpack、skiplist 等）
├── 缓冲内存（client 输出缓冲、AOF rewrite 缓冲、主从复制 backlog）
└── 碎片（mem_fragmentation_ratio = used_memory_rss / used_memory）

碎片率 > 1.5 时考虑重启或 MEMORY PURGE（jemalloc 支持）。

8 种 maxmemory-policy

maxmemory 2gb
maxmemory-policy allkeys-lru
策略行为适用场景
noeviction内存满时写命令报错，读正常不可丢数据，必须监控告警
allkeys-lru所有 key 中淘汰最近最少使用纯缓存（推荐）
volatile-lru仅淘汰设置了 TTL 的 key 中 LRU混合：部分持久 key + 缓存
allkeys-lfu所有 key 中淘汰访问频率最低热点明确、访问模式稳定
volatile-lfu仅 TTL key 中 LFU 淘汰带 TTL 的热点缓存
allkeys-random随机淘汰任意 key访问均匀、无热点
volatile-random随机淘汰 TTL key较少使用
volatile-ttl优先淘汰 TTL 最短的 key希望尽快释放即将过期 key

LRU vs LFU 原理

LRU（Least Recently Used）

淘汰最久没被访问的 key。Redis 用 24bit 存储，高 16bit 是过期时间，低 8bit 是 LRU 时钟（精度有限，近似 LRU）。

访问 key → 更新 LRU 时钟
内存满 → 采样 5 个 key → 淘汰时钟最小的
VS

LFU（Least Frequently Used）

淘汰访问次数最少的 key。Redis 4.0+ 引入，16bit：高 8bit 衰减计数 + 低 8bit 对数计数。

访问 key → 计数 +1（对数增长）
定期衰减 → 旧热点自然降权
内存满 → 采样淘汰计数最低的

LFU 适合热点长期稳定的场景（如商品详情）；LRU 适合访问模式变化快的通用缓存。

内存优化技巧

编码优化

  • listpack 阈值：小 Hash/List/ZSet 自动紧凑编码
  • Hash 存对象：比多个 String key 省内存
  • 控制 key 长度：短 key 减少元数据开销
  • Shared Integer：0-9999 整数共享对象
hash-max-listpack-entries 128
hash-max-listpack-value 64
list-max-listpack-size -2

过期策略

  • 惰性删除：访问时发现过期才删除
  • 定期删除：每秒采样 20 个 key 检查过期
  • TTL 随机偏移：避免大量 key 同时过期雪崩
# 过期时间加随机偏移
EXPIRE key 3600
# 应用层：3600 + random(0, 300)
面试题：Redis 内存满了会怎样？如何选择淘汰策略？

达到 maxmemory 后：

  • noeviction：写命令返回 OOM 错误，读/删正常
  • 其他策略：触发淘汰，写命令正常

选择建议：纯缓存 → allkeys-lru 或 allkeys-lfu；混合存储 → volatile-lru + 重要 key 不设 TTL；数据不可丢 → noeviction + 监控 + Cluster 扩容。

高可用架构

💡
一句话：一台 Redis 挂了整个系统就瘫——主从复制保数据，Sentinel 自动换主，Cluster 水平扩展。

主从复制

                    ┌─────────────┐
                    │   Master    │
                    │  (读写)      │
                    └──────┬──────┘
                           │ 异步复制
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ Replica1 │ │ Replica2 │ │ Replica3 │
        │  (只读)   │ │  (只读)   │ │  (只读)   │
        └──────────┘ └──────────┘ └──────────┘

全量同步流程：
Master ──PSYNC?──► Replica
Master ──+FULLRESYNC runid offset──► Replica
Master ──BGSAVE RDB 文件──► Replica （阻塞期间命令进 replication buffer）
Master ──增量命令 stream──► Replica
Replica ──ACK offset──► Master

全量同步：从节点首次连接或 offset 差距过大 → Master BGSAVE 生成 RDB → 发送 RDB + 缓冲区增量命令。

增量同步（PSYNC 2.0）：断线重连后，若 replication backlog 仍包含缺失数据 → 只传增量，无需全量。

# 从节点配置
replicaof 192.168.1.100 6379
replica-read-only yes

# 复制流程
# 1. 从节点发送 PSYNC runid offset
# 2. Master 判断：全量 or 增量
# 3. 全量：RDB 文件 + 缓冲命令
# 4. 增量：backlog 中 offset 之后的命令
主从复制是异步的，Master 宕机可能丢最后几秒写入。Sentinel/Cluster 做自动 failover。

Sentinel 故障转移流程

  Sentinel1 ──monitor──► Master
  Sentinel2 ──monitor──► Master     Master 宕机
  Sentinel3 ──monitor──► Master         │
                                        ▼
                              SDOWN（单个 Sentinel 判定）
                                        │
                                        ▼
                              ODOWN（quorum 个 Sentinel 确认）
                                        │
                                        ▼
                              Raft 选举 Leader Sentinel
                                        │
                                        ▼
                              选最优 Replica → SLAVEOF NO ONE
                                        │
                                        ▼
                              其他 Replica → SLAVEOF 新 Master
                                        │
                                        ▼
                              通知客户端新 Master 地址

Sentinel 哨兵

Sentinel 是独立进程，监控 Master 和 Slave，自动故障转移。至少 3 个 Sentinel 节点（奇数，防脑裂）。

# sentinel.conf
sentinel monitor mymaster 192.168.1.100 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
  1. 主观下线（SDOWN）：单个 Sentinel 认为 Master 无响应（超时 down-after-milliseconds）
  2. 客观下线（ODOWN）：quorum 个 Sentinel 都认为下线
  3. 领导者选举：Raft 算法选出一个 Sentinel 执行 failover
  4. 故障转移：选最优 Slave 提升为新 Master → 其他 Slave 指向新 Master → 旧 Master 恢复后变为 Slave

Cluster 槽位分配示意

面试题：Redis Cluster 如何保证高可用？MOVED 和 ASK 的区别？

高可用：每个 Master 至少 1 个 Replica；Master 宕机时 Cluster 自动将 Replica 提升为新 Master；Gossip 协议传播节点状态；fail 检测类似 Sentinel 的 Gossip + PFAIL/FAIL。

分布式锁与事务

💡
一句话：分布式锁像厕所门锁——一个人进去锁门，出来才开门；Lua 脚本保证「检查 + 操作」原子性。

SETNX + EX 基本分布式锁

# 加锁：SET key value NX EX 30
# NX = 不存在才设置，EX = 30 秒自动过期
SET lock:order:1001 uuid-abc123 NX EX 30

# 释放锁：必须验证 value 是自己的（防误删别人的锁）
# 用 Lua 脚本保证 GET + DEL 原子性
// Go 示例 — go-redis/v9
package main

import (
    "context"
    "fmt"
    "time"

    "github.com/google/uuid"
    "github.com/redis/go-redis/v9"
)

var ctx = context.Background()

func acquireLock(rdb *redis.Client, key string, ttl time.Duration) (string, bool) {
    token := uuid.NewString()
    ok, err := rdb.SetNX(ctx, key, token, ttl).Result()
    if err != nil || !ok {
        return "", false
    }
    return token, true
}

var releaseScript = redis.NewScript(`
    if redis.call("GET", KEYS[1]) == ARGV[1] then
        return redis.call("DEL", KEYS[1])
    else
        return 0
    end
`)

func releaseLock(rdb *redis.Client, key, token string) error {
    _, err := releaseScript.Run(ctx, rdb, []string{key}, token).Result()
    return err
}

func main() {
    rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
    key := "lock:order:1001"

    token, ok := acquireLock(rdb, key, 30*time.Second)
    if !ok {
        fmt.Println("failed to acquire lock")
        return
    }
    defer releaseLock(rdb, key, token)

    fmt.Println("critical section...")
}

Redlock 算法

在 N 个独立 Redis 节点（通常 5 个）上同时加锁，超过 N/2+1 成功才算获得锁。解决单节点 Sentinel failover 时锁丢失问题。

# 步骤
1. 获取当前时间 T1
2. 依次向 N 个节点 SET key value NX PX ttl
3. 获取当前时间 T2
4. 成功数 >= N/2+1 且 (T2-T1) < 锁有效时间 → 加锁成功
5. 实际锁 TTL = 初始 TTL - (T2-T1)
6. 释放：向所有节点发送 Lua DEL
Redlock 有争议（Martin Kleppmann vs Antirez 论战）。生产环境多数场景单节点 SET NX EX + 合理 TTL + 看门狗续期已足够。

Lua 脚本与 MULTI/EXEC

Lua 脚本

  • 原子执行，中间无其他命令插入
  • 可含条件逻辑（if/else）
  • 减少网络往返
  • 脚本缓存（EVALSHA）
EVAL "return redis.call('GET',KEYS[1])" 1 mykey
VS

MULTI/EXEC 事务

  • 命令排队，EXEC 时批量执行
  • 无回滚：某命令失败不影响其他
  • 不支持条件逻辑
  • 配合 WATCH 实现乐观锁
WATCH balance
MULTI
DECRBY balance 100
INCRBY other 100
EXEC  # 期间 balance 被改则 EXEC 失败

Python 分布式锁示例

import uuid
import redis

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

RELEASE_LUA = """
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
"""
release_script = r.register_script(RELEASE_LUA)

def acquire_lock(key: str, ttl: int = 30) -> str | None:
    token = uuid.uuid4().hex
    if r.set(key, token, nx=True, ex=ttl):
        return token
    return None

def release_lock(key: str, token: str) -> bool:
    return release_script(keys=[key], args=[token]) == 1

# 使用
lock_key = "lock:seckill:sku1001"
token = acquire_lock(lock_key)
if token:
    try:
        print("processing order...")
    finally:
        release_lock(lock_key, token)
面试题：Redis 分布式锁有哪些坑？如何解决？
  1. 锁过期业务未完成：看门狗线程定期 EXPIRE 续期（Redisson 已实现）
  2. 误删他人锁：value 存 UUID，Lua 脚本验证后删除
  3. Master 宕机锁丢失：Sentinel failover 时考虑 Redlock 或 fencing token
  4. 不可重入：Hash 结构记录线程 ID + 重入计数
  5. 主从异步复制：锁写入 Master 未同步到 Slave 时 Master 宕机 → Redlock 或多节点

互斥锁防击穿

import asyncio
import json

async def get_hot_product(r, product_id: int):
    key = f"product:{product_id}"
    lock_key = f"lock:product:{product_id}"

    cached = await r.get(key)
    if cached:
        return json.loads(cached)

    token = await r.set(lock_key, "1", nx=True, ex=10)
    if token:
        try:
            product = await db.get_product(product_id)
            await r.setex(key, 3600, json.dumps(product))
            return product
        finally:
            await r.delete(lock_key)
    else:
        await asyncio.sleep(0.05)
        cached = await r.get(key)
        return json.loads(cached) if cached else None

三大经典问题

缓存穿透 查不存在

查询不存在的数据，缓存和 DB 都 miss，恶意请求打穿到 DB。

解法：

  • 布隆过滤器（Bloom Filter）前置拦截
  • 空值缓存（cache null，短 TTL）
  • 参数校验（非法 ID 直接拒绝）

缓存击穿 热点过期

热点 key 过期瞬间，大量并发同时查 DB。

解法：

  • 互斥锁（只有一个线程查 DB 并回填）
  • 逻辑过期（不设 TTL，异步更新）
  • 热点 key 永不过期 + 后台刷新

缓存雪崩 大面积过期

大量 key 同时过期或 Redis 宕机，DB 压力激增。

解法：

  • TTL 加随机偏移
  • 多级缓存（本地 Caffeine + Redis）
  • 熔断降级（Sentinel/Hystrix）
  • Redis 高可用（Sentinel/Cluster）

读写策略

模式读写一致性场景
Cache-Aside先读缓存，miss 读 DB 并回填先更新 DB，再删缓存最终一致最常用，通用场景
Read-Through缓存层代理读，miss 自动加载—最终一致缓存中间件封装
Write-Through—同时写缓存和 DB强一致写少读多
Write-Behind—先写缓存，异步批量写 DB弱一致写密集（计数、日志）

Cache-Aside 代码模板

def get_user(user_id: int) -> dict | None:
    cache_key = f"user:{user_id}"
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)
    if cached == "NULL":  # 空值缓存
        return None

    user = db.query("SELECT * FROM users WHERE id = %s", user_id)
    if user is None:
        r.setex(cache_key, 60, "NULL")  # 短 TTL 防穿透
        return None

    ttl = 3600 + random.randint(0, 300)  # 随机偏移防雪崩
    r.setex(cache_key, ttl, json.dumps(user))
    return user

def update_user(user_id: int, data: dict):
    db.update("users", data, where={"id": user_id})
    r.delete(f"user:{user_id}")  # 先更 DB 再删缓存

缓存一致性

延迟双删

1. 删除缓存
2. 更新数据库
3. sleep(500ms)  # 等待读请求回填旧值
4. 再次删除缓存

简单但 sleep 时间难估，高并发仍可能不一致。

Canal + Binlog 订阅

MySQL Binlog → Canal → MQ → 消费者删缓存

基于 DB 变更事件驱动，一致性好，架构复杂。大厂主流方案。

面试题：先更新 DB 再删缓存，还是先删缓存再更新 DB？

推荐：先更新 DB，再删缓存（Cache-Aside 写策略）。

  • 先删缓存再更新 DB：删缓存后、更新 DB 前，读请求可能回填旧值到缓存
  • 先更新 DB 再删缓存：删缓存前读请求可能回填旧值，但窗口极短（删缓存通常很快）
  • 极端情况（删缓存失败）：延迟双删 或 Canal 订阅 binlog 补偿

func allowRequest(rdb *redis.Client, userID string, limit int, window time.Duration) (bool, error) {
    ctx := context.Background()
    key := fmt.Sprintf("rate:%s", userID)
    now := time.Now().UnixMilli()
    windowStart := now - window.Milliseconds()

    pipe := rdb.Pipeline()
    pipe.ZRemRangeByScore(ctx, key, "0", fmt.Sprintf("%d", windowStart))
    pipe.ZAdd(ctx, key, redis.Z{Score: float64(now), Member: now})
    pipe.ZCard(ctx, key)
    pipe.Expire(ctx, key, window)

    cmds, err := pipe.Exec(ctx)
    if err != nil {
        return false, err
    }
    count := cmds[2].(*redis.IntCmd).Val()
    return count <= int64(limit), nil
}

type RedisLock struct {
    rdb   *redis.Client
    key   string
    token string
    ttl   time.Duration
}

func NewRedisLock(rdb *redis.Client, key string, ttl time.Duration) *RedisLock {
    return &RedisLock{rdb: rdb, key: key, token: uuid.NewString(), ttl: ttl}
}

func (l *RedisLock) Lock(ctx context.Context) (bool, error) {
    return l.rdb.SetNX(ctx, l.key, l.token, l.ttl).Result()
}

func (l *RedisLock) Unlock(ctx context.Context) error {
    _, err := releaseScript.Run(ctx, l.rdb, []string{l.key}, l.token).Result()
    return err
}

// 看门狗续期
func (l *RedisLock) Watchdog(ctx context.Context) {
    ticker := time.NewTicker(l.ttl / 3)
    defer ticker.Stop()
    renewScript := redis.NewScript(`
        if redis.call("GET", KEYS[1]) == ARGV[1] then
            return redis.call("EXPIRE", KEYS[1], ARGV[2])
        end
        return 0
    `)
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            renewScript.Run(ctx, l.rdb, []string{l.key}, l.token, int(l.ttl.Seconds()))
        }
    }
}

def query_cache_key(query: str) -> str:
    h = hashlib.sha256(query.encode()).hexdigest()[:16]

async def cached_rag_query(r, query, embed_fn, search_fn):

删除 bigkey 绝不用 DEL（阻塞单线程），用 UNLINK 异步释放。

热点 key 问题

单个 key QPS 过高导致单节点 CPU 100%。

  • 本地缓存：热点 key 加一层进程内 cache（Caffeine/sync.Map），TTL 1-5 秒
  • key 拆分：读时 random 选一个副本 hotkey:{1..N}，写时全部更新
  • 读写分离：热点读走 Replica
  • Redis 7.0+：Client Side Caching 减少网络往返

面试题：生产环境能不能用 KEYS * 和 MONITOR？

KEYS *：绝对不行。O(N) 遍历所有 key，阻塞单线程，key 多时导致服务停顿数秒甚至分钟。用 SCAN 替代。

MONITOR：仅调试时短暂使用。每条命令都输出，CPU 和网络开销巨大，QPS 高时可能导致 Redis 不可用。生产排查用 SLOWLOG + 客户端日志。

面试题汇总 + 实战练习

以下 10 道综合面试题覆盖本指南全部核心知识点。点击展开查看详细答案。

1. Redis 单线程为什么还能支撑 10 万 QPS？

纯内存操作 + IO 多路复用（epoll）+ 单线程无锁无上下文切换 + 高效数据结构。6.0+ 多 IO 线程并行处理网络读写，命令执行仍单线程保证原子性。瓶颈通常在网络带宽或命令复杂度，而非 CPU。

2. Redis 和 Memcached 的区别？选型依据？

Redis 支持丰富数据结构、持久化、主从/Cluster、Lua 原子操作；Memcached 仅 String KV、纯内存。需要持久化、复杂数据结构、分布式锁、排行榜 → Redis；纯缓存加速、多核利用（Memcached 可 multi-thread）→ Memcached。现代项目几乎默认 Redis。

3. 如何保证 Redis 和 DB 的数据一致性？

Cache-Aside 模式：读 miss 回填，写时先更新 DB 再删缓存。强一致场景：延迟双删、Canal 订阅 binlog 异步删缓存、Write-Through。接受最终一致：TTL 兜底 + 短过期。核心原则：DB 是 source of truth，缓存可重建。

4. Redis 持久化方案如何选择？

纯缓存可不开持久化或仅 RDB；不可丢数据用 AOF everysec + 混合持久化（RDB preamble）。RDB 适合备份和快速恢复；AOF 适合数据安全。两者都开时重启优先加载 AOF。

5. 主从复制原理？全量和增量如何切换？

从节点发送 PSYNC runid offset。runid 匹配且 offset 在 replication backlog 内 → 增量同步（只传缺失命令）；否则全量同步（BGSAVE RDB + 缓冲命令）。backlog 大小默认 1MB，高写入场景需调大。

6. Redis Cluster 的 hash slot 是什么？为什么 16384 个？

16384 个 slot 映射到不同 Master 节点，key 路由 CRC16(key) % 16384。选 16384 因为：心跳包中携带 slot bitmap 约 2KB（16384/8），节点间通信开销合理；支持最多 1000 个 Master 节点，每节点 16-24 个 slot 足够。

7. 分布式锁的看门狗机制是什么？

加锁成功后启动后台线程，定期（TTL/3）检查锁是否仍持有，是则 EXPIRE 续期。防止业务执行时间超过锁 TTL 导致锁自动释放、被其他客户端获取。Redisson 的 Watchdog 默认 30 秒 TTL，每 10 秒续期。

8. 缓存穿透、击穿、雪崩的区别和解决方案？
  • 穿透：查不存在的数据 → 布隆过滤器 + 空值缓存
  • 击穿：热点 key 过期 → 互斥锁 + 逻辑过期
  • 雪崩：大量 key 同时过期 / Redis 宕机 → 随机 TTL + 多级缓存 + 熔断 + HA
9. Redis 内存淘汰策略有哪些？生产怎么选？

8 种：noeviction、allkeys-lru/lfu/random、volatile-lru/lfu/random/ttl。纯缓存 → allkeys-lru 或 allkeys-lfu；混合存储 → volatile-lru；数据不可丢 → noeviction + 监控 + 扩容。LFU 适合热点稳定，LRU 适合访问模式变化。

10. 如何发现和处理 Redis 慢查询/bigkey/热 key？

慢查询：SLOWLOG GET + 避免 KEYS/HGETALL 大 key。bigkey：redis-cli --bigkeys + UNLINK 异步删除 + 拆分。热 key：MONITOR 采样（短暂）、客户端统计、Redis 4.0+ HOTKEYS 命令；解决：本地缓存、key 分片、读写分离。

架构设计实战：秒杀系统的 Redis 缓存层

题目：设计一个秒杀系统的 Redis 缓存层，要求：

  1. 10 万 QPS 读库存，DB 不能被打穿
  2. 防止超卖（库存扣减原子性）
  3. 防止同一用户重复下单
  4. 活动结束后的数据清理
参考答案 
# ===== 数据结构设计 =====

# 1. 库存（String + DECR 原子扣减）
SET seckill:stock:sku1001 1000

# 2. 商品详情缓存（String JSON，逻辑过期）
SET seckill:detail:sku1001 "{...}" 
# 不设 TTL，后台异步刷新

# 3. 用户去重（Set 或 String SETNX）
SET seckill:ordered:sku1001:user123 1 EX 86400 NX

# 4. 限流（ZSet 滑动窗口）
ZADD rate:user123 {timestamp} {timestamp}

# ===== 秒杀流程（Lua 脚本保证原子性）=====
-- seckill.lua：检查去重 + 扣库存 + 标记下单
local stock_key = KEYS[1]       -- seckill:stock:sku1001
local order_key = KEYS[2]       -- seckill:ordered:sku1001:user123
local user_id = ARGV[1]

-- 1. 检查是否已下单
if redis.call('EXISTS', order_key) == 1 then
    return -1  -- 重复下单
end

-- 2. 扣库存
local stock = redis.call('DECR', stock_key)
if stock < 0 then
    redis.call('INCR', stock_key)  -- 回滚
    return 0  -- 库存不足
end

-- 3. 标记已下单
redis.call('SET', order_key, '1', 'EX', 86400)
return 1  -- 成功
# ===== 架构要点 =====
# 1. 前置：CDN 静态页 + Nginx 限流 + 布隆过滤器拦截无效 SKU
# 2. 缓存：商品详情预热到 Redis，逻辑过期 + 后台刷新
# 3. 库存：Redis DECR 原子扣减，Lua 脚本合并去重+扣减
# 4. 异步：Lua 返回成功后发 MQ，异步创建订单写 DB
# 5. 兜底：MQ 消费失败重试 + 定时对账（Redis 库存 vs DB）
# 6. 清理：活动结束后 DEL seckill:* 或设置 TTL
# 7. 热 key：库存 key 分片 seckill:stock:sku1001:{0..9} 或本地缓存
