gRPC 是什么

RPC（Remote Procedure Call）：像调用本地函数一样调用远程服务。客户端发起调用 → 网络传输 → 服务端执行 → 返回结果。gRPC 是 Google 开源的高性能 RPC 框架，基于 HTTP/2 和 Protocol Buffers。

为什么选择 gRPC

HTTP/2 多路复用 性能

单 TCP 连接上并行多个请求，头部压缩（HPACK），消除队头阻塞。微服务间高频调用场景延迟更低。

二进制协议 效率

Protobuf 序列化比 JSON 更小更快（通常 3–10 倍），解析开销低，适合内部服务通信。

代码生成 类型安全

从 .proto 自动生成 Go/Python/Java 客户端和服务端桩代码，编译期类型检查，减少接口不一致。

四种流式模式 实时

支持 Server/Client/Bidirectional Streaming，天然适合 LLM Token 流式输出、日志推送、实时分析。

Protocol Buffers 基础

Protocol Buffers（Protobuf）是 gRPC 的接口定义语言（IDL）和序列化格式。先写 .proto 描述数据结构和服务，再用 protoc 生成各语言代码。

.proto 文件基本结构

// alert.proto
syntax = "proto3";                    // 使用 Proto3（推荐）

package alert.v1;                      // 命名空间，防冲突
option go_package = "alert/v1;alertv1"; // Go 包路径

// 消息类型 —— 类似 struct
message AlertRequest {
  string biz_line = 1;               // 字段编号，不是默认值！
  string alert_id  = 2;
  string payload   = 3;
}

message AlertResponse {
  string analysis_id = 1;
  string summary     = 2;
  AlertStatus status = 3;
}

// 服务定义 —— RPC 方法集合
service AlertAnalysisService {
  rpc Analyze(AlertRequest) returns (AlertResponse);
  rpc AnalyzeStream(AlertRequest) returns (stream AnalysisChunk);
}

复合类型

// 枚举
enum AlertStatus {
  STATUS_UNSPECIFIED = 0;  // 必须有 0 值
  PENDING   = 1;
  RUNNING   = 2;
  COMPLETED = 3;
}

// repeated —— 列表
repeated string tags = 4;

// map —— 字典
map<string, string> metadata = 5;

// oneof —— 互斥字段
oneof source {
  string webhook_url = 6;
  string api_key     = 7;
}

字段编号规则（重要）

  • 1–15：占 1 字节编码，留给高频字段
  • 16–2047：占 2 字节
  • 19000–19999：Protobuf 保留，禁止使用
  • 字段编号一旦发布不可更改，只能废弃（reserved）
  • 删除字段时必须 reserved 编号和名称，防止误复用
message OldMessage {
  reserved 2, 15, 9 to 11;       // 保留编号
  reserved "foo", "bar";          // 保留字段名
  string name = 1;
}

Proto3 vs Proto2

特性Proto2Proto3（推荐）
required 字段支持移除（全部 implicit optional）
默认值可自定义零值（0, "", false）
枚举第一个值无强制要求必须是 0（UNSPECIFIED）
JSON 映射较弱官方 JSON 映射规范
新项目一律使用 syntax = "proto3"。Proto2 仅维护遗留系统。

gRPC 四种通信模式

1. Unary RPC 一问一答

客户端发一个请求，服务端返回一个响应。最常见的模式，等价于普通函数调用。

// proto
rpc GetAlert(GetAlertRequest)
    returns (AlertResponse);

// Go Server
func (s *server) GetAlert(
    ctx context.Context,
    req *pb.GetAlertRequest,
) (*pb.AlertResponse, error) {
    alert, err := s.repo.Find(req.Id)
    if err != nil {
        return nil, status.Error(
            codes.NotFound, "alert not found")
    }
    return toProto(alert), nil
}

// Go Client
resp, err := client.GetAlert(ctx,
    &pb.GetAlertRequest{Id: "alert-123"})

2. Server Streaming 服务端推送

客户端发一个请求，服务端返回多个响应流。适合 LLM Token 流、日志推送、大结果分页。

// proto
rpc AnalyzeStream(AlertRequest)
    returns (stream AnalysisChunk);

// Go Server
func (s *server) AnalyzeStream(
    req *pb.AlertRequest,
    stream pb.AlertAnalysisService_AnalyzeStreamServer,
) error {
    for chunk := range s.agent.Run(req) {
        if err := stream.Send(&pb.AnalysisChunk{
            Token: chunk.Text,
            Done:  chunk.Finished,
        }); err != nil {
            return err
        }
    }
    return nil
}

// Go Client —— 消费流
stream, _ := client.AnalyzeStream(ctx, req)
for {
    chunk, err := stream.Recv()
    if err == io.EOF { break }
    fmt.Print(chunk.Token)
}

3. Client Streaming 客户端上传

客户端发送多个请求，服务端返回一个汇总响应。适合批量上传、聚合写入。

// proto
rpc UploadMetrics(stream MetricPoint)
    returns (UploadSummary);

// Go Server
func (s *server) UploadMetrics(
    stream pb.MetricsService_UploadMetricsServer,
) error {
    count := 0
    for {
        pt, err := stream.Recv()
        if err == io.EOF {
            return stream.SendAndClose(
                &pb.UploadSummary{Count: int32(count)})
        }
        s.store.Save(pt)
        count++
    }
}

4. Bidirectional Streaming 双向流

双方独立发送消息流。适合实时对话、协作编辑、双向数据管道。

// proto
rpc Chat(stream ChatMessage)
    returns (stream ChatMessage);

// Go Server
func (s *server) Chat(
    stream pb.ChatService_ChatServer,
) error {
    for {
        msg, err := stream.Recv()
        if err == io.EOF { return nil }
        reply := s.process(msg)
        if err := stream.Send(reply); err != nil {
            return err
        }
    }
}
🤖
Agent 最佳实践：LLM 分析结果用 Server Streaming（AnalyzeStream）逐 Token 推送，客户端实时渲染。Unary 仅用于短结果或状态查询。本项目的 Stream 服务（:8092 NDJSON）与 gRPC Server Streaming 语义类似。

Go 实现 gRPC 服务

完整流程四步：定义 Proto → 生成代码 → 实现 Server → 编写 Client。以下以告警分析服务为例。

Step 1：定义 Proto

// api/analyze/v1/analyze.proto
syntax = "proto3";
package analyze.v1;
option go_package = "analyze/v1;analyzev1";

service AnalyzeService {
  rpc Analyze(AnalyzeRequest) returns (AnalyzeResponse);
  rpc AnalyzeStream(AnalyzeRequest) returns (stream StreamChunk);
}

message AnalyzeRequest {
  string biz_line = 1;
  string alert_body = 2;
  map<string, string> context = 3;
}

message AnalyzeResponse {
  string result_id = 1;
  string summary = 2;
}

message StreamChunk {
  string content = 1;
  bool is_final = 2;
}

Step 2：生成 Go 代码

protoc --go_out=. --go-grpc_out=. \
  --go_opt=paths=source_relative \
  --go-grpc_opt=paths=source_relative \
  api/analyze/v1/analyze.proto

Step 3：实现 Server

type analyzeServer struct {
    pb.UnimplementedAnalyzeServiceServer // 必须嵌入，保证向前兼容
    svc *analyzeservice.Service
}

func (s *analyzeServer) Analyze(
    ctx context.Context,
    req *pb.AnalyzeRequest,
) (*pb.AnalyzeResponse, error) {
    result, err := s.svc.RunAnalysis(ctx, req.BizLine, req.AlertBody)
    if err != nil {
        return nil, status.Errorf(codes.Internal,
            "analysis failed: %v", err)
    }
    return &pb.AnalyzeResponse{
        ResultId: result.ID,
        Summary:  result.Summary,
    }, nil
}

func main() {
    lis, _ := net.Listen("tcp", ":50051")
    s := grpc.NewServer(
        grpc.UnaryInterceptor(unaryLoggingInterceptor),
    )
    pb.RegisterAnalyzeServiceServer(s, &analyzeServer{svc: svc})
    s.Serve(lis)
}

Step 4：实现 Client

conn, err := grpc.Dial("localhost:50051",
    grpc.WithTransportCredentials(insecure.NewCredentials()),
    grpc.WithBlock(),
)
defer conn.Close()

client := pb.NewAnalyzeServiceClient(conn)
ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
defer cancel()

resp, err := client.Analyze(ctx, &pb.AnalyzeRequest{
    BizLine:   "im",
    AlertBody: alertJSON,

Interceptors（中间件）

func unaryLoggingInterceptor(
    ctx context.Context,
    req interface{},
    info *grpc.UnaryServerInfo,
    handler grpc.UnaryHandler,
) (interface{}, error) {
    start := time.Now()
    resp, err := handler(ctx, req)
    log.Printf("%s took %v err=%v", info.FullMethod, time.Since(start), err)
    return resp, err
}

// 链式注册多个 interceptor
s := grpc.NewServer(
    grpc.ChainUnaryInterceptor(
        loggingInterceptor,
        authInterceptor,
        recoveryInterceptor,
    ),
)
Interceptor 分 Unary 和 Stream 两种，分别对应两种 RPC 类型。Recovery interceptor 防止 panic 导致进程崩溃。

连接管理

  • 长连接复用：一个 *grpc.ClientConn 应全局复用，不要每次 RPC 新建
  • 优雅关闭：conn.Close() 等待进行中的 RPC 完成
  • Keep-Alive：配置 grpc.WithKeepaliveParams 检测死连接
  • 重连：gRPC 客户端内置指数退避重连，Unavailable 时可安全重试

import grpc
from generated.analyze.v1 import analyze_pb2, analyze_pb2_grpc

def analyze_alert(biz_line: str, alert_body: str) -> str:
    # 连接 Go gRPC 服务（长连接应全局复用）
    channel = grpc.insecure_channel("localhost:50051")
    stub = analyze_pb2_grpc.AnalyzeServiceStub(channel)

    request = analyze_pb2.AnalyzeRequest(
        biz_line=biz_line,
        alert_body=alert_body,
        context={"source": "agent"},
    )

    try:
        response = stub.Analyze(request, timeout=30)
        return response.summary
    except grpc.RpcError as e:
        if e.code() == grpc.StatusCode.NOT_FOUND:
            raise ValueError("alert not found") from e
        raise
    finally:
        channel.close()

消费 Server Streaming（LLM 输出）

def stream_analysis(biz_line: str, alert_body: str):
    """逐 chunk 消费 Go 服务的流式分析结果。"""
    channel = grpc.insecure_channel("localhost:50051")
    stub = analyze_pb2_grpc.AnalyzeServiceStub(channel)

    request = analyze_pb2.AnalyzeRequest(
        biz_line=biz_line, alert_body=alert_body
    )

    for chunk in stub.AnalyzeStream(request, timeout=120):
        yield chunk.content
        if chunk.is_final:
            break

# Agent 中使用
full_text = ""
for token in stream_analysis("im", alert_json):
    full_text += token
    print(token, end="", flush=True)

异步客户端（grpc.aio）

import grpc.aio

async def async_analyze(biz_line: str, alert_body: str) -> str:
    async with grpc.aio.insecure_channel("localhost:50051") as channel:
        stub = analyze_pb2_grpc.AnalyzeServiceStub(channel)
        request = analyze_pb2.AnalyzeRequest(
            biz_line=biz_line, alert_body=alert_body
        )
        response = await stub.Analyze(request, timeout=30)
        return response.summary

# 与 asyncio Agent 集成
async def agent_tool_call(state):
    summary = await async_analyze(state["biz_line"], state["alert"])

Deadline / Timeout 传播

超时从调用链上游向下游自动传播，避免级联阻塞。

// 客户端设置 5 秒 deadline

    context.Background(), 5*time.Second)
defer cancel()

// 超时 → codes.DeadlineExceeded

// 服务端检查
if ctx.Err() == context.DeadlineExceeded {
    return nil, status.Error(
        codes.DeadlineExceeded, "timeout")
}

面试题 + 实战练习

gRPC vs REST 的核心权衡是什么？

gRPC 优势：性能（二进制 + HTTP/2 多路复用）、强类型契约（proto 代码生成）、原生流式支持、跨语言一致性。

REST 优势：人类可读（JSON）、浏览器原生支持、生态成熟（Swagger/curl）、学习成本低、防火墙友好（纯 HTTP）。

选型原则：内部微服务 → gRPC；对外公开 API → REST；两者兼顾 → gRPC + gRPC-Gateway。

HTTP/2 多路复用是什么？为什么 gRPC 需要它？

HTTP/1.1 每个请求需要一个 TCP 连接（或串行复用），存在队头阻塞：前一个请求慢会阻塞后续请求。

HTTP/2 在单个 TCP 连接上通过 Stream ID 并行多个请求/响应，且头部 HPACK 压缩减少冗余。gRPC 基于 HTTP/2，微服务间高频 RPC 调用时延迟显著降低，连接开销更小。

Protobuf 向后兼容规则有哪些？
  1. 不要改字段编号：编号是二进制编码的标识符
  2. 不要改字段类型：int32 → string 会导致解析错误
  3. 新增字段用新编号：旧客户端自动忽略未知字段
  4. 删除字段用 reserved：防止编号被误复用
  5. 枚举只增不删：旧客户端收到新枚举值视为未知
  6. 不要改 oneof/repeated 语义

核心原则：只加不改不删（删除必须 reserved）。

gRPC 四种通信模式分别适合什么场景？
模式场景示例
Unary简单请求-响应查询告警详情、创建任务
Server Streaming服务端持续推送LLM Token 流、日志 tail、股票行情
Client Streaming客户端批量上传批量写入指标、文件分块上传
Bidirectional双向实时通信聊天、实时协作、传感器双向管道
gRPC 的错误码和 HTTP 状态码如何对应？

gRPC 使用自己的 Status Code 体系（16 个标准码），通过 gRPC-Gateway 映射到 HTTP 状态码。例如 NotFound → 404、InvalidArgument → 400、DeadlineExceeded → 504。

客户端应始终检查 status.FromError(err).Code()，而非字符串匹配 error message。

实战练习：设计 Agent 分析服务的 Proto

题目：为告警分析 Agent 服务设计完整的 .proto 文件，要求：

  1. 支持 Unary 分析（提交告警，返回分析 ID + 摘要）
  2. 支持 Server Streaming（流式返回分析过程：思考步骤 + Token + 最终结果）
  3. 包含告警级别枚举、metadata map、可选的 session_id（oneof 或 optional）
  4. 定义 Health Check 兼容的标准服务
参考答案 
syntax = "proto3";
package agent.v1;
option go_package = "agent/v1;agentv1";

enum AlertLevel {
  ALERT_LEVEL_UNSPECIFIED = 0;
  INFO     = 1;
  WARNING  = 2;
  CRITICAL = 3;
}

enum StreamEventType {
  EVENT_TYPE_UNSPECIFIED = 0;
  THINKING  = 1;  // Agent 思考步骤
  TOKEN     = 2;  // LLM 输出 token
  TOOL_CALL = 3;  // 工具调用
  FINAL     = 4;  // 最终结果
  ERROR     = 5;
}

message AnalyzeRequest {
  string biz_line   = 1;
  string alert_body = 2;
  AlertLevel level    = 3;
  map<string, string> metadata = 4;
  optional string session_id = 5;  // 续接会话
}

message AnalyzeResponse {
  string analysis_id = 1;
  string summary     = 2;
  AlertLevel level   = 3;
}

message StreamEvent {
  StreamEventType type    = 1;
  string content          = 2;
  int32 sequence          = 3;
  bool is_final           = 4;
  map<string, string> extra = 5;
}

service AgentAnalysisService {
  // Unary：快速分析
  rpc Analyze(AnalyzeRequest) returns (AnalyzeResponse);

  // Server Streaming：流式分析（LLM 输出）
  rpc AnalyzeStream(AnalyzeRequest) returns (stream StreamEvent);

  // 查询历史分析
  rpc GetAnalysis(GetAnalysisRequest) returns (AnalyzeResponse);
}

message GetAnalysisRequest {
  string analysis_id = 1;
}
