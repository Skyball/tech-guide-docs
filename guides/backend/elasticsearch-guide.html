ES 是什么 — 搜索引擎的本质

💡
一句话：Elasticsearch 是一个分布式的「倒排索引数据库」——你给它一堆文档，它帮你快速找到包含某个词的所有文档，还能告诉你哪个最相关。

直觉理解：图书馆的索引卡片

想象你走进一个巨大的图书馆，要找所有提到「分布式」的书。

  • 笨办法（全表扫描）：一本一本翻，看有没有「分布式」这个词 → 这就是 MySQL 的 LIKE '%分布式%'
  • 聪明办法（倒排索引）：图书馆有一个索引柜，抽屉标签写着「分布式」，拉开就看到所有包含这个词的书号列表 → 这就是 Elasticsearch

ES 的核心价值：把「翻书找词」变成「查字典找书」。

Lucene 底层引擎

Java 编写的全文检索库。负责倒排索引的创建、搜索和评分。Lucene 是单机的、嵌入式的——它不知道「集群」「分片」是什么。

Elasticsearch 分布式包装

在 Lucene 之上加了分布式层：分片（Shard）、副本（Replica）、集群协调、REST API、聚合引擎。把单机搜索库变成了可水平扩展的搜索服务。

ES 擅长什么 / 不擅长什么

擅长

  • 全文搜索（文本匹配 + 相关性排序）
  • 日志/指标分析（时序数据聚合）
  • 模糊搜索、拼写纠错、自动补全
  • 地理位置搜索
  • 近实时（NRT）数据可见

不擅长

  • 事务（无 ACID，非关系数据库）
  • 频繁更新（每次更新 = 删除+重建索引）
  • JOIN 查询（反范式设计，不支持关联）
  • 做主数据库（数据安全性不如 MySQL/PG）
  • 小数据量场景（杀鸡用牛刀）
面试题：ES 和 MySQL LIKE 查询有什么本质区别？

MySQL LIKE '%keyword%'：遍历每一行，逐行做字符串匹配 → O(N)，N = 总行数。无法利用 B+Tree 索引（左模糊失效）。

Elasticsearch：建立倒排索引，词 → 文档列表的映射已预先计算好 → O(1) 查字典 + O(K) 取结果，K = 匹配文档数。还支持 TF-IDF / BM25 相关性评分，返回「最相关」而非「最早的」。

本质区别：MySQL 是「扫描文档找词」，ES 是「查词找文档」，数据结构不同导致了质的差异。

倒排索引 — ES 的核心数据结构

💡
一句话：倒排索引就是把「文档→词」的关系反转成「词→文档」。一本书的目录是正排索引（章节→内容），而书末尾的关键词索引是倒排索引（关键词→页码）。

直觉理解：从正排到倒排

假设我们有 3 个文档：

文档 ID内容
doc_1Elasticsearch is a search engine
doc_2Elasticsearch is distributed
doc_3Lucene is a search library

正排索引（Forward Index）—— 文档 → 词：

doc_1 → [elasticsearch, is, a, search, engine]
doc_2 → [elasticsearch, is, distributed]
doc_3 → [lucene, is, a, search, library]

倒排索引（Inverted Index）—— 词 → 文档：

elasticsearch → [doc_1, doc_2]
is            → [doc_1, doc_2, doc_3]
a             → [doc_1, doc_3]
search        → [doc_1, doc_3]
engine        → [doc_1]
distributed   → [doc_2]
lucene        → [doc_3]
library       → [doc_3]

搜索 "search" → 直接拿到 [doc_1, doc_3]，不需要扫描任何文档内容。

倒排索引的三层结构

倒排索引内部结构： ┌─────────────────────────────────────────────────┐ │ Term Dictionary（词典） │ │ 排序的词表，支持快速查找 │ │ ┌──────────┬──────────┬──────────┬────────────┐ │ │ │ a │ dist... │ elastic..│ engine ... │ │ │ └────┬─────┴────┬─────┴────┬─────┴────┬───────┘ │ │ ▼ ▼ ▼ ▼ │ │ ┌─────────────────────────────────────────────┐ │ │ │ Posting List（倒排列表） │ │ │ │ 每个词对应的文档列表 + 位置信息 │ │ │ │ │ │ │ │ "search" → [(doc_1, pos:4), (doc_3, pos:4)]│ │ │ │ "engine" → [(doc_1, pos:5)] │ │ │ └─────────────────────────────────────────────┘ │ │ │ │ ┌─────────────────────────────────────────────┐ │ │ │ Term Index（词典索引 / FST） │ │ │ │ 前缀树结构，加速 Term Dictionary 查找 │ │ │ │ 常驻内存，实现 O(len) 快速定位 │ │ │ └─────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────┘

Term Index

内存中的 FST（Finite State Transducer）前缀树。存储词的前缀，快速定位到 Term Dictionary 的磁盘位置。类似书本目录中的字母索引。

Term Dictionary

磁盘上的有序词表。按字典序排列所有 term，通过二分查找定位具体词。类似新华字典的正文部分。

Posting List

每个 term 对应的文档 ID 列表 + 词频（TF）+ 位置（Position）+ 偏移（Offset）。用于计算相关性评分和高亮显示。

Posting List 的压缩优化

如果一个词出现在 100 万个文档中，Posting List 就会存 100 万个 doc_id。ES 使用两个关键优化：

技术原理效果
FOR 编码
(Frame of Reference)		存差值而非绝对值。[73, 300, 302, 332] → 存为 [73, 227, 2, 30]，差值更小用更少 bit压缩率 70-90%
Roaring Bitmaps对 65536 大小的块：稀疏用 Array，密集用 Bitmap。求交集/并集直接位运算布尔查询飞快
⚠️ 倒排索引一旦写入就是不可变的（immutable）。这是 Lucene 的核心设计决策——不可变带来了简单的并发读取和系统文件缓存友好，但也意味着更新文档 = 标记删除旧文档 + 写入新文档。
面试题：为什么倒排索引是不可变的？不可变有什么好处和代价？

好处：

  • 无锁并发读：不可变数据天然线程安全，多线程搜索无需加锁
  • OS 缓存友好：不变的文件可以长期驻留在操作系统页缓存（page cache）中
  • 压缩效率高：数据不变，可以做更激进的压缩（FOR、Roaring Bitmap）

代价：

  • 更新代价大：修改一个文档 = 旧文档标记删除 + 新写一个 Segment
  • 需要 Merge：随着写入产生大量小 Segment，需要后台合并（Merge）来清理已删除文档并优化查询
  • 近实时而非实时：新写入的文档需要 refresh（默认 1s）后才可搜索
面试题：ES 的 Term Index 为什么用 FST 而不是 HashMap？

HashMap：精确查找 O(1) 很快，但必须把所有 key 完整存在内存中 → 内存占用巨大。百万级 term 时内存可能几个 GB。

FST（Finite State Transducer）：一种压缩的前缀树，共享公共前缀 → 内存占用极小（通常只有 HashMap 的 1/10）。支持前缀查询和范围查询（HashMap 做不到）。代价是查询 O(len) 略慢于 HashMap 的 O(1)，但对 Term 查找来说可以接受。

核心权衡：用少量 CPU 时间换大量内存空间，让 Term Index 能常驻内存。

分词与分析器 — 文本处理 Pipeline

💡
一句话：分析器（Analyzer）是 ES 的「文本预处理流水线」——把原始文本拆成一个个标准化的词（Token），然后才能建倒排索引。好比把一篇文章拆成关键词卡片放进索引柜。

分析器三阶段流水线

输入: "The Quick-Brown FOX jumped!!" │ ▼ ┌─────────────────────────┐ │ Character Filter │ 字符级预处理 │ 去除 HTML 标签、替换字符 │ "&" → "and" │ "The Quick-Brown FOX │ │ jumped!!" │ └────────┬────────────────┘ ▼ ┌─────────────────────────┐ │ Tokenizer │ 切词（核心步骤） │ 按规则拆分成 Token │ 按空格/标点拆分 │ ["The","Quick","Brown", │ │ "FOX","jumped"] │ └────────┬────────────────┘ ▼ ┌─────────────────────────┐ │ Token Filter │ Token 级后处理 │ 小写化、去停用词、词干提取 │ │ ["quick","brown", │ │ "fox","jump"] │ └─────────────────────────┘

内置分析器

分析器行为适用
standardUnicode 分词 + 小写英文默认，通用
simple非字母字符分割 + 小写简单英文
whitespace仅按空格分割日志、ID
keyword不分词，整体作为一个 Token精确匹配字段
ik_max_word中文最细粒度分词中文全文搜索
ik_smart中文智能分词中文精确匹配

中文分词的挑战

英文天然用空格分词，但中文没有分隔符。「中华人民共和国」怎么切？

  • ik_max_word：中华/人民/共和/国/中华人民共和国 → 召回率高
  • ik_smart：中华人民共和国 → 精确度高

最佳实践：写入时用 ik_max_word（多切词，更容易被搜到），搜索时用 ik_smart（少切词，更精确）。

text vs keyword — 最容易踩的坑

text

  • 写入时经过分析器分词
  • 支持全文搜索（match）
  • 不支持排序和聚合
  • 适合：文章标题、正文
VS

keyword

  • 不分词，作为整体存储
  • 支持精确匹配（term）
  • 支持排序和聚合
  • 适合：状态码、标签、邮箱
⚠️ 常见坑：用 term 查询 text 字段搜不到。因为存储时 "Hello World" 被分词为 ["hello", "world"]，而 term 精确匹配 "Hello World" 找不到。解决方案：给字段同时加 .keyword 子字段，或用 match 查询。

Dynamic Mapping（动态映射）

不定义 Mapping 直接写文档，ES 会自动推断类型。方便但容易出问题：

JSON 值自动推断为常见问题
"hello"text + keyword字符串默认双类型，浪费空间
123long可能只需要 integer
"2024-01-15"date不一定是日期的字符串被误判
3.14float精度问题

最佳实践：生产环境一定要显式定义 Mapping，关闭或限制动态映射。

PUT /my_index
{
  "mappings": {
    "dynamic": "strict",
    "properties": { ... }
  }
}

分布式架构 — 分片、副本与集群拓扑

💡
一句话：ES 把一个大索引切成多块（分片）分散在不同机器上，每块再复制几份（副本）放到其他机器上。分片解决容量，副本解决可用性——就像把一本百科全书拆成多卷，每卷复印几份放在不同图书馆。

分片（Shard）与副本（Replica）

Index: "products" — 3 Primary Shards, 1 Replica Node 1 Node 2 Node 3 ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ P0 (主分片) │ │ P1 (主分片) │ │ P2 (主分片) │ │ R1 (副本) │ │ R2 (副本) │ │ R0 (副本) │ └─────────────┘ └─────────────┘ └─────────────┘ P0 的数据 = R0 的数据（副本是主分片的精确拷贝） 写入 → 先到主分片 → 同步到对应副本 查询 → 主分片或副本都可以响应（负载均衡）

主分片（Primary Shard）

  • 每个分片是一个独立的 Lucene 实例
  • 索引创建后主分片数不可更改
  • 文档通过路由公式分配到分片：shard = hash(_routing) % num_primary_shards
  • 默认 _routing = _id

副本分片（Replica Shard）

  • 主分片的完整拷贝，提供冗余
  • 副本数可以随时动态调整
  • 读请求可以由副本响应 → 提升读吞吐
  • 主分片所在节点挂了 → 副本自动提升为主分片

集群节点角色

角色职责配置
Master Node管理集群元数据、索引创建/删除、分片分配决策node.roles: [master]
Data Node存储分片数据、执行搜索和聚合node.roles: [data]
Coordinating Node接收客户端请求、分发到数据节点、合并结果返回node.roles: []（空）
Ingest Node写入前的数据预处理（Pipeline）node.roles: [ingest]

分片分配与路由

# 文档路由公式
shard_num = hash(_routing) % number_of_primary_shards

# 默认 _routing = 文档 _id
# 可以自定义路由（让同一用户的数据落在同一分片）：
PUT /orders/_doc/order_123?routing=user_456
{
  "user_id": "user_456",
  "amount": 99.9
}
⚠️ 这就是为什么主分片数创建后不能改——改了 hash 取模结果就变了，已有文档的路由全部错乱。需要改分片数只能 Reindex。

分片数量规划

  • 单个分片推荐大小：10GB–50GB（官方建议）
  • 分片过少：无法水平扩展，单分片过大影响恢复速度
  • 分片过多：每个分片占用内存和文件句柄，Master 节点压力大（需要管理所有分片的元数据）
  • 经验公式：分片数 = 预估数据量 / 单分片目标大小
  • 日志场景：按时间滚动索引（logs-2024-09-01），配合 ILM 自动管理生命周期
面试题：ES 的主分片数为什么创建后不能修改？

因为文档的分片路由使用公式 shard = hash(_routing) % num_primary_shards。如果修改了主分片数，取模的结果就变了，已写入文档的分片位置与新路由不一致 → 搜索时去错误的分片查找 → 找不到文档。

如果确实需要改，唯一的办法是创建新索引（新分片数）并 Reindex（重新导入所有文档），或使用 _split/_shrink API（但有严格的限制条件）。

写入流程 — 近实时搜索的实现原理

💡
一句话：ES 的写入不是直接写磁盘，而是先写内存 Buffer → 定期 Refresh 生成可搜索的 Segment → 最终 Flush 到磁盘。中间靠 Translog 防丢数据。这就是为什么 ES 是「近实时」而非「实时」——默认有 1 秒延迟。

写入全流程

Primary Shard 处理 │ │ ① 写入 Translog（追加写，顺序IO） │ │ ② 写入 In-Memory Buffer │ │ ③ 返回 ACK 给 Coordinating Node │ └────────────────┬────────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ 3. 同步到 Replica Shard │ │ 并行写入所有副本 │ │ 所有副本 ACK 后 → 客户端收到成功响应 │ └────────────────┬────────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ 4. Refresh（默认每 1 秒） │ │ Buffer → 新的 Segment（in OS cache） │ │ 文档变为可搜索！ │ └────────────────┬────────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ 5. Flush（默认 30 分钟或 Translog 满） │ │ Segment fsync 到磁盘 │ │ 清空 Translog │ └────────────────┬────────────────────────┘ ▼ ┌─────────────────────────────────────────┐ │ 6. Merge（后台持续进行） │ │ 合并多个小 Segment 为大 Segment │ │ 物理删除标记为删除的文档 │ └─────────────────────────────────────────┘

核心概念详解

Translog（事务日志）

类似 MySQL 的 redo log。每次写入先追加到 Translog（顺序写，极快）。如果节点崩溃，重启后从 Translog 回放恢复未 Flush 的数据。

# Translog 配置
PUT /my_index/_settings
{
  "index.translog.durability": "request",
  "index.translog.flush_threshold_size": "512mb"
}

# durability: "request" → 每次请求 fsync（安全）
# durability: "async"  → 定期 fsync（快但可能丢少量数据）

Refresh（刷新）

把 In-Memory Buffer 中的文档写成一个新的 Lucene Segment（在 OS 文件缓存中，尚未 fsync 到磁盘）。Refresh 后文档就能被搜索到。

# 手动 refresh
POST /my_index/_refresh

# 修改 refresh 间隔
PUT /my_index/_settings
{
  "index.refresh_interval": "5s"
}

# 批量导入时关闭 refresh 提升写入速度
PUT /my_index/_settings
{
  "index.refresh_interval": "-1"
}

Segment 与 Merge

每次 Refresh 都会产生一个新的 Segment 文件。大量写入会导致 Segment 数量爆炸。后台 Merge 进程会持续合并小 Segment：

时间线： t=0 [Seg_0] t=1 [Seg_0] [Seg_1] t=2 [Seg_0] [Seg_1] [Seg_2] ↓ Merge t=3 [Seg_0_1_2] ← 合并为一个大 Segment t=4 [Seg_0_1_2] [Seg_3] t=5 [Seg_0_1_2] [Seg_3] [Seg_4] Merge 时做的事情： 1. 多个小 Segment → 一个大 Segment 2. 被标记为 "deleted" 的文档在此时被真正物理删除 3. 合并后的 Segment 被 fsync 到磁盘 4. 删除旧的小 Segment 文件

更新和删除的真相

因为 Segment 不可变：

  • 删除：不是真删，而是在 .del 文件中标记该文档已删除。搜索时过滤掉。真正物理删除在 Merge 时发生
  • 更新：= 标记删除旧文档 + 写入新文档。所以 ES 的更新代价比 MySQL 大得多
  • 版本控制：_version 字段实现乐观并发控制，防止并发更新覆盖
面试题：ES 为什么是「近实时」而不是「实时」？如何实现实时可搜索？

近实时原因：文档写入后先进入 In-Memory Buffer，需要等 Refresh（默认 1s）生成 Segment 后才可搜索。这 1 秒的窗口就是「近实时」的含义。

实现实时：

  • 方法 1：写入后手动调用 POST /index/_refresh（牺牲性能）
  • 方法 2：设置 refresh_interval: "1ms"（几乎实时但 CPU 开销大）
  • 方法 3：使用 GET /index/_doc/id 按 ID 查询（直接读 Translog，不依赖 Refresh）

实际权衡：绝大多数场景 1s 延迟可接受。过于频繁的 Refresh 会产生大量小 Segment，反而降低搜索性能。

读取与查询 — DSL 查询与相关性评分

💡
一句话：ES 查询分两大类——精确查询（是或不是）和全文查询（有多相关）。全文查询的灵魂是 BM25 评分算法：词频越高、文档越短、越稀有的词匹配上了，分数就越高。

查询的分布式执行流程

客户端: GET /products/_search { "query": ... } │ ▼ Coordinating Node │ ├─── Query Phase ────────────────────────┐ │ 广播查询到所有相关分片 │ │ ┌──────┐ ┌──────┐ ┌──────┐ │ │ │Shard0│ │Shard1│ │Shard2│ │ │ │top 10│ │top 10│ │top 10│ │ │ └──┬───┘ └──┬───┘ └──┬───┘ │ │ └─────────┼─────────┘ │ │ ▼ │ │ Coordinating Node 汇总排序 → 全局 top 10 │ │ ├─── Fetch Phase ────────────────────────┤ │ 只去存有 top 10 文档的分片取完整内容 │ │ │ ▼ │ 返回结果给客户端 │ └────────────────────────────────────────────┘

两大查询类型

Term Level 查询 精确匹配

不分词，直接在倒排索引中精确查找。

# term：精确匹配单个值
{"term": {"status": "active"}}

# terms：匹配多个值（OR）
{"terms": {"status": ["active", "pending"]}}

# range：范围查询
{"range": {"price": {"gte": 10, "lte": 100}}}

# exists：字段是否存在
{"exists": {"field": "email"}}

# wildcard：通配符（慎用，性能差）
{"wildcard": {"name": "elas*"}}

Full Text 查询 全文搜索

先分词，再在倒排索引中匹配，计算相关性分数。

# match：分词后 OR 匹配
{"match": {"title": "分布式 搜索引擎"}}
# → "分布式" OR "搜索引擎"

# match_phrase：短语匹配（顺序+相邻）
{"match_phrase": {"title": "分布式搜索"}}

# multi_match：多字段搜索
{"multi_match": {
  "query": "elasticsearch",
  "fields": ["title^3", "content"]
}}
# title 权重 ×3

# match + operator
{"match": {
  "title": {
    "query": "分布式 搜索引擎",
    "operator": "and"
  }
}}

布尔查询（Bool Query）— 最常用的组合查询

GET /products/_search
{
  "query": {
    "bool": {
      "must": [
        {"match": {"title": "Elasticsearch"}}
      ],
      "filter": [
        {"term": {"status": "published"}},
        {"range": {"price": {"lte": 100}}}
      ],
      "should": [
        {"match": {"tags": "搜索引擎"}}
      ],
      "must_not": [
        {"term": {"category": "deprecated"}}
      ]
    }
  }
}
子句影响评分？语义
must是必须匹配，参与评分
filter否必须匹配，不评分（可缓存，性能更好）
should是加分项，匹配则分数更高
must_not否必须不匹配，不评分
⚠️ 性能关键：不需要评分的条件放 filter。filter 结果可以被 ES 缓存（bitset cache），重复查询几乎零开销。典型的 filter 场景：状态过滤、时间范围、权限控制。

BM25 评分算法

ES 默认使用 BM25（Best Matching 25）计算相关性分数。核心思想：

BM25(q, d) = Σ IDF(qi) × (tf(qi, d) × (k1 + 1)) / (tf(qi, d) + k1 × (1 - b + b × |d| / avgdl)) 三个核心因子： ┌─────────────────────────────────────────────────┐ │ 1. TF（词频） │ │ 这个词在这篇文档中出现几次？ │ │ 出现越多 → 分数越高（但有上限，避免灌水） │ │ │ │ 2. IDF（逆文档频率） │ │ 这个词在所有文档中有多常见？ │ │ 越稀有的词 → 权重越大 │ │ "的" 出现在 90% 文档中 → IDF 很低 │ │ "Elasticsearch" 出现在 1% 文档中 → IDF 很高 │ │ │ │ 3. 字段长度归一化 │ │ 短文档匹配 → 更相关（100字的摘要提到一次 │ │ 比 10000字的文章提到一次更可能是核心主题） │ └─────────────────────────────────────────────────┘

# 查看评分细节
GET /products/_search
{
  "explain": true,
  "query": {
    "match": {"title": "Elasticsearch 指南"}
  }
}

# 响应中会包含评分分解：
# "explanation": {
#   "value": 3.14,
#   "description": "sum of:",
#   "details": [
#     { "value": 2.1, "description": "idf × tf for 'elasticsearch'" },

#   ]
# }
面试题：filter 和 must 有什么区别？为什么 filter 更快？

must：文档必须匹配，且匹配程度参与 _score 计算。每次查询都要计算 BM25 评分。

filter：文档必须匹配，但不计算评分（_score = 0）。好处：

  • 跳过评分计算：省掉 TF-IDF/BM25 的浮点运算
  • 结果可缓存：filter 的结果是确定的（是/否），ES 会用 bitset 缓存。相同的 filter 条件第二次查询直接命中缓存
  • 典型场景："status": "active"、"date": {"gte": "2024-01-01"} 这类不需要排名的过滤条件

总结：需要排名 → must/should；只需要过滤 → filter/must_not。

聚合分析 — ES 作为分析引擎

💡
一句话：聚合（Aggregation）是 ES 的「GROUP BY + 统计函数」——在搜索结果上做分组、计数、求和、平均值、百分位等统计分析。ES 的聚合比 SQL 更灵活，支持多层嵌套和近似算法。

三大聚合类型

Bucket 聚合 分桶

按条件分组，类似 GROUP BY。每个桶里的文档可以继续做子聚合。

  • terms：按字段值分组
  • range：按范围分组
  • date_histogram：按时间间隔分组
  • histogram：按数值间隔分组
  • filters：按多个查询条件分组

Metric 聚合 指标

对桶内文档计算统计值，类似 SUM/AVG/COUNT。

  • avg：平均值
  • sum：求和
  • min / max
  • cardinality：去重计数（HLL）
  • percentiles：百分位
  • stats：一次返回 count/min/max/avg/sum

Pipeline 聚合 管道

对其他聚合的结果做二次计算，类似子查询。

  • avg_bucket：桶平均值
  • max_bucket：最大桶
  • derivative：求导（环比）
  • cumulative_sum：累计求和
  • moving_avg：移动平均

实战示例：电商数据分析

# 按类目分组 → 每组算平均价格 + 销量总和
GET /products/_search
{
  "size": 0,
  "aggs": {
    "by_category": {
      "terms": {"field": "category", "size": 10},
      "aggs": {
        "avg_price": {"avg": {"field": "price"}},
        "total_sales": {"sum": {"field": "sales_count"}},
        "price_ranges": {
          "range": {
            "field": "price",
            "ranges": [
              {"to": 50, "key": "cheap"},
              {"from": 50, "to": 200, "key": "medium"},
              {"from": 200, "key": "expensive"}
            ]
          }
        }
      }
    }
  }
}

# 按天统计日志量（时序分析）
GET /logs-*/_search
{
  "size": 0,
  "aggs": {
    "logs_per_day": {
      "date_histogram": {
        "field": "@timestamp",
        "calendar_interval": "day"
      },
      "aggs": {

}

cardinality 聚合与 HyperLogLog

cardinality 用于去重计数（如：今天有多少独立用户访问？）。底层使用 HyperLogLog++ 算法——一种概率数据结构，用极小的内存（几 KB）就能估算上亿级别的基数。

# 统计独立用户数
GET /access_logs/_search
{
  "size": 0,
  "aggs": {
    "unique_users": {
      "cardinality": {
        "field": "user_id",
        "precision_threshold": 3000
      }
    }
  }
}
# precision_threshold 越大越精确（但内存越多）
# 默认 3000：基数 < 3000 时几乎精确，超过后误差约 1-6%
⚠️ cardinality 是近似值！如果需要精确去重计数，要么数据量小直接用 terms 聚合，要么在应用层用精确算法。
面试题：ES 的 terms 聚合在分布式环境下结果是精确的吗？

不一定精确。在分布式环境中，terms 聚合的执行过程：

  1. 每个分片独立计算本地 top N 的桶
  2. Coordinating Node 合并各分片结果

问题：如果某个词在每个分片上都排不进 top N，但全局加起来其实排得进 → 被遗漏。

解决方案：

  • 增大 shard_size（默认 = size * 1.5 + 10）：让每个分片返回更多候选
  • 如果数据按某个字段路由（如 user_id），同一用户的数据在同一分片，则该字段的 terms 聚合是精确的
  • 对精度要求极高的场景，用 composite 聚合做分页遍历

集群管理 — 节点角色、故障恢复与脑裂

💡
一句话：ES 集群通过 Master 选举管理分片分配，通过副本实现高可用。最怕的问题是「脑裂」——集群分成两半，两边都认为自己是合法的，导致数据不一致。ES 7.x 用新的选举机制基本解决了这个问题。

集群健康状态

GET /_cluster/health

# 三种颜色：
# 🟢 green  — 所有主分片和副本都已分配，集群完全健康
# 🟡 yellow — 所有主分片已分配，部分副本未分配（单节点集群常见）
# 🔴 red    — 有主分片未分配，部分数据不可用
状态主分片副本分片数据可用性常见原因
Green全部 ✅全部 ✅100%正常状态
Yellow全部 ✅部分 ❌100%（但无冗余）节点不够 / 刚重启
Red部分 ❌—<100%节点宕机且无副本

Master 选举与脑裂

什么是脑裂（Split Brain）？

正常状态： 脑裂状态： ┌──────────────┐ ┌──────┐ ┌──────┐ │ Master │ │Master│ │Master│ ← 两个 Master！ │ Node1 Node2 │ 网络分区→ │Node1 │ │Node2 │ │ Node3 │ │Node3 │ │ │ └──────────────┘ └──────┘ └──────┘ 两边各自接收写入 → 数据不一致

ES 6.x 及之前

使用 discovery.zen.minimum_master_nodes：设为 (N/2)+1（N = 候选 Master 节点数）。配置错误是脑裂的主因。

ES 7.x 及之后

使用新的 Voting Configuration 机制，自动管理。只需配置初始种子节点：

# elasticsearch.yml
cluster.initial_master_nodes:
  - node-1
  - node-2
  - node-3
discovery.seed_hosts:
  - 192.168.1.1
  - 192.168.1.2
  - 192.168.1.3

集群自动维护投票配置，大大降低脑裂风险。

当节点加入或离开集群时，Master 会重新平衡分片：

面试题：ES 集群出现 Red 状态怎么排查？

Red = 有主分片未分配。排查步骤：

  1. GET /_cluster/health?level=indices → 找到哪个索引是 Red
  2. GET /_cat/shards/index_name?v → 找到哪个分片 UNASSIGNED
  3. GET /_cluster/allocation/explain → 查看未分配原因
  4. 常见原因和对策：
    • 节点宕机且无副本 → 等节点恢复或从备份恢复
    • 磁盘满 → 清理磁盘或增加节点
    • 分片数据损坏 → POST /_cluster/reroute?retry_failed=true 或接受数据丢失 allocate_empty_primary

性能调优 — 索引设计与查询优化

💡
一句话：ES 调优的核心三件事——合理的 Mapping（减少无用索引）、善用 filter 缓存（避免重复计算）、控制分片大小和数量（平衡读写性能）。

查询优化

Mapping 层面

  • 不搜索的字段设 "index": false
  • 不需要聚合的 text 字段关闭 fielddata
  • 不需要评分的字段关闭 "norms": false
  • 用 keyword 而非 text 做精确过滤
  • 避免 Dynamic Mapping 产生多余字段

查询层面

  • 过滤条件放 filter 而非 must
  • 避免 wildcard 前缀通配（*foo）
  • 用 _source 过滤只返回需要的字段
  • 深度分页用 search_after 代替 from+size
  • 聚合大数据量用 composite 分页

深度分页问题

ES 默认最多 from + size ≤ 10000。为什么？

查询: from=9990, size=10（取第 9991-10000 条） 每个分片需要返回 top 10000 给 Coordinating Node 如果有 5 个分片 → 协调节点要处理 50000 条文档 from 越大 → 每个分片返回越多 → 内存和网络开销爆炸

解决方案对比：

方案原理适用
from + size跳过 from 条取 size 条浅分页（< 1000 页）
search_after用上一页最后一条的排序值做游标无限向下翻页
scroll创建快照，用游标遍历导出全部数据（已不推荐，用 PIT）
PIT + search_afterPoint In Time 快照 + 游标大数据量稳定遍历（推荐）
# search_after 示例
GET /products/_search
{
  "size": 10,
  "sort": [{"price": "desc"}, {"_id": "asc"}],
  "search_after": [79.9, "product_abc"]
}

面试题：ES 的 JVM 堆为什么建议不超过 30GB？

Java 在堆 ≤ 约 32GB 时启用压缩对象指针（Compressed Ordinary Object Pointers）：用 4 字节指针代替 8 字节。一旦堆超过 ~32GB，指针膨胀为 8 字节，实际可用内存反而更少。

同时，ES 严重依赖 OS 的 page cache 缓存 Lucene Segment 文件。留给 OS 的内存越多，搜索时命中缓存的概率越高 → 避免磁盘 IO。

最佳实践：堆设为物理内存的 50%，最大 30-31GB。64GB 机器 → 堆 30GB + OS cache 34GB。

ES 与向量搜索

ES 8.x 引入了 kNN（k-Nearest Neighbors）向量搜索，支持 dense_vector 字段类型，可以做语义搜索。

# 定义向量字段
PUT /articles
{
  "mappings": {
    "properties": {
      "title_vector": {
        "type": "dense_vector",
        "dims": 768,
        "index": true,
        "similarity": "cosine"
      }
    }
  }
}

# kNN 搜索
GET /articles/_search
{
  "knn": {
    "field": "title_vector",
    "query_vector": [0.1, 0.2, ...],
    "k": 10,
    "num_candidates": 100
  }
}

ES vs 专用向量数据库（Milvus/Pinecone）：ES 的向量搜索适合「关键词 + 语义」混合检索场景。纯向量搜索（十亿级别）用专用引擎性能更好。

面试题：什么场景下应该用 ES 而不是 MySQL？反过来呢？

选 ES：

  • 需要全文搜索、模糊匹配、相关性排序（商品搜索、内容搜索）
  • 日志/指标的海量写入 + 时序聚合分析
  • 需要自动补全、拼写纠错等搜索体验
  • 数据量大且查询模式偏分析型

选 MySQL/PG：

  • 需要事务保证（订单、支付、库存）
  • 复杂的 JOIN 和关联查询
  • 频繁的单行更新操作
  • 强一致性要求（金融场景）

最佳实践：MySQL 做 Source of Truth（写入），ES 做搜索加速（只读副本），通过 CDC 工具同步。

面试高频题汇总

💡
一句话：ES 面试的核心考点就三个——倒排索引的原理（数据结构）、写入/查询的分布式流程（系统设计）、性能优化的实战经验（工程能力）。下面是高频题精选。
ES 的写入流程是怎样的？为什么是近实时的？

完整写入流程：客户端 → Coordinating Node 路由 → Primary Shard 写入 Translog + Memory Buffer → 同步 Replica → ACK 客户端。

Buffer 中的数据需要 Refresh（默认 1 秒）后才生成 Segment 并可搜索 → 这就是「近实时」的原因。Translog 保证即使 Refresh 前宕机数据也不丢。

维度倒排索引B+Tree

ES 如何实现高可用？节点宕机了会怎样？

通过副本分片实现高可用：

  1. 每个主分片有 N 个副本，分布在不同节点
  2. 节点宕机 → Master 检测到节点离开
  3. 如果宕机节点有主分片 → 对应副本自动提升为新主分片
  4. Master 在其他存活节点上创建新的副本，恢复冗余级别
  5. 写入重定向到新的主分片，读取由剩余分片/副本承担

关键配置：Master 节点数为奇数（3 或 5），避免选举平票。

ES 查询很慢怎么排查优化？

排查步骤：

  1. GET /_cat/indices?v&s=docs.count:desc — 检查索引大小和分片数
  2. GET /index/_search + "profile": true — 查看每个分片的查询耗时分解
  3. 检查是否用了 wildcard/regexp（前缀通配符是性能杀手）
  4. 检查是否把过滤条件放在了 must 而非 filter
  5. 检查 JVM 堆使用和 GC 情况：GET /_nodes/stats/jvm

常见优化：

  • 过滤条件 → filter（利用缓存）
  • 只返回需要的字段 → "_source": ["field1", "field2"]
  • 深度分页 → search_after
  • 大结果集聚合 → composite 聚合
  • Mapping 优化 → 关闭不需要的 index/norms/doc_values
ES 和 MySQL 数据不一致怎么办？

在 MySQL + ES 双写架构中，数据不一致是常见问题：

原因：应用双写（先写 MySQL 再写 ES）→ ES 写入失败但 MySQL 已提交，或顺序不一致。

解决方案（按推荐顺序）：

  1. CDC 同步（推荐）：Canal/Debezium 监听 MySQL binlog → 投递到 Kafka → 消费写入 ES。单一数据流，天然保序
  2. 消息队列解耦：写 MySQL 后发消息到 MQ → 消费者写 ES。失败可重试
  3. 定时全量校对：定期比对 MySQL 和 ES 数据差异，修复不一致
  4. 版本号兜底：写入 ES 时带版本号，旧版本不覆盖新版本
如何设计一个商品搜索系统？

整体架构：

用户搜索 → API Gateway → Search Service → ES ↑ 商品管理 → MySQL → Canal → Kafka → ES Writer

Mapping 设计：

  • name: text（ik_max_word）— 全文搜索
  • category: keyword — 精确过滤
  • price: float — 范围过滤和排序
  • tags: keyword — 标签过滤
  • sales: integer — 排序因子
  • create_time: date — 时间范围

查询策略：用户输入关键词 → bool 查询：must(match name) + filter(category, price range) + should(boost by sales)。支持 suggest/completion 做自动补全。

Segment Merge 是什么？为什么需要？有什么风险？

是什么：后台进程将多个小 Segment 合并为少量大 Segment 的过程。

为什么需要：

  • 每次 Refresh 产生一个新 Segment → 数量持续增长
  • Segment 越多，搜索时要查询的文件越多 → 性能下降
  • 被标记删除的文档只有在 Merge 时才被物理清理 → 释放磁盘空间

风险：Merge 是 IO 密集操作。大 Segment 合并时可能占满磁盘 IO → 影响搜索延迟。需要合理配置 index.merge.policy 和 indices.store.throttle 控制 Merge 速率。

ES 的 Nested 类型和 Object 类型有什么区别？

Object 类型：嵌套对象被扁平化存储。数组场景会丢失对象边界。

# 文档：{"users": [{"name":"Alice","age":30}, {"name":"Bob","age":25}]}
# 扁平化后：users.name = ["Alice","Bob"], users.age = [30, 25]
# 查询 name=Alice AND age=25 → 错误匹配！（Alice 是 30 岁）

Nested 类型：每个嵌套对象作为独立的内部文档存储，保持对象边界。查询时使用 nested 查询确保条件在同一个对象内匹配。代价是更多的存储空间和更复杂的查询语法。
