1. 容器化是什么

💡
一句话：容器 = 轻量级的「应用沙盒」，把代码和依赖打包在一起，在任何机器上都能一模一样地运行。

直觉理解：集装箱的类比

想象国际贸易——以前货物散装运输，到港口要逐件卸载，效率低还容易损坏。集装箱的发明改变了一切：不管里面装的是玩具、电子产品还是食品，外面都是标准化的箱子，任何港口的吊车都能装卸。

容器对应用做了同样的事：不管你的应用是 Python + Redis 还是 Go + PostgreSQL，打包成容器后，在开发机、测试服务器、云平台上都能以完全一致的方式运行。

演进路线

物理机时代          虚拟机时代              容器时代
┌─────────┐     ┌──────────────┐     ┌──────────────────┐
│  App A   │     │ VM1   VM2    │     │ C1  C2  C3  C4   │
│  App B   │     │┌────┐┌────┐ │     │┌──┐┌──┐┌──┐┌──┐ │
│  App C   │     ││AppA││AppB│ │     ││A ││B ││C ││D │ │
│──────────│     ││Libs││Libs│ │     │└──┘└──┘└──┘└──┘ │

                └──────────────┘

虚拟机 重量级

  • 每个 VM 包含完整 Guest OS
  • 启动时间：分钟级
  • 内存占用：GB 级
  • 隔离性：硬件级别，安全性强

容器 轻量级

  • 共享宿主机 OS 内核
  • 启动时间：秒级（甚至毫秒级）
  • 内存占用：MB 级
  • 隔离性：进程级别，通过 Namespace + Cgroups

容器的底层原理（Linux）

技术作用类比
Namespace隔离进程、网络、文件系统等资源每个容器有自己的「房间」，看不到别人的东西
Cgroups限制 CPU、内存等资源使用量每个房间有「水电表」，超额就断供
UnionFS分层文件系统，镜像层共享 + 容器层可写多层透明纸叠在一起，最上面一层可以写字
面试题：容器和虚拟机的本质区别是什么？

参考答案：虚拟机通过 Hypervisor 虚拟化硬件，每个 VM 运行一个完整的 Guest OS，隔离粒度是硬件级别；容器通过 Linux Namespace 隔离进程视图（PID/NET/MNT/UTS/IPC/USER），通过 Cgroups 限制资源配额，共享宿主机内核，隔离粒度是进程级别。因此容器更轻量（MB vs GB）、启动更快（秒 vs 分钟），但隔离性弱于 VM。生产中常见的方案是 VM + 容器混用：VM 做租户级隔离，容器做应用级部署。

面试题：Docker 容器本质上是什么？

参考答案：Docker 容器本质上就是一个被 Namespace 隔离、被 Cgroups 限制、根文件系统由 UnionFS（如 OverlayFS）提供的特殊进程。它不是虚拟机，没有独立的内核，docker exec 进入容器看到的 PID 1 进程就是容器的主进程。所以容器的生命周期 = 主进程的生命周期。

2. Docker 核心概念

💡
一句话：镜像是「菜谱」，容器是「做出来的菜」，Registry 是「菜谱分享平台」。

镜像 Image

只读模板，包含运行应用的一切：代码、运行时、库、环境变量。由多个只读层叠加组成。

容器 Container

镜像的运行实例。在镜像的只读层上加一个可写层。停止后可写层还在，删除后消失。

仓库 Registry

存储和分发镜像的服务。Docker Hub 是公共仓库，企业用 Harbor、ECR、GCR 做私有仓库。

镜像分层原理

┌──────────────────────┐  ← 可写层（Container Layer）
├──────────────────────┤
│  COPY app.py .       │  ← Layer 4（应用代码）
├──────────────────────┤
│  RUN pip install     │  ← Layer 3（依赖安装）
├──────────────────────┤
│  RUN apt-get update  │  ← Layer 2（系统包）
├──────────────────────┤
│  FROM python:3.11    │  ← Layer 1（基础镜像）
└──────────────────────┘

关键：每一层只读且可被多个镜像/容器共享 → 节省磁盘和传输时间

常用命令速查

# 镜像操作
docker pull nginx:1.25           # 拉取镜像
docker images                     # 列出本地镜像
docker rmi nginx:1.25            # 删除镜像
docker build -t myapp:v1 .       # 构建镜像
docker tag myapp:v1 registry/myapp:v1  # 打标签
docker push registry/myapp:v1   # 推送到仓库

# 容器操作
docker run -d --name web -p 8080:80 nginx  # 后台运行
docker ps                         # 列出运行中的容器
docker ps -a                      # 列出所有容器（含停止的）
docker logs -f web               # 查看日志（实时跟踪）
docker exec -it web /bin/sh      # 进入容器
docker stop web                  # 优雅停止（SIGTERM → SIGKILL）
docker rm web                    # 删除容器

# 调试诊断
docker inspect web               # 查看容器元数据（JSON）
docker stats                     # 实时资源使用
docker top web                   # 容器内进程列表
⚠️ 常见坑：docker run 不加 --rm 时，容器停止后仍占用磁盘空间。开发环境建议加 --rm 自动清理；生产环境不要加，方便 debug。
面试题：docker run 的完整生命周期是什么？

参考答案：docker run 背后发生了：① Docker Client 发 HTTP 请求给 Docker Daemon；② Daemon 检查本地是否有镜像，没有则 pull；③ 创建容器（分配 ID、可写层、网络配置）；④ 配置 Namespace 和 Cgroups；⑤ 启动容器主进程（ENTRYPOINT/CMD）；⑥ 主进程退出时容器停止（exit code 传递给 Daemon）。

3. Dockerfile 最佳实践

💡
一句话：Dockerfile 就是镜像的「施工图纸」，写得好构建快且镜像小，写得差构建慢且镜像大。

多阶段构建（Multi-stage Build）

核心思想：用一个阶段编译，另一个阶段只拷贝产物。最终镜像不包含编译工具链，体积大幅缩小。

单阶段（臃肿）

FROM golang:1.22
WORKDIR /app
COPY . .
RUN go build -o server .
EXPOSE 8080
CMD ["./server"]
# 最终镜像 ~800MB（含 Go 工具链）
VS

多阶段（精简）

# 阶段 1：编译
FROM golang:1.22 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o server .

# 阶段 2：运行
FROM alpine:3.19
COPY --from=builder /app/server /server
EXPOSE 8080
CMD ["/server"]
# 最终镜像 ~15MB

层缓存优化

# ❌ 错误：每次代码改动都会重新 pip install
FROM python:3.11-slim
COPY . /app
RUN pip install -r /app/requirements.txt

# ✅ 正确：先拷贝依赖文件，利用层缓存
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
# 只有 requirements.txt 变化时才重新安装依赖

最佳实践清单

镜像瘦身

  • 用 alpine 或 distroless 基础镜像
  • 合并 RUN 指令减少层数
  • 用 .dockerignore 排除无关文件
  • --no-cache-dir 避免 pip 缓存

安全加固

  • 不要用 root 运行应用
  • 用 USER 指令切换非特权用户
  • 不在镜像中硬编码密钥/密码
  • 定期用 trivy / snyk 扫描漏洞

完整 Python 项目 Dockerfile

FROM python:3.11-slim AS base

RUN groupadd -r appuser && useradd -r -g appuser appuser

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN chown -R appuser:appuser /app
USER appuser

EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost:8000/health || exit 1

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
⚠️ 常见坑：COPY . . 会把 .git、node_modules、__pycache__ 都拷进去。务必写好 .dockerignore！
面试题：Docker 层缓存的失效规则是什么？

参考答案：Docker 从 Dockerfile 顶部逐层检查缓存：① 对 COPY/ADD 指令，比较文件内容的 checksum，有变化则缓存失效；② 对 RUN 指令，比较命令字符串是否完全相同（不会检查命令的输出）；③ 某一层缓存失效后，后续所有层都不再使用缓存。所以把变化频率低的指令放前面（如安装依赖），变化频率高的放后面（如拷贝代码）。

面试题：ENTRYPOINT 和 CMD 的区别？

参考答案：ENTRYPOINT 定义容器的「入口程序」，CMD 定义「默认参数」。docker run 后面的参数会覆盖 CMD，但不会覆盖 ENTRYPOINT（除非加 --entrypoint）。最佳实践：ENTRYPOINT 设为可执行文件，CMD 设为默认参数。例如 ENTRYPOINT ["python"]、CMD ["app.py"]，这样 docker run myimage test.py 会执行 python test.py。

4. Docker 网络

💡
一句话：Docker 网络就是给容器「接网线」——选择不同的网络模式，决定容器怎么跟外界和彼此通信。

四种网络模式

模式原理场景隔离性
bridge（默认）创建虚拟网桥 docker0，容器通过 veth pair 连接单机多容器通信中
host容器直接使用宿主机网络栈，无网络隔离性能敏感场景（减少 NAT 开销）无
none没有网络，只有 loopback安全敏感的离线计算任务完全
overlay跨主机的虚拟网络（VXLAN 隧道）Docker Swarm / 多主机通信高

自定义网络

# 创建自定义网络（推荐替代默认 bridge）
docker network create --driver bridge my-net

# 容器加入自定义网络（支持容器名 DNS 解析）
docker run -d --name api --network my-net myapi:v1
docker run -d --name db  --network my-net postgres:16

# api 容器中可以直接用 "db" 作为主机名访问 postgres
# psql -h db -U postgres  ← 这就能连上！

# 查看网络详情
docker network inspect my-net
✅
最佳实践：不要用默认的 bridge 网络。创建自定义网络可以获得容器名 DNS 解析，默认 bridge 只能用 IP 通信，非常不方便。
面试题：容器间通过容器名通信的原理是什么？

参考答案：Docker 的自定义 bridge 网络内置了一个 DNS 服务器（运行在 127.0.0.11）。当容器用 --name 启动并加入自定义网络后，Docker Daemon 会在 DNS 中注册 容器名 → IP 的映射。其他同网络容器解析该容器名时，会被 /etc/resolv.conf 中的 nameserver 127.0.0.11 截获，由 Docker 内置 DNS 返回对应 IP。注意：默认的 bridge 网络不支持此功能。

5. Docker 存储

💡
一句话：容器默认是「用完即扔」的，数据要持久化就得用 Volume 或 Bind Mount 把数据「存到容器外面」。

三种存储方式对比

类型数据位置适用场景生命周期
VolumeDocker 管理的区域
/var/lib/docker/volumes/		数据库、持久化数据独立于容器，需手动删除
Bind Mount宿主机任意路径开发环境热重载、配置注入跟随宿主机文件
tmpfs内存中敏感数据临时存储容器停止即消失
# Volume（推荐生产使用）
docker volume create pgdata
docker run -d --name db \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16

# Bind Mount（开发环境代码热重载）
docker run -d --name dev \
  -v $(pwd)/src:/app/src \
  -p 8000:8000 \
  myapp:dev

# tmpfs（内存存储，适合存临时密钥）
docker run -d --name secure \
  --tmpfs /run/secrets:rw,size=64m \
  myapp:v1
⚠️ 常见坑：-v /host/path:/container/path 如果宿主机路径不存在，Docker 会自动创建空目录（不会报错），导致容器内看到空目录覆盖了原有文件。调试时经常踩这个坑。
面试题：Volume 和 Bind Mount 的区别？生产应该用哪个？

参考答案：Volume 由 Docker Daemon 管理，存在 /var/lib/docker/volumes/ 下，支持驱动扩展（如 NFS、云存储），可被多个容器安全共享，是生产环境首选。Bind Mount 直接映射宿主机路径，性能略好但与宿主机文件系统耦合，适合开发环境的代码热重载。生产环境应使用 Volume，原因：① 可移植性好（不依赖宿主机目录结构）；② 安全性好（不暴露宿主机文件系统）；③ 支持 backup/restore 工具链。

6. Docker Compose

💡
一句话：Compose 是管理多容器应用的「剧本」——一个 YAML 文件描述所有服务，一条命令全部拉起。

直觉理解

单独的 docker run 就像手动一个一个做菜。Compose 就像一份「宴席菜单」：定义好所有菜品（服务）、原料（镜像/构建）、调味（环境变量）、上菜顺序（依赖关系），然后喊一声「开始」——所有菜同时开做。

完整示例：FastAPI + PostgreSQL + Redis

# docker-compose.yml
version: "3.9"

services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/mydb
      - REDIS_URL=redis://cache:6379/0
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: mydb
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      timeout: 3s
      retries: 5

  cache:
    image: redis:7-alpine
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru
    volumes:
      - redis-data:/data

volumes:
  pgdata:
  redis-data:

常用命令

docker compose up -d          # 后台启动所有服务
docker compose ps             # 查看服务状态
docker compose logs -f api    # 查看 api 服务日志
docker compose exec api sh    # 进入 api 容器
docker compose down           # 停止并删除容器
docker compose down -v        # 停止并删除容器 + Volume（危险！）
docker compose build --no-cache  # 重新构建（不用缓存）

开发环境技巧

  • 用 volumes 挂载源代码实现热重载
  • 用 profiles 区分 dev/test 服务
  • 用 override 文件叠加配置

生产注意事项

  • Compose 适合单机部署，多机用 K8s
  • 敏感信息用 docker secret 或环境变量注入
  • 始终指定镜像版本号，不用 latest
面试题：depends_on 能保证服务就绪吗？

参考答案：depends_on 默认只保证依赖容器启动了，不保证服务就绪了。比如 PostgreSQL 容器启动后还需要几秒初始化数据库，此时 API 连接会失败。解决方案：① Compose v2 支持 condition: service_healthy，配合 healthcheck 等服务真正就绪后才启动依赖者；② 应用层做重试逻辑（指数退避）。

7. Kubernetes 架构全景

💡
一句话：K8s 就是容器世界的「操作系统」——你告诉它「我要 3 个 API 实例 + 1 个数据库」，它自动调度、部署、修复。

直觉理解

想象你经营一家连锁餐厅。你（开发者）只需要告诉总部（K8s）：「我要在 3 个门店各开一个窗口卖汉堡」。总部负责：选哪些门店（调度）、配送原料（拉取镜像）、监控出餐速度（健康检查）、如果某个窗口关了就自动开一个新的（自愈）。你不需要亲自跑到每个门店操作。

核心组件详解

Control Plane 组件

  • API Server：集群的「前台」，所有操作都经过它（kubectl、Dashboard、其他组件）
  • etcd：分布式键值存储，保存集群所有状态数据（唯一的有状态组件）
  • Scheduler：决定新 Pod 放在哪个 Node（考虑资源、亲和性、污点等）
  • Controller Manager：运行各种控制器（Deployment、ReplicaSet、Node Controller 等），确保实际状态 = 期望状态

Node 组件

  • kubelet：Node 上的「管家」，负责管理 Pod 生命周期，向 API Server 汇报状态
  • kube-proxy：维护网络规则（iptables/IPVS），实现 Service 到 Pod 的负载均衡
  • Container Runtime：实际运行容器的引擎（containerd / CRI-O），通过 CRI 接口与 kubelet 通信

声明式 vs 命令式

告诉 K8s 期望状态，它自己搞定

✅
核心哲学：K8s 是声明式系统。你定义「期望状态」（YAML），Controller 不断对比「实际状态 vs 期望状态」，自动修复差异。这就是Reconciliation Loop（调谐循环）。
面试题：etcd 在 K8s 中的角色？为什么它如此关键？

参考答案：etcd 是 K8s 集群的「唯一真相之源」（Single Source of Truth），存储所有资源对象的状态（Pod、Service、ConfigMap 等）。它是基于 Raft 共识算法的分布式键值数据库，保证强一致性。只有 API Server 直接读写 etcd，其他组件通过 API Server 间接访问。etcd 挂了 = 集群瘫痪（虽然已运行的容器不会立即停止，但无法做任何变更）。生产环境必须做 etcd 高可用（奇数节点，至少 3 个）和定期备份。

面试题：一个 Pod 从创建到运行的完整流程是什么？

参考答案：① 用户提交 YAML → API Server 验证并写入 etcd；② Scheduler watch 到未调度的 Pod，根据资源请求、亲和性、污点等策略选择 Node，把结果写回 etcd；③ 目标 Node 上的 kubelet watch 到分配给自己的 Pod，通过 CRI 接口调用 Container Runtime（containerd）拉取镜像、创建容器；④ kubelet 持续通过 Probe 监控容器健康状态，上报给 API Server；⑤ kube-proxy 更新 iptables/IPVS 规则，将 Service 流量路由到该 Pod。

💡
一句话：K8s 的对象就像乐高积木——Pod 是最小的砖块，Deployment 管理砖块的数量和更新，Service 给砖块一个稳定的门牌号。

对象层级关系

     │                                        │

Pod — 最小调度单位

apiVersion: v1
kind: Pod
metadata:
  name: myapp
  labels:
    app: myapp
    env: production
spec:
  containers:
  - name: api
    image: myapp:v1
    ports:
    - containerPort: 8000
    resources:
      requests:          # 调度时的最低保障
        cpu: "100m"      # 0.1 核
        memory: "128Mi"
      limits:            # 运行时的上限
        cpu: "500m"
        memory: "512Mi"
    livenessProbe:       # 存活检查：失败则重启
      httpGet:
        path: /health
        port: 8000
      initialDelaySeconds: 10
      periodSeconds: 15
    readinessProbe:      # 就绪检查：失败则从 Service 摘除
      httpGet:
        path: /ready
        port: 8000
      periodSeconds: 5

面试题：Pod 中为什么可以有多个容器？什么场景需要？

参考答案：Pod 内的容器共享网络命名空间（同一个 IP、通过 localhost 通信）和存储卷，适合需要紧密协作的场景。常见模式：① Sidecar：主容器 + 日志收集器（如 Fluentd）、代理（如 Envoy）；② Init Container：在主容器启动前执行初始化（等待依赖就绪、迁移数据库）；③ Ambassador：代理外部服务连接（如本地缓存代理）。但注意不要滥用多容器——如果两个容器不需要共享网络/存储，就应该放在不同 Pod 中。

面试题：requests 和 limits 的区别？设置不当会怎样？

参考答案：requests 是调度依据——Scheduler 保证 Node 有足够资源满足 requests；limits 是运行时上限——超过 CPU limit 会被节流（throttle），超过 Memory limit 会被 OOM Kill。设置不当的问题：① requests 设太高 → 资源浪费，Pod 调度困难；② requests 设太低 → 节点过载，Pod 互相抢资源；③ 不设 limits → 一个 Pod 可以吃掉整个 Node 的资源。最佳实践：通过监控实际使用量来设置，requests ≈ P50 使用量，limits ≈ P99 使用量的 1.5 倍。

面试题：kube-proxy 的 iptables 模式和 IPVS 模式有什么区别？

参考答案：iptables 模式：为每个 Service 的每个后端 Pod 生成一条 iptables 规则，流量通过规则链逐条匹配。当 Service/Pod 数量很多时（如数千个），规则数量爆炸，更新和匹配都变慢，延迟增加。IPVS 模式：基于 Linux 内核的 IPVS 模块（Layer 4 负载均衡器），使用哈希表查找后端，时间复杂度 O(1)，支持更多负载均衡算法（轮询、最小连接、加权等）。大规模集群（Service 数量 > 1000）推荐 IPVS 模式。

10. K8s 存储体系

💡
一句话：PV 是「硬盘」，PVC 是「申请单」，StorageClass 是「硬盘供应商」——开发者只需填申请单，K8s 自动分配硬盘。

存储对象关系

StorageClass ──(定义)──→ 存储类型（SSD/HDD、供应商）
     │
     │ 动态供给
     ▼
PersistentVolume (PV) ←──(绑定)──→ PersistentVolumeClaim (PVC)
     │                                     │
     │ 实际存储资源                          │ Pod 引用
     │ （NFS/EBS/Ceph/...）                 ▼
     │                                   Pod.spec.volumes
     │
     └─ 静态供给：管理员手动创建 PV
        动态供给：通过 StorageClass 自动创建（推荐）

动态供给实战

# StorageClass（通常集群管理员预先创建）
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: ebs.csi.aws.com    # AWS EBS CSI 驱动
parameters:
  type: gp3
  iopsPerGB: "50"
reclaimPolicy: Retain           # PVC 删除后 PV 保留数据
volumeBindingMode: WaitForFirstConsumer
---
# PVC — 开发者只需写这个
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-storage
spec:
  accessModes:
  - ReadWriteOnce               # 单 Node 读写
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 50Gi
---
# Pod 使用 PVC
apiVersion: v1
kind: Pod
metadata:
  name: db
spec:
  containers:
  - name: postgres
    image: postgres:16
    volumeMounts:
    - name: data
      mountPath: /var/lib/postgresql/data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: db-storage

访问模式对比

模式缩写含义场景
ReadWriteOnceRWO单 Node 读写数据库（最常用）
ReadOnlyManyROX多 Node 只读共享配置/静态资源
ReadWriteManyRWX多 Node 读写共享文件存储（NFS/CephFS）
⚠️ 常见坑：不是所有存储后端都支持 RWX。AWS EBS 只支持 RWO。如果你的 Pod 需要在多个 Node 上共享文件，需要用 EFS（NFS）或 CephFS。
面试题：reclaimPolicy 的 Retain 和 Delete 有什么区别？

参考答案：当 PVC 被删除时：Delete（默认）会自动删除对应的 PV 和底层存储资源（如 AWS EBS 卷），适合临时数据；Retain 会保留 PV 和数据，PV 状态变为 Released，需管理员手动清理或重新绑定，适合重要数据（如数据库）。生产环境的数据库存储必须用 Retain + 定期备份。

11. 部署策略

💡
一句话：部署策略决定「新版本怎么上线、旧版本怎么退场」——选错策略可能导致服务中断或故障扩散。

四种主流策略

策略原理停机时间回滚速度资源开销
Rolling Update逐步替换旧 Pod零中（回滚到旧 ReplicaSet）低（多 1-2 个 Pod）
Blue-Green新旧两套完整环境，切流量零快（切回旧环境）高（双倍资源）
Canary小流量灰度 → 逐步放大零快（减少金丝雀比例）中
Recreate先全部销毁，再全部创建有慢（重新部署）低

Rolling Update（K8s 默认）

# 滚动更新过程示意
时间线 →

Step 1:  [v1] [v1] [v1]           ← 初始状态，3 个旧 Pod
Step 2:  [v1] [v1] [v1] [v2]     ← maxSurge=1，创建 1 个新 Pod
Step 3:  [v1] [v1] [v2]          ← 新 Pod 就绪后，销毁 1 个旧 Pod
Step 4:  [v1] [v1] [v2] [v2]     ← 再创建 1 个新 Pod
Step 5:  [v1] [v2] [v2]          ← 销毁 1 个旧 Pod
Step 6:  [v1] [v2] [v2] [v2]     ← 再创建
Step 7:  [v2] [v2] [v2]          ← 完成！

配置关键参数：
  maxSurge: 1        # 更新时最多多出几个 Pod
  maxUnavailable: 0  # 更新时最多少几个 Pod（设 0 = 永不减少可用数）

面试题：如何实现零停机部署？需要注意什么？

参考答案：零停机部署需要多方面配合：① Rolling Update + maxUnavailable: 0，保证始终有足够 Pod 服务；② Readiness Probe，新 Pod 必须就绪后才接收流量；③ Graceful Shutdown，旧 Pod 收到 SIGTERM 后要完成处理中的请求再退出（设置 terminationGracePeriodSeconds）；④ preStop Hook，在 Pod 被杀前等一小段时间（如 5s），让 Service 的 Endpoint 更新传播完成，避免流量还打到已关闭的 Pod；⑤ PodDisruptionBudget，限制同时被驱逐的 Pod 数量。

12. 监控与运维

💡
一句话：K8s 的运维核心是「让集群自己照顾自己」——通过 Probe、HPA、日志三件套实现自愈和自动伸缩。

三种健康检查

Probe作用失败后果使用场景
Liveness检测容器是否还活着kubelet 重启容器检测死锁、内存泄漏导致的无响应
Readiness检测容器是否准备好接流量从 Service Endpoint 摘除启动初始化、依赖未就绪

spec:
  containers:
  - name: api
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8000
      initialDelaySeconds: 15     # 启动后等 15s 再检查
      periodSeconds: 20            # 每 20s 检查一次
      failureThreshold: 3         # 连续 3 次失败才重启
    readinessProbe:
      httpGet:
        path: /ready
        port: 8000
      periodSeconds: 5
      failureThreshold: 3
    startupProbe:
      httpGet:
        path: /healthz
        port: 8000
      failureThreshold: 30
      periodSeconds: 10            # 最多等 300s 启动

HPA — 自动水平伸缩

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-deployment
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70    # CPU 使用率超过 70% 则扩容
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容冷却 5 分钟
      policies:
      - type: Percent
        value: 10                       # 每次最多缩 10%
        periodSeconds: 60

面试题：Liveness 和 Readiness Probe 的区别？配置不当会怎样？

参考答案：Liveness 检测「是不是挂了」→ 失败则重启容器；Readiness 检测「能不能干活」→ 失败则从 Service 摘除（不接受流量）。配置不当的典型问题：① Liveness 太敏感（如 failureThreshold: 1）→ 应用偶尔慢一下就被重启，造成雪崩；② Readiness 没配 → 应用启动未完成就接收流量，导致 502；③ Liveness 检查了下游依赖 → 数据库挂了导致所有 Pod 被反复重启（应该只检查自身健康）。最佳实践：Liveness 只检查进程自身，Readiness 检查是否能提供服务（含关键依赖）。

面试题：HPA 的工作原理？有什么限制？

参考答案：HPA Controller 每 15s（默认）从 Metrics Server 获取 Pod 的资源使用数据，计算 期望副本数 = ceil(当前副本数 × 当前指标值 / 目标值)。限制：① 必须设置 resources.requests，否则无法计算使用率；② 默认只支持 CPU/内存，自定义指标需要 Prometheus Adapter；③ 缩容有冷却期（默认 5min），防止频繁抖动；④ 不适合突发流量——扩容有延迟（拉镜像 + 启动），应搭配预热或 KEDA 使用。

13. 面试高频题总结

💡
一句话：面试考的不是背 YAML 模板，而是「为什么这样设计」和「出了问题怎么排查」。

Docker 高频题

Q1：如何减小 Docker 镜像体积？

答：① 多阶段构建（编译和运行分离）；② 用 alpine/distroless 基础镜像；③ 合并 RUN 指令减少层数；④ 使用 .dockerignore 排除无关文件；⑤ 清理包管理器缓存（apt clean、pip --no-cache-dir）。实际效果：Go 应用从 ~800MB 降到 ~15MB，Python 应用从 ~1.2GB 降到 ~150MB。

Q2：Docker 的 Copy-on-Write 机制是什么？

答：Docker 镜像由多个只读层叠加而成，容器在最上面加一个可写层。当容器要修改某个文件时，先从只读层拷贝一份到可写层，然后修改可写层的副本——这就是 Copy-on-Write。好处：① 多个容器共享同一镜像的只读层，节省磁盘；② 容器之间互不影响。坏处：首次写入某文件时有额外的拷贝开销，所以数据库等写密集应用应该用 Volume 而不是容器层。

Q3：Docker 网络 bridge 模式的数据包流转路径？

答：外部请求 → 宿主机 eth0 → iptables DNAT（根据 -p 映射的端口规则）→ docker0 虚拟网桥 → veth pair → 目标容器 eth0。容器间通信：容器 A eth0 → veth pair → docker0 → veth pair → 容器 B eth0。容器访问外网：容器 eth0 → veth → docker0 → iptables SNAT/MASQUERADE → 宿主机 eth0 → 外部。

Kubernetes 高频题

Q4：K8s 中 Pod 被驱逐（Eviction）的原因有哪些？

答：① 节点资源压力：内存/磁盘不足时 kubelet 根据 QoS 等级驱逐 Pod（BestEffort → Burstable → Guaranteed）；② 抢占调度：高优先级 Pod 需要资源，驱逐低优先级 Pod；③ Taint/Toleration：Node 被打上 NoExecute taint 且 Pod 没有对应 toleration；④ 手动操作：kubectl drain 维护节点时驱逐所有 Pod。防止关键服务被驱逐：设置 PodDisruptionBudget + Guaranteed QoS（requests = limits）。

Q5：如何排查 Pod 一直处于 Pending 状态？

答：kubectl describe pod <name> 看 Events 部分。常见原因：① 资源不足：没有 Node 满足 requests（CPU/内存），解决方案：扩容节点或降低 requests；② 调度约束：nodeSelector/affinity/toleration 不匹配任何 Node；③ PVC 未绑定：PersistentVolumeClaim 找不到匹配的 PV（检查 StorageClass、容量、访问模式）；④ ResourceQuota 超限：Namespace 的资源配额用完了。

Q6：Deployment、StatefulSet、DaemonSet 的区别和应用场景？

答：Deployment：无状态应用，Pod 可以随意创建/销毁/调度，适合 API 服务、Web 服务器；StatefulSet：有状态应用，每个 Pod 有稳定的网络标识（pod-0、pod-1）和独立的持久存储，有序启动/停止，适合数据库、Kafka、ZooKeeper；DaemonSet：保证每个（或指定）Node 上运行一个 Pod 副本，适合日志采集（Fluentd）、监控 Agent（Node Exporter）、网络插件（Calico）。

Q7：Kubernetes 的 Service Mesh（如 Istio）解决什么问题？

答：Service Mesh 通过在每个 Pod 旁注入 Sidecar 代理（如 Envoy），把微服务治理能力从应用代码中剥离到基础设施层。解决的问题：① 流量管理：灰度发布、A/B 测试、故障注入、熔断限流；② 可观测性：自动收集请求延迟、成功率、调用链（无需改代码）；③ 安全：服务间 mTLS 加密、细粒度访问控制。代价：每个 Pod 多一个 Sidecar 容器，增加约 50-100MB 内存和 ~1ms 延迟。小规模集群不一定需要。

Q8：如何设计一个高可用的 K8s 集群？

答：① Control Plane 高可用：至少 3 个 Master 节点，etcd 3 或 5 节点（奇数，Raft 需多数派）；② Node 冗余：跨可用区（AZ）部署 Worker 节点，用 Pod Anti-Affinity 保证副本分散；③ 应用层：Deployment replicas ≥ 2 + PDB 限制最大不可用数 + Readiness Probe；④ 网络：Ingress Controller 多副本 + 云 LB；⑤ 存储：etcd 定期备份（velero）、数据库用跨 AZ 持久存储；⑥ 监控告警：Prometheus + Grafana + PagerDuty，关键指标告警（节点 NotReady、Pod OOM、etcd 延迟）。

综合场景题

Q9：描述你如何将一个 Python 应用从本地开发部署到 K8s 生产环境？

答：完整流水线：

  1. 本地开发：Docker Compose 起本地环境（API + DB + Redis），代码 Bind Mount 热重载
  2. 编写 Dockerfile：多阶段构建（slim 基础镜像），非 root 用户，HEALTHCHECK
  3. CI 流水线：代码提交 → 运行测试 → 构建镜像 → trivy 安全扫描 → 推送到 ECR/GCR
  4. K8s 清单：Deployment（replicas=3，Rolling Update）+ Service（ClusterIP）+ Ingress（TLS）+ ConfigMap/Secret（环境配置）+ HPA（CPU 70%）
  5. 部署：kubectl apply 或 ArgoCD GitOps（推荐），Canary 灰度 10% → 观察 → 全量
  6. 运维：Prometheus 监控 + Grafana 仪表盘 + 告警（P99 延迟、错误率、Pod 重启次数）
Q10：容器化部署中最容易被忽视的安全问题有哪些？

答：① 以 root 运行：容器内默认是 root，一旦容器逃逸就是宿主机 root。解决：Dockerfile 中 USER 非特权用户 + K8s securityContext runAsNonRoot；② 特权容器：privileged: true 等于关掉所有隔离，除非必须（如 CNI 插件）否则禁用；③ 镜像漏洞：基础镜像不更新，含已知 CVE。解决：CI 中集成 trivy/snyk 扫描；④ Secret 明文：K8s Secret 只是 Base64，RBAC 权限过宽则任何人可读。解决：用 Sealed Secrets 或 Vault；⑤ 网络未隔离：默认所有 Pod 互通。解决：用 NetworkPolicy 限制 Pod 间通信。
