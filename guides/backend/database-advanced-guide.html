索引原理

索引是数据库的目录——用空间换时间，让查询从全表扫描 O(n) 降到 B+ Tree 查找 O(log n)。理解索引原理是 SQL 优化的根基。

B+ Tree 结构

MySQL InnoDB 默认使用 B+ Tree 作为索引数据结构（非 B Tree）。

[ 10 | 20 | 30 ] ← 非叶子节点（只存 key + 指针） / | | \ [ 1|5|8 ] [12|15] [22|25] [35|40] ← 叶子节点（存 key + 数据/主键） ↓ linked list → → → → → → → → → → → → ← 叶子节点双向链表（范围查询）
  • 所有数据在叶子节点：非叶子节点只存索引键，一个节点可存更多 key → 树更矮 → 磁盘 IO 更少
  • 叶子节点有序链表：天然支持 WHERE age BETWEEN 20 AND 30 范围扫描
  • 聚簇索引：InnoDB 主键索引的叶子节点直接存整行数据；二级索引叶子存主键值（回表）
💡
为什么不用 Hash 索引？Hash 只支持等值查询（=），不支持范围查询和排序。Memory 引擎支持 Hash，但 InnoDB 自适应 Hash 是内部优化，不暴露给用户。

索引类型

主键索引 PRIMARY

每张 InnoDB 表必须有且只有一个聚簇索引。没显式定义主键时，MySQL 会选第一个 UNIQUE NOT NULL 列，或隐式创建 6 字节 row_id。

CREATE TABLE alerts (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(256) NOT NULL
);

唯一索引 UNIQUE

保证列值唯一，允许 NULL（NULL 可重复）。常用于业务唯一键。

CREATE UNIQUE INDEX uk_task_id
  ON analysis_results(task_id);

联合索引 Composite

多列组合索引，遵循最左前缀原则：(a,b,c) 可加速 a、a,b、a,b,c，不能加速 b 或 c 单独查询。

CREATE INDEX idx_biz_status_time
  ON alerts(biz_line, status, created_at);

覆盖索引 Covering

查询所需列全在索引中，无需回表。EXPLAIN 的 Extra 显示 Using index。

-- idx(biz_line, status, created_at)
SELECT biz_line, status, created_at
FROM alerts
WHERE biz_line = 'im' AND status = 'pending';

全文索引 FULLTEXT

用于自然语言文本搜索（MATCH ... AGAINST）。MySQL 5.7+ InnoDB 支持；PostgreSQL 用 tsvector + GIN 更强大。Agent 场景若需语义搜索，优先考虑 pgvector 而非 FULLTEXT。

MySQL 如何选择索引

优化器基于成本模型选择索引，主要考量：

因素说明
选择性（Cardinality）区分度越高越好。性别字段（2 值）索引几乎无用
最左前缀匹配联合索引必须从左列开始匹配 WHERE 条件
索引列数量多个可用索引时，优化器估算各索引扫描行数
统计信息ANALYZE TABLE 更新 Cardinality，影响优化器决策
索引合并多个单列索引可能 Index Merge（通常不如联合索引）

EXPLAIN 输出解读

EXPLAIN SELECT * FROM alerts
WHERE biz_line = 'im' AND status = 'done'
ORDER BY created_at DESC LIMIT 20;
列含义理想值
type访问类型const > eq_ref > ref > range > index > ALL
key实际使用的索引非 NULL
rows预估扫描行数越小越好
Extra额外信息Using index（覆盖）最好；避免 Using filesort / Using temporary
possible_keys候选索引参考用，不一定使用
生产环境用 EXPLAIN ANALYZE（MySQL 8.0.18+）获取真实执行时间和行数，比传统 EXPLAIN 估算更准确。

索引选择性

-- 计算选择性 = DISTINCT 值数 / 总行数
SELECT
  COUNT(DISTINCT biz_line) / COUNT(*) AS biz_selectivity,
  COUNT(DISTINCT status)     / COUNT(*) AS status_selectivity
FROM alerts;
-- biz_line ≈ 0.01（100 个业务线）→ 适合索引
-- status ≈ 0.000003（3 种状态）→ 单独索引价值低

经验法则：选择性 < 0.01 的单列索引通常效果差，应放入联合索引或放弃。

什么时候不该加索引

  • 小表：几百行的配置表，全表扫描比索引查找更快
  • 写多读少：每次 INSERT/UPDATE 都要维护索引，Agent 日志表若只写不查，索引是负担
  • 低选择性列：性别、布尔值、状态（仅 2-3 值）单独建索引无效
  • 频繁更新的列：索引维护成本高，引发页分裂
  • 索引过多：优化器选择困难，写入性能下降。单表索引建议 ≤ 5 个
  • 冗余索引：(a,b) 已存在时，(a) 是冗余的

SQL 优化

慢 SQL 是线上 P0 故障的常见根因。优化路径：发现 → EXPLAIN 分析 → 改索引/改 SQL → 验证。

-- 分析工具

# 或 pt-query-digest（Percona Toolkit）
🔍
Agent 服务还要监控应用层慢查询：Go 用 db.SetConnMaxLifetime + 中间件记录 >500ms 的 SQL；Python 用 SQLAlchemy event listener。

常见反模式

❌ SELECT *

-- 坏：回表取所有列，含 TEXT/BLOB
SELECT * FROM analysis_results
WHERE task_id = 'abc123';

-- 好：只取需要的列，可能覆盖索引
SELECT id, status, summary
FROM analysis_results
WHERE task_id = 'abc123';

❌ 前导通配 LIKE

-- 坏：'%keyword' 无法使用 B+ Tree
WHERE title LIKE '%OOM%'

-- 好：前缀匹配可用索引
WHERE title LIKE 'OOM%'

-- 更好：全文索引或 Elasticsearch

❌ 索引列上套函数

-- 坏：对 indexed_col 运算，索引失效
WHERE DATE(created_at) = '2026-09-12'
WHERE YEAR(created_at) = 2026

-- 好：范围查询保留索引
WHERE created_at >= '2026-09-12'
  AND created_at < '2026-09-13'

❌ 隐式类型转换

-- phone 是 VARCHAR，传入 INT → 全表扫描
WHERE phone = 13800138000

-- 正确：类型一致
WHERE phone = '13800138000'

-- 规则：字符串列 vs 数字 → 字符串转数字 → 索引失效

JOIN 优化

  • 小表驱动大表：优化器通常自动选择，但 JOIN 顺序影响中间结果集大小
  • JOIN 列加索引：ON 条件两侧都应有索引，type 达到 ref/eq_ref
  • 避免 JOIN 过多表：超过 3-4 表考虑反范式或应用层组装
  • STRAIGHT_JOIN：强制 JOIN 顺序（优化器选错时用）
-- Agent 场景：分析结果 JOIN 业务线配置
SELECT r.id, r.summary, b.display_name
FROM analysis_results r
INNER JOIN biz_lines b ON r.biz_line = b.code   -- b.code 需索引
WHERE r.status = 'completed'
  AND r.created_at >= '2026-09-01'
ORDER BY r.created_at DESC
LIMIT 50;

子查询 vs JOIN

子查询

MySQL 8.0 前常产生临时表；适合 EXISTS 半连接、少量结果集。

SELECT * FROM alerts a
WHERE EXISTS (
  SELECT 1 FROM alert_tags t
  WHERE t.alert_id = a.id
    AND t.tag = 'critical'
);
vs

JOIN

大表关联通常更快；优化器选择 Hash Join / Nested Loop。

SELECT a.* FROM alerts a
INNER JOIN alert_tags t
  ON t.alert_id = a.id
WHERE t.tag = 'critical';
经验：MySQL 8.0+ 优化器对子查询改进很大，但仍建议用 EXPLAIN 对比两者。IN (SELECT ...) 大结果集时 JOIN 通常更优。

Index Hint（索引提示）

-- 强制使用指定索引
SELECT * FROM alerts
USE INDEX (idx_biz_status_time)
WHERE biz_line = 'im' AND status = 'pending';

-- 忽略某个索引
SELECT * FROM alerts
IGNORE INDEX (idx_status)
WHERE status = 'pending';

-- 强制使用（优化器认为更差时也用）
SELECT * FROM alerts
FORCE INDEX (idx_biz_status_time)
WHERE biz_line = 'im';
Index Hint 是最后手段——优先修正索引设计和统计信息。Hint 硬编码在 SQL 中，表结构变化后可能适得其反。

事务与锁

并发环境下，事务保证数据一致性。Agent 服务常见场景：任务状态更新、幂等写入、分布式锁——都需要理解隔离级别和锁机制。

ACID 特性

A — Atomicity 原子性

事务内操作要么全成功，要么全回滚。InnoDB 通过 undo log 实现。

C — Consistency 一致性

事务前后数据满足完整性约束（外键、唯一、CHECK）。

I — Isolation 隔离性

并发事务互不干扰。由隔离级别 + 锁 + MVCC 共同实现。

D — Durability 持久性

提交后数据不丢。InnoDB 通过 redo log + 双写缓冲保证。

隔离级别

级别脏读不可重复读幻读实现
Read Uncommitted✅ 可能✅✅几乎不用
Read Committed❌✅ 可能✅Oracle 默认；每次 SELECT 新快照
Repeatable Read❌❌⚠️ 部分MySQL InnoDB 默认；MVCC + Gap Lock
Serializable❌❌❌串行执行，性能最差
-- 查看/设置隔离级别
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

MVCC（多版本并发控制）

InnoDB 每行隐藏列：DB_TRX_ID（最后修改事务 ID）、DB_ROLL_PTR（undo log 指针）。

  • Read View：事务开始时创建快照，记录活跃事务 ID 列表
  • 可见性判断：行的 TRX_ID 如果在 Read View 创建前已提交 → 可见；否则沿 undo log 找历史版本
  • RR vs RC：RR 在第一次 SELECT 创建 Read View 并复用；RC 每次 SELECT 新建 Read View
📌
MVCC 让普通 SELECT 不加锁也能保证一致性读。写操作（UPDATE/DELETE）仍需要行锁。

Gap Lock 与 Next-Key Lock

Record Lock：锁定索引记录（行锁）。
Gap Lock：锁定索引记录之间的间隙，防止幻读插入。
Next-Key Lock = Record Lock + Gap Lock，锁定记录及其前面的间隙。

-- 事务 A（RR 级别）
BEGIN;
SELECT * FROM alerts WHERE id > 10 AND id < 20 FOR UPDATE;
-- 锁住 (10, 20) 区间，其他事务无法 INSERT id=15

-- 事务 B
INSERT INTO alerts (id, ...) VALUES (15, ...);  -- 阻塞等待
Gap Lock 仅存在于 RR 级别 + 非唯一索引 / 范围查询。等值查询唯一索引时退化为 Record Lock。

死锁检测与处理

InnoDB 自动检测死锁：回滚代价较小的事务（修改行数少），另一个继续执行。

-- 查看最近一次死锁
SHOW ENGINE INNODB STATUS\G
-- LATEST DETECTED DEADLOCK 段落

-- 应用层处理
// Go: 捕获 Error 1213 (Deadlock)，指数退避重试
for i := 0; i < maxRetries; i++ {
    err = tx.UpdateStatus(...)
    if !isDeadlock(err) { break }
    time.Sleep(time.Duration(1<<i) * time.Millisecond)
}

预防：固定加锁顺序（先锁 id 小的行）、缩短事务、避免大事务、索引加速减少锁范围。

SELECT FOR UPDATE

-- 悲观锁：读取并锁定，其他事务不能修改
BEGIN;
SELECT status FROM analysis_tasks
WHERE task_id = 'task-001'
FOR UPDATE;   -- 行锁

-- 若 status == 'pending'，更新为 running
UPDATE analysis_tasks SET status = 'running'
WHERE task_id = 'task-001';
COMMIT;

-- 变种
FOR SHARE     -- 共享锁（S 锁），允许读不允许写
FOR UPDATE NOWAIT  -- 不等待，锁冲突立即报错（MySQL 8.0+）
FOR UPDATE SKIP LOCKED  -- 跳过已锁行，适合任务队列抢单
🎯
Agent 任务调度：SELECT ... WHERE status='pending' ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED 是经典抢任务模式，多 Worker 并发不阻塞。

连接池管理

数据库连接建立代价高（TCP 握手 + 认证 + 内存分配）。连接池复用连接，是后端服务稳定性的基础设施。

为什么需要连接池

  • MySQL 默认 max_connections = 151，无池化时每个 HTTP 请求新建连接，瞬间打满
  • 连接创建 ~1-5ms，池化后获取连接 ~0.01ms
  • 控制并发连接数，保护数据库不被压垮

核心参数

参数含义建议
min / idle最小空闲连接数保持预热，避免冷启动延迟
max最大连接数按公式估算（见下），不超过 MySQL max_connections 的 70%
idle timeout空闲连接回收时间5-10 分钟，过长占资源，过短频繁重建
max lifetime连接最大存活时间30-60 分钟，避免 MySQL wait_timeout 断连后用脏连接
connect timeout获取连接超时3-5 秒，超时快速失败而非无限等待

连接泄漏检测

泄漏：借出连接未归还（忘记 Close / defer 缺失 / 异常路径未释放）。

-- MySQL 侧：查看连接来源
SHOW PROCESSLIST;
SELECT * FROM information_schema.processlist
WHERE db = 'alert_analysis' ORDER BY time DESC;

-- Go: 务必 defer rows.Close() 和 defer tx.Rollback()
rows, err := db.Query("SELECT ...")
if err != nil { return err }
defer rows.Close()  // 泄漏最常见原因
监控指标：pool_active / pool_max 持续 >80% 告警；pool_wait_count 持续增长说明池太小或泄漏。

Go database/sql 配置

import "database/sql"

db, err := sql.Open("mysql", dsn)
if err != nil { log.Fatal(err) }

db.SetMaxOpenConns(25)                  // 最大连接数
db.SetMaxIdleConns(10)                  // 最大空闲连接
db.SetConnMaxLifetime(30 * time.Minute) // 连接最大存活
db.SetConnMaxIdleTime(5 * time.Minute)  // 空闲连接超时 (Go 1.15+)

// 监控
stats := db.Stats()
log.Printf("open=%d inUse=%d idle=%d waitCount=%d",
    stats.OpenConnections, stats.InUse, stats.Idle, stats.WaitCount)

Python SQLAlchemy 配置

from sqlalchemy import create_engine

engine = create_engine(
    "mysql+pymysql://user:pass@host/db",
    pool_size=10,           # 常驻连接数
    max_overflow=20,       # 超出 pool_size 的临时连接
    pool_timeout=30,       # 获取连接超时（秒）
    pool_recycle=1800,     # 30 分钟回收（对应 max lifetime）
    pool_pre_ping=True,    # 使用前 ping，自动剔除断连
)
# 最大连接 = pool_size + max_overflow = 30

Agent 服务连接池 sizing

# 估算公式
pool_size = (core_count * 2) + effective_spindle_count
# 对于 IO 密集型 Agent 服务，可放宽到：
max_connections_per_instance = QPS * avg_query_time_seconds * safety_factor

# 示例：Agent 分析服务
# - 4 核 Pod，QPS ≈ 50，平均 SQL 耗时 20ms
# - 并发 SQL = 50 * 0.02 = 1（看起来很少）
# - 但 Agent 分析单次可能触发 5-10 条 SQL（读写 session/chat/result）
# - 实际并发 = 50 * 0.02 * 8 ≈ 8，加 3x 安全系数 → max_open = 25

# 多实例注意
# 10 个 Pod × 25 连接 = 250 → 需确保 MySQL max_connections ≥ 300
⚠️
Agent 服务 SQL 模式：短连接高频（状态更新）+ 偶尔长查询（历史检索）。不要把 max_open 设太大——Agent 瓶颈通常在 LLM API 而非 DB，50 连接足够大多数场景。

分库分表

单表数据量超过 5000 万行或单库 QPS 超过硬件上限时，需要考虑水平扩展。但分库分表是架构级决策，过早拆分代价极高。

垂直拆分 vs 水平拆分

垂直拆分（按业务）

不同业务模块用不同数据库。

  • 用户库 / 订单库 / 告警分析库
  • 减少单库压力，团队自治
  • 无法解决单表过大问题
→

水平拆分（按 Key）

同一张表的数据分散到多个库/表。

  • analysis_results_0 ~ _15
  • 解决单表数据量和写入瓶颈
  • 引入跨分片查询复杂度

分片策略

Range 范围

按 ID/时间范围分片

shard_0: id 0~1M
shard_1: id 1M~2M

✅ 范围查询友好
❌ 热点集中在最新分片

Hash 哈希

hash(key) % N

shard = hash(task_id) % 16

✅ 数据均匀
❌ 扩容需 rehash

Consistent Hash

一致性哈希环

vnode → physical node
扩缩容只迁移部分数据

✅ 平滑扩容
❌ 实现复杂

跨分片查询

分片后最痛苦的问题——尽量避免，设计时让查询带分片键。

场景方案
带分片键查询直接路由到目标分片 ✅
不带分片键广播到所有分片 + 应用层聚合 ❌ 慢
跨分片 JOIN禁止；改为应用层组装或冗余数据
全局排序分页各分片取 Top-N → 归并排序（不精确）或 ES
聚合 COUNT/SUM各分片分别聚合 → 汇总

分布式 ID：Snowflake

// 64 bit ID 结构
// | 1bit符号 | 41bit时间戳 | 10bit机器ID | 12bit序列号 |
// 每毫秒 4096 个 ID，可用 69 年

// Go 简化示例
type Snowflake struct {
    epoch    int64
    nodeID   int64
    sequence int64
    mu       sync.Mutex
}

func (s *Snowflake) NextID() int64 {
    s.mu.Lock()
    defer s.mu.Unlock()
    now := time.Now().UnixMilli() - s.epoch
    if now == s.lastTimestamp {
        s.sequence = (s.sequence + 1) & 0xFFF
    } else {
        s.sequence = 0
    }
    s.lastTimestamp = now
    return (now << 22) | (s.nodeID << 12) | s.sequence
}

替代方案：MySQL AUTO_INCREMENT（分片后冲突）、UUID（无序影响 B+ Tree 插入性能）、Redis INCR、数据库号段模式。

迁移策略

  1. 双写：新旧库同时写入，验证一致性
  2. 数据同步：Canal / Debezium 监听 binlog 同步历史数据
  3. 灰度切读：按用户/业务线逐步切到新库读
  4. 切写 + 停双写：确认无差异后完全切换
  5. 清理：旧库保留备份一段时间后下线

什么时候不该分库分表

🛑
Premature Optimization 警告：以下情况先优化索引/SQL/硬件，不要急着分片：
  • 单表 < 1000 万行，查询仍可通过索引优化
  • 团队没有分片中间件经验（ShardingSphere / Vitess）
  • 业务查询大量不带分片键（跨分片噩梦）
  • Agent 分析结果表——写入量大但查询按 task_id/biz_line，单库 + 归档足够

MySQL vs PostgreSQL

两者都是成熟的开源 RDBMS，但设计哲学不同：MySQL 偏简单高效 OLTP，PostgreSQL 偏功能丰富 + 扩展性。Agent 服务选型取决于是否需要向量搜索和复杂查询。

Redis 数据结构与应用

Redis 是内存 KV 存储，单机 10 万+ QPS。Agent 服务中用于缓存、限流、会话、任务队列、分布式锁——几乎每种后端架构都离不开 Redis。

五种核心数据结构

String 最基础

缓存：热点数据缓存，TTL 自动过期

SET biz:im:config "{...}" EX 3600
GET biz:im:config

# 限流（固定窗口）
INCR rate:api:user123:2026091213
EXPIRE rate:api:user123:2026091213 60
# count > 100 → 拒绝

Hash 字段级

Session 存储：Agent 会话上下文

HSET session:abc123
  user_id "u001"
  biz_line "im"
  agent_type "cursor"
  last_active "1694510400"

HGETALL session:abc123
EXPIRE session:abc123 86400

List 有序队列

消息队列：简单 LPUSH/BRPOP

LPUSH task:queue '{"task_id":"t001"}'
BRPOP task:queue 30  # 阻塞消费

# 可靠队列：RPOPLPUSH 到 processing 列表
RPOPLPUSH task:queue task:processing

Set 去重集合

去重：已处理告警 ID、标签集合

SADD processed:alerts "alert-001"
SISMEMBER processed:alerts "alert-001"
# → 1（已处理，跳过）

SCARD processed:alerts
# 集合大小

Sorted Set (ZSet) 有序 + 去重

排行榜：Agent 分析耗时排名

ZADD leaderboard 12.5 "task-001"
ZADD leaderboard 8.3  "task-002"
ZREVRANGE leaderboard 0 9 WITHSCORES

延迟队列：定时任务调度

ZADD delay:queue 1694514000 "task-001"
# score = 执行时间戳
ZRANGEBYSCORE delay:queue 0 {now}
# 取出到期任务

TTL 策略

数据类型TTL 建议说明
热点配置缓存1-24 小时变更时主动 DEL，TTL 作兜底
Session30 分钟 - 24 小时滑动过期：每次访问 EXPIRE 续期
限流计数器窗口大小（60s/3600s）自动过期，无需清理
分析结果缓存5-30 分钟DB 是 source of truth，缓存可丢
分布式锁10-30 秒必须设 TTL，防死锁
避免大量 key 同时过期导致 CPU 尖刺：TTL 加随机偏移 EX 3600 + random(0, 300)。

内存优化

  • ziplist / listpack：小 Hash/List/ZSet 自动紧凑编码（<64 元素且 value <64B）
  • 控制 key 数量：100 万个小 key 比 1 个大 Hash 浪费更多内存（每个 key ~50-100B 元数据）
  • 选择合适数据结构：能 Hash 就不 String（HSET session:id field val vs 多个 SET session:id:field）
  • maxmemory-policy：allkeys-lru（缓存场景）或 volatile-lru（混合持久化）
# redis.conf
maxmemory 2gb
maxmemory-policy allkeys-lru
hash-max-listpack-entries 128
hash-max-listpack-value 64

持久化：RDB vs AOF

RDB 快照

  • 定时 fork 子进程写磁盘
  • 文件紧凑，恢复快
  • 可能丢失最后一次快照后的数据
  • 适合：可重建的缓存
vs

AOF 日志

  • 每条写命令追加到文件
  • everysec 模式最多丢 1 秒
  • 文件大，恢复慢（rewrite 压缩）
  • 适合：Session / 队列等不可丢数据
生产推荐 RDB + AOF 混合持久化（Redis 4.0+）：AOF rewrite 时用 RDB 格式写入，兼顾恢复速度和数据安全。

Redis Cluster

16384 个 hash slot 分布在多个 master 节点，key 路由：CRC16(key) % 16384。

  • 最少 3 主 3 从：每个 master 配 replica 做 failover
  • 跨 slot 操作受限：MGET/MSET 的 key 必须在同一 slot；用 {hash_tag} 强制同 slot
  • 扩容：reshard slot 到新节点，在线迁移
  • 客户端：Go 用 go-redis ClusterClient；需处理 MOVED/ASK 重定向
# hash tag：只有 {} 内部分参与 hash
SET user:{123}:profile "..."
SET user:{123}:session "..."
# 两个 key 在同一 slot，可事务操作

B+ Tree 索引 vs Hash 索引，数据库为什么默认用 B+ Tree？

B+ Tree：

  • 叶子节点有序链表 → 支持范围查询（BETWEEN、>、ORDER BY）
  • 非叶子节点不存数据 → 单个节点容纳更多 key → 树高低 → 磁盘 IO 少
  • 稳定 O(log n) 查询、插入、删除

Hash 索引：

  • 等值查询 O(1)，但不支持范围查询和排序
  • Hash 冲突需链表解决，退化 O(n)
  • 只适用于 Memory 引擎或精确匹配场景（如 Redis 内部）

结论：数据库查询模式以范围扫描 + 排序为主，B+ Tree 是更通用的选择。

MySQL Repeatable Read 如何避免幻读？

RR 通过 MVCC + Gap Lock/Next-Key Lock 组合防止幻读：

  1. 快照读（普通 SELECT）：MVCC Read View 保证同一事务内多次读取结果一致
  2. 当前读（SELECT FOR UPDATE / INSERT / DELETE）：Next-Key Lock 锁定记录 + 间隙，阻止其他事务在范围内插入新行
-- 事务 A
BEGIN;
SELECT * FROM alerts WHERE id > 100 FOR UPDATE;
-- Next-Key Lock 锁住 (100, +∞)

-- 事务 B 无法 INSERT id=150 → 不会幻读

注意：纯快照读（不加 FOR UPDATE）在 RR 下仍可能"看到"其他事务新插入的行（一致性读不保证避免幻读），只有当前读 + 锁才完全防止。

如何优化一条慢 SQL？完整排查流程是什么？
  1. 定位：slow_query_log / APM 工具 / SHOW PROCESSLIST 找到慢 SQL
  2. EXPLAIN：关注 type（避免 ALL）、key（是否走索引）、rows（扫描行数）、Extra（filesort/temporary）
  3. 分析原因：
    • 缺索引 → 加联合索引（遵循最左前缀）
    • 索引失效 → 检查函数、隐式转换、前导通配 LIKE
    • 回表多 → 改覆盖索引或减少 SELECT 列
    • 数据量大 → 分页优化（延迟关联）、归档历史数据
  4. 验证：EXPLAIN ANALYZE 对比优化前后
  5. 上线：低峰期加索引（Online DDL），监控 QPS 和延迟

实战练习：设计 Agent 分析结果存储 Schema

需求：为 gdp-gravitysvr-alertAnalysis 设计分析结果表，要求：

  1. 支持按 task_id 精确查询（幂等）
  2. 支持按 biz_line + status + 时间范围列表查询（分页）
  3. 存储分析摘要（TEXT）和完整 HTML 报告（可能 >1MB）
  4. 记录 Agent 类型、模型、耗时、token 用量
  5. 日增量 10 万条，保留 90 天
参考答案 
-- 主表：元数据 + 摘要（热数据）
CREATE TABLE analysis_results (
  id            BIGINT       NOT NULL AUTO_INCREMENT,
  task_id       VARCHAR(64)  NOT NULL COMMENT '幂等键',
  biz_line      VARCHAR(32)  NOT NULL,
  status        ENUM('pending','running','completed','failed') NOT NULL DEFAULT 'pending',
  agent_type    VARCHAR(16)  NOT NULL COMMENT 'cursor/claude/codex',
  model         VARCHAR(64)  DEFAULT NULL,
  summary       TEXT         COMMENT '分析摘要（通知用）',
  duration_ms   INT          DEFAULT NULL,
  token_input   INT          DEFAULT NULL,
  token_output  INT          DEFAULT NULL,
  report_url    VARCHAR(512) DEFAULT NULL COMMENT 'GCS 报告 URL',
  error_msg     VARCHAR(1024) DEFAULT NULL,
  created_at    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at    DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_task_id (task_id),
  KEY idx_biz_status_time (biz_line, status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 设计要点：
-- 1. task_id UNIQUE → 幂等写入 INSERT ... ON DUPLICATE KEY UPDATE
-- 2. idx(biz_line, status, created_at) → 覆盖列表查询 + ORDER BY
-- 3. 大 HTML 报告存 GCS（report_url），不进 DB → 避免行过大影响 B+ Tree
-- 4. summary TEXT 够用（通知摘要通常 <4KB）
-- 5. 90 天归档：定时任务 DELETE WHERE created_at < NOW()-INTERVAL 90 DAY
--    或 PARTITION BY RANGE (TO_DAYS(created_at)) 按月分区 DROP PARTITION

进阶优化：

  • Redis 缓存热点 biz_line 的 pending 任务数（INCR biz:im:pending）
  • completed 结果缓存 5 分钟（SET result:{task_id} ... EX 300）
  • 若需全文检索历史分析，同步到 Elasticsearch 而非 MySQL LIKE
